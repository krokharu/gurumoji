# Gurumoji 現行デザイン監査と実装可能な改善計画

監査基準日時: 2026-10-02 18:20–19:06 UTC（2026-10-03 JST）  
対象: `dot/cloud-cpu-setup` / `ddc23abe0d747a1e6cfd6d3bc262ce226f4756b0`、実装差分の直近 `59ebd24`  
作業: 現行コード・関連Software Vault・既存受入記録の読取、旧スクリーンショット5枚の画素閲覧、ソース分離Nodeプローブ。アプリコード変更・実データ操作・push・ローカルPC操作なし。

## 1. 結論

**見た目の全面刷新より、研究者が「何を実行したか／どの版を読んでいるか／次に何を確認するか」を理解して進められる設計を優先する。** 現行の紙色＋濃緑、3段階の新規作成、発話のコンパクト表示、4つの作業タブ、引用から音声へ戻る導線は継承できる。

先に解決すべき3点は以下。

1. **実行の入口と実態を一致させる（DG-01）**。画面はTransformer・AI見解の個別実行を案内するが、現在のCSSがその実行ボタンと分類ボタンを非表示にする。AI見解panel自体も案内された「内容・文脈検索」ではなく「概要」にある。新しい基礎pipelineはこの代替にはならない。APIがあることは人が使えるUIの証明にならない。
2. **手動測定を、意味を確認して採用するフローへする（DG-02）**。現行4入力欄は名前などだけで、実際の測定は本文文字数・数値・比率尺度・記述統計へ暗黙に固定される。少数試行後も研究者の確認を待たず採用される。さらに同ID編集で旧採用版が置換され、受付した定義v1と実行するv2が食い違う技術課題を再現した。測定規則の明示だけでなく、採用版の保全と固定版解決が必要。
3. **状態・表示版・保存先を一貫して見せる（DG-03/06/11）**。失敗中の大見出しが実行中を示す箇所がある。現在データ、固定run、計算完了、Vault書出し、研究者確認を1つの「完了」に潰さない。

### 判定の境界

- **原25件は再計上しない。** 既存レビューは15 addressed / 10 UI partial / 0 open。UI partialは実装がないという意味ではなく、修正版Windows実画面の受入待ち。原UI-01〜10、A01〜14、V01の完了状況を本監査で下げたり、ブラウザー未実施のまま上げたりしない。
- 今回の14項目は同じ性質ではない。新しいコード不整合、既知未対応UX-34の再確認、既存ADRの導入計画、旧画像からの改善仮説を区別した。**「14件の新規確定バグ」と数えない。**
- **現行HEADの実画面はこの監査では未確認。** 画素を見た5枚は元版 `4b311df` のWindows合成fixture。現在の余白・色・focus・文字潰れを測定したことにはならない。
- Nodeプローブは実ソース関数＋合成DOMであり、ブラウザー操作ではない。追加のPython検証は一時/メモリー内SQLiteを使った定義lifecycleと、合成adapters付きの元M0〜M7全体であり、実データや実出力ファイル/Vaultの受入ではない。独立担当の通常sandbox Chromiumも起動前のsocket制約で停止した。安全条件を緩めて再実行していない。
- P0に該当する新しい根拠は得ていない。上位のP1テーマはDG-01/02。追加調査でDG-02の内部に、別々に再現したP1技術課題T2（採用版保全）とT3（固定版と実行版の不整合）を明記した。「新規UI指摘を水増し」せず、「P1は2つだけ」と技術欠陥を過小報告もしない。原25件の判定とは別である。

## 2. 今のアプリを正しく理解する

### 2.1 現行の情報構造

### 2.2 既存の強みと、壊してはいけない条件

- 新規作成はファイル→設定→開始。段階的に詳細を開き、desktop/mobileで同じフォームを使う
- 文字起こしの処理中と編集中データのIDを分離。別データで作業中に処理完了しても勝手に作業を置き換えない
- 未保存の文字起こし、話者、分析設定、準備記録を移動時に守る。保存中に増えた変更も単純に保存済みへしない
- 話者CSVはプレビュー→未保存編集→通常保存。削除undo、失敗通知、競合draft退避、live regionは今回以前の改善に含まれる
- 根拠引用は生成時の本文・時刻・話者と照合。入力変更後の引用を無言で現在音声へつながない
- 分析は欠測、未実行、参照値、更新必要を区別する方向の保護を持つ。参加者名簿がないのに未発言者を0秒と補完しない
- グラフの代替表やCSV、方法の注意、対象集合・分母、保存済みrunの来歴を保持する
- 研究者の本文・タグ・別名・ノートを、見た目の変更のついでに上書きしない

根拠: `app.js:1111–1135,1247–1259`、`analysis-content.js:45–122`、`analysis-storage.js:43–69`、原25件受入表。ここに挙げた対策も現在の実GUI合格を意味しない。

### 2.3 古い設計文書と現行コードの差

`ui-screens.md` は「3つの上部タブ」「6段階」「画面側で順番に実行」「永続pipelineは後続」とする。一方、現在のtemplate/JS/backendは上部4入口とM0〜M7のサーバー永続pipelineを持つ。

新しい `analysis-milestone-visualization-design.md:19` は初回導入範囲を実装済みと明記する。したがって「永続化が未実装だから作る」という計画は誤り。現在の基礎pipelineの手法は発話量・会話の時間構造・手動測定で、47成果物、7つのLLM役割、全推測統計が一斉に提供されたわけでもない。

また、既存の通常分析APIのExcel出力と、pipeline固定packageからのXLSX未提供は別。両方を「Excel対応／非対応」の一語にまとめない。

## 3. 研究の仕事から整理する5フロー

### F1. 原音を確認し、分析可能な入力版へ整える

現在: 取込→処理→発話編集→明示保存→分析側の準備記録→入力の確認状態を保存。

改善: 対象名・本文版・未保存件数・未確認件数を同じコンテキスト帯に置く。表示上の「編集済み」「本文・区切り確認済み」「分析用に確認済み」を別の状態にする。AI修正案を適用しただけで人の照合済みへしない。

守るもの: 既存の原本保護、source hash、source segment ID、revision、準備記録。確認のために新しい保存体系を作らない。

### F2. 結果から根拠を確認して同じ場所へ戻る

現在: 結果の根拠details→発話本文・話者・時刻→音声で確認→発話編集画面→見解・文脈検索へ戻る。

改善: 現在の結果ページ／run／選択引用とfocus起点を復帰契約にする。desktopでは根拠pane、mobileでは全幅の根拠画面が候補。paneは「引用を見る」目的に留め、常時3カラムへ増やすことを前提にしない。

守るもの: 過去引用と現在の本文の区別、元音声がない時の本文代替、研究者未確定の候補表示、弱い推論を確定表現へ強めないこと。

### F3. 測定の意味を決め、試して採用する

現状の不足はDG-02。提案する順序は「定義→少数試行→研究者確認→採用→全件実行」。

必須の表示: 入力列、計算規則、分析単位、出力名、単位、型、尺度、集計手法、欠測、試行件数、少なくとも数件の入力と出力の対、適用できない場合の理由。自由記述の説明は構造化規則の代わりではない。

既存対応に限定: 入力列 `speaker/speaker_name/role/text/duration/characters/question_candidate`、規則 `identity/text_length/nonempty/duration/boolean_true`、手法 `frequency/descriptive`。未提供のLLMによる新概念・尺度自動生成を画面上で約束しない。IDは必要なら自動候補を出せるが、実保存IDと履歴は明示する。


### F3の技術依存: UIだけでは保証できない部分

| ID | 区分 | 現行契約と証拠 | 必要な設計 |
|---|---|---|---|
| DG-02-T1 / P2 | 試行レビューのAPI拡張依存 | `trial_definition:258–280` はinput_hash、values、件数を返すが、segment ID付きの個票、欠測理由、定義revision/hashを返さない | 少数の入力→出力対と欠測理由、試行時の定義版/入力hashを紐付ける。現在画面から後で推測補完しない |
| DG-02-T2 / P1 | 採用版保全の技術課題 | 台帳の主キーはitem+definition ID。adopted v1へ同IDのdraft v2を保存すると同じ行を置換し、adopted lookupはdefinition_not_adoptedになる | 新しいdraft ID/不変version等で旧adopted版と編集中draftを分ける。取消・試行失敗をしても旧採用版を選択可能にする |
| DG-02-T3 / P1 | 固定版の実行不整合 | bindingはdefinition_version=1を記録するが、worker開始時はIDだけで最新を取得。受付後v2へ変更するとv2を計算してしまう | 固定definition snapshotまたはID+version+hashの厳密取得。最小安全策は版不一致時に計算前で明示停止し、最新へ黙って置き換えない |

**再現の正確な範囲:** [definition-lifecycle-probe.json](definition-lifecycle-probe.json)は、合成in-memory SQLite、元workerの定義取得prefix、元manual stepで、v1文字数3に対しv2のduration60を`committed`にすることを確認。監査担当も同じprobeを再実行し一致した。

[definition-full-pipeline-probe.json](definition-full-pipeline-probe.json)は独立担当の補強検証。受付後のscheduleを一時停止して同IDを変更し、**元M0〜M7オーケストレーターを最後まで実行**すると、全段committed・pipeline completedになる。save adapterへ渡されるpackageはbinding v1／definitions v2／測定値60で混在した。method/save/publication adaptersとデータは合成で、SQLiteは一時領域。実手法・実保存ファイル・実Vault・GUIでの再現とはしない。

この追加検証は「既保存runが消えた」「すべてのrunが誤計算する」という主張ではない。**受付からworker読込までに同じ定義IDが変更される競合条件**で成立する。旧adopted payloadの台帳保全と、実行時の固定版解決は関連するが別の失敗モードとして追跡する。

最小の導入順は、(1)固定版不一致で安全停止、(2)draft/採用版の分離、(3)版付き試行レビュー、(4)明示採用と全件実行のUI接続。永続pipeline自体の作り直しは不要。既存SQLを破壊的に変更せず、必要な版付き情報を追加する。UI2〜4日という元概算だけで閉じず、技術契約と競合/再開回帰を含めて再見積りする。

受入は、受付v1→v2編集でもv1値3を使うか計算前で停止、draft取消後も旧採用版を使える、定義/入力が変わったら旧trialを採用根拠へ流用しない、実packageにも定義版/hashが一致する、まで分けて行う。

### F4. 実行・中断・部分成果を理解する

現在: 永続M0〜M7、実行チップ、バックグラウンド移動、中止、再試行、公開のみ再試行がある。

改善: 主見出しは利用者の状態説明、M番号や永続ゲートは補助。8段階のステッパーと3ノードの処理経路を両方常時強調せず、主表示は現在・完了・次の処理、詳細に内部段階を置く。progressが実作業量に比例しないなら「8段階中3完了」など根拠を添える。

次の操作: 待つ／不足入力を直す／失敗だけ再試行／保存済み結果を見る／公開だけ再試行を区別。失敗後も「バックグラウンドで続ける」という完走前提の文言に頼らない。

### F5. 過去の結果を見つけ、再現可能な出力として渡す

現在: run履歴、成果物リンク、Obsidianへのリンク、Vault再試行。既知UX-34として直近100件上限。

改善: 一覧filter、総数・上限、run選択、入力版、算出日時、対象集合、除外、設定版、モデル/版、表示中snapshot、出力内来歴を一連にする。研究者は「当時の結果を読む」と「現在の入力で計算し直す」を明確に選べる。

守るもの: A04/A05で改善されたstale/fingerprint/旧来歴の保持。不明な旧hashを現在値で埋めない。保存とVault公開を二軸で伝える。

## 4. 段階的な情報構造案

ADR-118の既存方針を採用しつつ、最初から全画面を差し替えない。

### 第1段階: 入口と用語の整合

- 上部4入口、作成3ステップ、データ作業4タブは維持
- 分析の主ボタンを実態に即した「基礎分析を実行」で統一。現在JSが表示時に「分析を実行」へ戻すため、ラベルを共通化
- テーマ分析・AI見解・分類の入口は適切なページに可視で置き、送信前確認と中止を同じ部品へ寄せる
- 「手動実行」は「測定を定義して実行」、「手動分析」は「研究者の確認・コード付け」など目的を分離。正式語彙は利用者の理解で検証して確定
- データ一覧／分析の補助ナビは上部と同じ意味を繰り返さず、対象コンテキストと戻り先へ整理

### 第2段階: 分析内の作業主語へ移行

| 主入口案 | 現行機能をどこから移すか | 初期実装の境界 |

| データ・出力 | 出力・検証、run履歴、各成果物、Vault状態 | 現在のプレビューと固定runを区別 |

全結果を新旧レイアウトへ二重描画せず、既存panel builderを再利用する。現在desktop/mobileの両contentを再構築しているので、値・選択・イベント・focusの回帰を確認し、技術刷新を導線改善の前提にしない。

## 5. 視覚体系: 維持するものと整えるもの

### 5.1 方向性

Gurumojiは、根拠を読む時間の長い研究用ワークスペースとして整える。濃緑は選択と主要操作、紙色は背景、白は作業面。既存の色の骨格を残し、装飾の光沢やカード数を増やすより、対象・内容・操作の優先順をはっきりさせる。

旧1440pxの根拠画面では、結果文と引用本文・話者・時刻・音声操作の近接は有用。旧結果編集画面でも、選択した発話の境界が明瞭。この良さを残してコンテキスト帯と操作密度を整える。現行修正版の視覚品質を旧画像だけで評点化しない。

### 5.2 トークンの提案

| 用途 | 現行 | 提案・条件 |
|---|---|---|
| 基本本文 | `--ink #18211d` | 維持 |
| 背景/作業面 | `#f4f5f0 / #fffef9` | 維持。階層は背景濃度・境界・余白の少数ルールで表す |
| 主要操作 | `#1c6b50` | 維持。白上6.425:1の指定色対 |
| 補助文 | `#68736e`、analysisのみ`#526159` | 役割tokenへ。小さく薄い文字を増やさない |
| 警告文字 | `--orange #e87941`の流用 | orange装飾とwarning-textを分離。文字は濃色に |
| focus | `rgba(28,107,80,.35)` | 不透明の識別しやすい色と3px枠を候補。各背景で検証 |
| タイプ階層 | root`.7rem`、各画面override多数 | title / section / body / label / caption / monoの役割を定義 |
| 余白 | 5/7/9/11/13等が多い | 4/8/12/16/24/32を基準候補に。既存表示の調整値まで機械的に置換しない |
| 角丸/影 | 7〜22px、画面と部品で多数 | panel、control、pillの3系統へ。選択・hoverを影だけで示さない |

fontは既存日本語system stackを継承。本文16px相当、操作label14〜15px相当、補助13px相当を候補に試す。これは製品の読みやすさの方針であり、「WCAGが16pxを要求する」という主張ではない。

指定色の計算は[specified-color-contrast.json](specified-color-contrast.json)に保存。独立反証でcascadeを追跡し、drop-zoneの通常背景は後続media queryのwhite、文字比率は3.128:1と補正した。基底gradientとの2.892〜3.029:1は現行画面比率として使わない。登録話者概要の未保存orangeは実gradient端点上2.627〜2.759:1。一方、analysis sidebarの未保存は濃色overrideで5.992:1あり、維持する反例。半透明保存バーやhover/selectedを含むcomputed styleは別途必要。既存mutedのcard上4.875:1を、淡い文字と同じ扱いにしない。

### 5.3 密度とレスポンシブ

- desktopの資料照合は本文・音声/動画・根拠の優先度で幅を配分。常時サイドバーを増やさない
- 959px以下の既存切替を当面維持。320pxでは横ナビの選択名、主操作、入力エラーを確実に読めるようにする
- 表は研究用途上の二次元性を維持し、横スクロールと同等のダウンロードを用意。全列をカードへ変換することを既定にしない
- 固定保存バーは未保存保護として残す。viewport・ソフトキーボード・拡大でfocusや編集中本文を完全に隠さない
- 多数発話の性能改善は別計測。見た目を軽くするために根拠や件数を黙って間引かない

## 6. 状態は少なくとも4軸で仕様化する

| 軸 | 例 | 主表示と操作 |
|---|---|---|
| 実行 | 未開始／受付／実行中／入力待ち／失敗／中止要求／中止／完了 | 現在処理、待つ理由、復旧、再試行、中止 |
| 結果 | 未実行／空／利用不可／参考値／一部／現行／更新必要 | 値の意味、対象/除外、過去版、実行できる場合の入口 |
| 保存/公開 | 未保存／保存中／保存済み／競合／Vault未書出し／公開失敗 | draft保全、退避、保存再試行、公開だけ再試行 |
| 人の確認 | AI/規則の候補／未確認／確認途中／採用／入力変更後要再確認 | 根拠、反例、確認者の判断、定義の採用 |

一つの緑バッジで4軸すべてを「完了」としない。表示形式は文字＋必要なicon＋色。長い説明は詳細へ置くが、結果の利用可否を変える注意は値や主操作の近くに残す。

空状態は「対象データなし」「絞込0件」「未実行」「入力不足」「欠測で計算不可」「取得失敗」を別にする。原因を示さず同じ「データがありません」で済ませない。今回旧UI-11の自動実行文言は既に撤回されているため、新規バグとして再掲しない。

## 8. 実GUI受入パック

### 必須fixture

合成データだけで以下を用意する。

- 空の環境、未分析1件、メディア無し2発話、短い合成音声、長い日本語・長いファイル名
- 数百〜数千発話、複数話者、UNKNOWN、時刻不明、除外、欠測、確認済み/未確認が混在
- 古いrun＋現在更新版、legacy来歴不明、100/101/201件履歴
- 409競合、500、通信断、逆順応答、保存中の追加編集、公開のみ失敗
- pipeline各状態、モデル未設定/未取得、外部送信OFF/有効設定

### 優先する操作

1. DG-01の3入口: 可視位置・accessible nameから通常クリック/Tab/Enterで到達。JS `.click()`やforce-clickで人の到達性を代用しない
2. DG-02: 秒数と文字数の異なる発話で試行し、ルールが期待値と一致。明示採用前はdraftのまま。旧採用版を保全し、受付v1→同ID v2編集の競合・再開でもv1使用または計算前停止を保証
3. 結果→根拠→音声/本文→戻る。表示run/入力版・ページ・選択引用・focusが一致
4. 入力編集→保存→更新必要→再実行。旧結果を残し、新旧を読み分ける
5. 失敗/取消/公開失敗→適切な回復。完了済み結果への導線と再試行の範囲が一致
6. 2タブ競合、削除undo、CSV preview、手動設定保持、live通知等、原UI-01〜10の修正版受入を再実施
7. 1440×900、390×844、320px、200%拡大、motion低減、キーボード、実スクリーンリーダーを区別して記録

### 記録に必ず残す

対象HEAD/差分hash、OS・ブラウザー・font、viewport/DPR/zoom、fixture ID、mockと実backendの範囲、操作、期待/実結果、画像、console/networkの要点、未実施。検証者の所見と計測値を分ける。

画面が見えること、クリックできること、APIが応答すること、保存・再読込が成立すること、実モデルの精度が妥当であることを同じ合格にしない。UI研究で利用者のタスク時間や理解率を測る場合も、今回のソース監査を実ユーザーテストと呼ばない。

## 9. DESIGN.mdの実用的な構成案

巨大な既存設計書を複写するのではなく、普段の実装時に参照できる短い正面入口にする。詳細は今回の監査・一次資料・既存契約へリンクする。

1. **目的・範囲・現在版**: Gurumojiが支援する研究作業、対象commit、初回実装能力、未提供、受入待ち。DG-13
2. **守る設計原則**: 入力所有権、候補と確定、根拠・分母・版、閲覧で実行しない、現実の保存先。原25件、AGENTS、ADR-118
3. **代表フロー**: F1〜F5。各フローに入口→情報→主操作→例外→復帰→完了を記載。DG-01/02/03/06
4. **情報構造と語彙**: 現行画面map＋段階移行map、互換URL、手動測定と手動解釈の違い。DG-05
5. **視覚token**: semantic color、type roles、spacing、radius、density、focus、motion。既存値/提案値/検証済みを別欄に。DG-08/09/12
6. **部品の契約**: 対象コンテキスト帯、結果card、根拠、測定定義form、試行レビュー、run状態、保存/競合、履歴、出力。DG-02/03/04/06/10/11
7. **状態と文言**: 4軸state matrix、empty/error/retry、外部送信、保存先、未提供の表示。DG-01/03/11
8. **アクセシビリティ/レスポンシブ**: label、keyboard、focus、live、selected navigation、表、拡大、motion、実AT受入。DG-07/09/10/12
9. **変更の安全境界**: 既存ID/API/SQL/ノート契約、無断外部送信なし、CSSだけで存在する操作を消さない、mock成功と実受入の区別
10. **実装順・受入・追跡**: DG ID→source→decision→component→test→result。未実施を未実施のまま残し、画像とHEADを紐付ける

### 追跡行の形

`DG-02 → definition/trial/adopt API → ManualDefinition + TrialReview → duration/character対照fixture → keyboard + API + revision検証 → 状態: 提案/実装/静的合格/GUI合格`
