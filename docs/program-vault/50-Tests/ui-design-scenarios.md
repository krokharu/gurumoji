# Gurumoji 研究作業シナリオと受入条件

第4稿 0.4 · 2026-10-02 UTC · 確認HEAD `88f5e3e`（0.3文書統合）／ソース基準 `ddc23abe`・実装 `59ebd24`  
これは実装と利用者検証に使う歩行仕様。実際の利用者テスト、現行HEADのブラウザー操作、AT音声確認を実施した結果ではない。

[仕様注釈付きv1](../40-Design/ui-design-assets/2026-10-02/prototypes/comparison.md)は8図。[clean v2](../40-Design/ui-design-assets/2026-10-02/prototypes/v2/index.html)はS02/S04に関係する1280px／390pxの比較8図＋定義変更後の補助2図。密度比較はv2を使い、開発条件は[画面外凡例](../40-Design/ui-design-assets/2026-10-02/prototypes/v2/outside-legend.md)へ分ける。[独立批評](ui-design-evidence/2026-10-02/mockup-critique.md)の初回／修正後レビューは同じ案の反復で、独立した評価件数として足さない。いずれも全長の静止図で、操作・保存・復帰の合格証拠ではない。規則・根拠数・対象数は各fixtureと照合する。

## 共通の実施条件

合成発話・合成音声・一時DB／Vault・stub providerを使用し、実研究データ／外部AI／追加モデルを必要としない。研究者役のタスク文にはボタン名や正解経路を入れず、操作可能性の自動試験ではrole／labelから通常操作する。初期fixture・遅延・失敗responseの注入は可。測定対象のclick／入力／visibility／navigationを内部state代入で代用しない。

記録はシナリオごとにcommit、環境、ブラウザー、viewport／拡大、合成fixture ID、経路、観測、API・保存結果、画像を結ぶ。V1 contract、V2 component、V3 browser操作、V4 AT、V5利用者理解を分け、passed／failed／not-runを明記する。画像だけ、JS clickだけ、説明できそうというエージェント判断だけで上位層を合格にしない。

まず1440px、390px、境界959/960px。該当箇所は320 CSS px相当、200%文字拡大、400%相当reflowも確認する。キーボードのみ、reduced-motion、Windows日本語font／IMEとATは独立条件。環境がない条件は未実施で残す。

## S01 個別の分析を見つけて実行する

**研究者の仕事:** 保存済みの会話にテーマ分析を追加し、何をどこへ送るか確認して開始する。別ケースでAI見解と発話分類も行う。

**入力:** 保存済み・dirtyなしの会話A、未実行／保存済み旧run／実行中の各fixture。provider未設定、モデル未取得、適格stubの3条件。対応: DG-01、W01、UX:K02/UX:K03。

1. データ一覧で会話Aを開き、画面の通常の案内から分析へ移る
2. 目的に対応する入口を見つけ、対象・処理・送信先・現在の条件を確認する
3. 条件不足なら理由と設定入口を確認し、中止する。適格条件では開始する
4. 連続して開始を押す。処理中に別画面へ移り、同じ分析の状態へ戻る。中止は取消対応のあるTransformer／AI見解で行い、分類の取消能力を装わない。分類Aの応答を遅延させてBへ移る分岐も別に試す
5. 保存済み結果を開く。この閲覧だけでは再実行しない

**受入:** 3入口がproduction CSS適用後に見えて通常pointer／Tabで操作可能。AI見解の案内先が実panel位置と一致。正しいAPI／item／providerが1回、dirty時は適切に止まる。取消対応のあるcontrolは実running状態で可視。分類Aの遅延応答がBのstate／成功通知を変更しないことを照合する。基礎分析のみを実行して個別分析が済んだように表示しない。

**送信内容の照合:** AI見解の合成prompt captureで、発話、話者識別子／名前／役割、研究目的、コードID／label、重要フラグと、expert時の短い説明・許可手順情報を説明文へ対応付ける。除外発話や空本文を省く条件と、単なる画面filterを混同しない。LM Studioを含む実際の設定接続先を示し、閲覧端末内の処理とは断定しない。全文の研究ノート・文献・音声まで送るとは補完しない。[独立契約確認](ui-design-evidence/2026-10-02/microcopy-contract-review.md)はcall引数の合成捕捉であり、外部AI接続試験ではない。

**理解の問い:** 「今回実行した処理と送信先は何ですか」「保存済みの結果を見るだけで新しい処理は走りましたか」。正しく説明できたか、どこで迷ったかを記録する。

**失敗時:** 入口が非表示ならV3失敗。JSでbuttonを押せることを代替合格にしない。stub成功を実モデル品質・外部サービス接続成功と呼ばない。

## S02 定義したつもりの測定と実際の値を照合する

**研究者の仕事:** 各発話の長さを秒数で測る変数を作り、少数例を見てから全件へ適用する。

**入力:** e1本文「あいう」＝3文字・0〜60秒、e2本文「abcdefghij」＝10文字・70〜72秒、e3はstart/end欠測またはtime_unknown=true（durationの保存値が0でも欠測）、e4はstart=end=80・duration=0・time_unknown=falseの真の0秒。本文文字数とdurationの順位を逆にする。手動測定の名称・説明は「発話の長さ」「各発話の持続時間を秒数で測る」。対応: DG-02、W02、PR:T11、UX:K03/UX:K06/UX:K09。

1. 手動測定を開き、名称だけでなく入力列・規則・型・尺度・単位・手法を確認する
2. durationの定義で少数試行を行い、e1=60、e2=2、e3=欠測理由付き、e4=0の個別値を見る
3. 一度閉じる／取り消す。採用や全件実行が発生していないことを確認する
4. 再度開き、文字数へ変更して試す。e1=3、e2=10となり、秒数を意味しない説明へ変わることを確かめる
5. durationへ戻し、試行値を確認して明示採用する。その定義revisionで全件実行する
6. 別条件として名義尺度のまま平均を求める手法を選び、fieldに紐付いた拒否理由を見る

**受入:** 説明文だけを変更して規則が変わったように見せない。限定文字数案を採る場合はduration作成を明示的に利用不可とし、このシナリオは機能限定として記録する。対応版では採用前のadopted PUT／pipeline POSTが0回、採用後のpayload・固定版・結果が一致。受付後に版が変わった場合は旧固定内容で実行するか理由付きで安全停止し、別版の値を正常確定しない。名義尺度に平均を出さず、欠測を0にしない。

**追加の競合:** 試行後に定義変更、別itemへ移動、入力revision更新、二重submit、保存409、別definition IDへ変更を行う。古い試行をそのまま新定義の採用証拠にせず、未保存入力と旧採用版を保護する。既adopted IDの編集試行は別draft ID等へ分離し、取消後に旧採用payloadが変わらないことをDBで確認する。受付後に別タブで定義を変える／処理を再起動・retryする条件でも、固定した定義内容と実結果を照合する。

**v2から引き継ぐ条件:** 試行した定義版・入力版、全体→除外→試行数、測定の限界が採用前に見える。補助失効図は状態の要約であり、編集面を置換する指示ではない。定義変更後も入力とfocusを保ち、古い結果を前回の試行と明示して確認／採用を失効させる。遅い旧試行は現在の結果へ反映しない。欠測の確認linkは発話IDを含む名前で固定入力を開き、現在入力を直したら再試行する。採用応答不明では成功・失敗を推測せず正式状態を確認する。PNGでこれらが動いたとは扱わない。

**理解の問い:** 「説明欄を書き換えると計算も変わりますか」「この列の単位は何ですか」「いつ研究者が採用しましたか」。試行件数だけ見て無自覚に全件へ進んでいないかを観察する。

**実装前提:** 現行trial responseにはinput_hashはあるが、発話ID付きの個票・欠測理由・定義revisionがない。W02のresponse拡張を先に行う。試行版rと同内容を採用する版r+1を追跡し、画面が古いvaluesと現在発話を推測で結ばない。個票に添える本文／時刻も同じtrial snapshot由来であることを確認し、入力変更後の現在値で表示を埋めない。受付後の版ずれは[隔離probe](ui-design-evidence/2026-10-02/definition-lifecycle-probe.json)で再現済みのため、W02の実行境界対策が受入の前提。[全pipeline合成probe](ui-design-evidence/2026-10-02/definition-full-pipeline-probe.json)でも保存adapter入力の不整合を確認したが、実ディスク保存／GUIでの再現済みとはしない。

**保存互換のgate:** W02の固定payload提案は実装前。旧manual／旧automatic／新形式、受付前後の並行編集、restart/retryを分ける。旧binaryへのdowngradeはDB初期化前のcompat guardと復元dry runが必要で、pending=0だけで許可しない。

**証拠:** 画面要約、trial個票、definition revision、API順序、固定run。これは研究上の妥当性を証明するテストではなく、宣言した計算と実行の一致のテスト。

## S03 長時間処理の失敗と保存先の競合から戻る

**研究者の仕事:** 会話Aの分析を開始し、待つ間に会話Bの編集を行う。失敗した場所だけ回復して保存済み結果を見る。

**入力:** AとB、Aのpipeline、Bの未保存編集。accepted→running→waiting、failed、中止送信中→cancelling→cancelled、completedの各分岐。計算・本体保存済み＋VisualizationVault conflict、および3生成先成功＋ResearchVault conflictの条件。対応: DG-03/11と追加契約確認、W03、UX:K11/UX:K12。

1. 開始前に対象A、基礎pipelineの処理、計画相談の有無、Vault保存先を確認する
2. 実行中にBを開いて1発話を編集し、Aのchipへ戻ろうとする。confirmLeaveで移動を中止してBのdraftを保つ分岐と、Bを保存してからAへ移る分岐を確認する。未保存確認を無視した複数対象draft保持を前提にしない
3. waiting理由を見る。条件を直す操作と再試行の違いを確認する
4. failed時に見出し・現在工程・保存済み成果・次操作を読む。通常workspaceへ戻る
5. 別ケースで中止要求直後と中止確定後を観察する。完了との競合も試す
6. Vaultだけ失敗したケースで本体結果を開く。Research conflictでも既存保存履歴の「保存済み結果から再試行」は全保存工程を再訪できるため、その範囲を確認する。OFFだった未実行runのpendingから同経路を使う場合は、初回の「Vaultにも保存」と範囲を確認し、再試行と混同しない。pipeline completedに新たな再試行actionを置く場合や、Researchのみ等の部分再試行はW03の別契約後に試す
7. 画面更新・Back/Forward・通信取得失敗を試し、最後に確認した状態と新しい状態の区別を見る

**受入:** A完了でBの作業対象・draftを自動置換しない。明示的な移動は既存の未保存確認を通り、移動中止時のdraftと保存後の本文をそれぞれ保持する。failedを実行中、中止送信中／cancellingを中止済みとしない。failedのreviewが設定を開くなら再試行と呼ばない。通信断をbackend failedと決めつけない。retryは表示範囲と実writerが一致し、計算／外部AIを再実行しない。閉じても続く範囲の説明が実際のserverライフサイクルと一致する。

**保存scopeのgate:** 空／全3先／inputのみを別fixtureにする。現行の[合成probe](ui-design-evidence/2026-10-02/microcopy-contract-probes.json)では空のVault callbackは0、非空の両ケースはResearch込み4経路attemptで、Research conflictでもcompletedだった。改修受入では、部分集合を明示4xxでwriter前に拒否する暫定案、又は実対象だけを呼ぶ完全案に従い、要求→有効保存先→writer trace→outcome→台帳→画面を照合する。対象外writerは0回。OFFはこのpipeline限定で、Research pendingを今回の保存失敗と表示しない。旧completedやpublishedを全4先／全ノート存在へ読み替えず、削除されたノートのmissing保護と競合・不明を残す。部分再試行と再起動後のscopeも同じ境界で確認する。

**理解の問い:** 「計算は終わっていますか」「今回、どこへの保存を試みましたか」「どの保存結果が未完了・不明ですか」「この再試行で何がもう一度走りますか」。『完了』一語だけで全保存先や研究者確認まで済んだと受け取られないかを観察する。

**証拠:** 各stateの見出し・操作・live通知、API spy、B draft、run／publicationレコード。現行でもworkspaceへ戻れるため『失敗時に全結果を失う』を前提にしない。

## S04 根拠を確認して編集し同じ結果へ戻る

**研究者の仕事:** 「全員が賛成した」というAI見解を確かめ、反対する発話を原音で確認する。必要な文字起こしを直し、元の見解へ戻る。

**入力:** 会話A revision1の固定runR1、賛成／反対／伝聞／質問の合成発話、選択filterと引用。revision2に本文または時刻・話者の変更。対応: DG-06/12、W04、UX:K01/UX:K03/UX:K05/UX:K08/UX:K13。

1. 結果で対象・run・入力版・対象集合を確認する。根拠と反例候補を開く
2. 該当発話の前後を読み、音声を聞く。生成説明と入力の証拠を区別する
3. 発話編集へ移り、合成音声に合う修正をして保存する。保存失敗の分岐ではdraftを保持する
4. 元の見解へ戻る。filter、結果ページ、引用、scroll、focus起点を確認する
5. revision1の結果がrevision2に対して古いことを確認し、旧結果を保持したまま必要に応じた再分析の入口を確認する

**受入:** 古い引用から現在音声へ黙って飛ばない。生成時本文・時刻・話者と現在内容が違えば不一致を伝える。R1へ戻ったときに現在版の来歴へ書き換わらず、stale／unknownが残る。固定成果物の閲覧・戻るだけで再分析を始めない。既存pipeline status GETには再起動後の自動回復があるため、固定結果ビューからその経路を使わない。研究者メモや確定解釈をAI再生成で上書きしない。

**理解の問い:** 「いま読んでいる結果はどの入力版ですか」「全員という見解を支持しない根拠はありますか」。採用率や信頼自己評価だけで良否を決めない。

**固定viewerのgate:** 最初はai_insights／milestone_analysisだけをW04のmanifest・input・resultのfield対応で扱う。100件外のrun lookup、未知schema、artifact409／404、quote欠落、hashは一致するがbindingとdefinitionsの版が異なる旧package、同tab Back/Forward、reload contextあり／なしを試す。reload contextが無くても同じrun概要へ戻し、現在データへfallbackしない。定義版が不整合な旧packageは正常確認済みと表示せず、自動比較を止め、元artifactを残す。全sessionを越える位置復元や他kind対応は未提供とする。

**比較案:** Aは既存details＋往復、Bはdesktop根拠pane／mobile全幅根拠。両案に照合する主張、AI下書き、取得できた確認状態、限界、選択発話IDを残す。確認記録なし／読取不能を区別し、人が未読と推定しない。B mobileの研究者メモは別状態なので、メモを読み直す課題も含める。現在発話を確実に解決できない条件ではその入口を無効にする。等価fixtureで正しい根拠への到達、誤り発見、復帰の失敗、不要な遷移を比較し、画像の短さやpaneの広さを改善点数にしない。

## S05 古いrunを探し比較して同じ対象を出力する

**研究者の仕事:** 前回の分析と今回の分析を探し、条件の違いを確認して比較・出力する。

**入力:** 通常runと比較runの各0/1/99/100/101/105/201件、同時刻ID、legacy来歴不明、旧入力と新入力、異なるfilter／分母。履歴閲覧中に新規runが加わる条件。対応: DG-04/06、W04/06、UX:K09/UX:K13。

1. 履歴を開き、表示件数と保存総数の違いを読む
2. 101件目以降の指定runを通常のページ操作で探し、開いて戻る
3. 2つの結果の入力版・定義版・対象集合・欠測・比較可能性を確認する
4. 不適合な比較は理由を読み、無理に共通の母集団として扱わない
5. 対応する形式を選び、本文・時刻・話者・コード・ノート・来歴のうち含む情報と省かれる情報を読む。出力を取得し、画面のrun／revision／hash／対象数と照合する

**受入:** 変更なしのfixtureではページ間の重複・取りこぼしがなく、同時刻でも順序が安定。live keysetの並行追加ではcursorより新しいkeyのrunを現在の走査へ割り込ませず、更新後に先頭から発見できる。同時刻の小さいIDや過去日時の追加は古い範囲へ入り得るため、全新規runの除外や初回時点のsnapshot固定は保証しない。上限説明だけの段階では101件目への通常到達は未対応と明記する。元保存物と既知IDリンクは保持。legacy不明値を現在値で補わない。表・CSV・JSON／ZIPで分母と欠測が一致。

**能力の確認:** 通常分析XLSXとpipeline固定packageのXLSX未提供を区別し、後者をダウンロード可能と案内しない。比較を開く操作と新しい比較runを作る操作を区別する。

**理解の問い:** 「一覧の100件は保存の全件ですか」「このCSVはどの結果を出したものですか」「分母の違う結果をそのまま比較できますか」。履歴上限をデータ削除と誤解していないかを見る。

## S06 キーボードと読み上げで相互作用を記録する

**研究者の仕事:** ある発話が前の発話への反論だと記録し、根拠メモを付け、不要なら取り消す。

**入力:** 選択発話e2と候補e1/e3、未設定select、長い関係名、入力済みmemo。通常／focus／error／disabled、固定header/footer、200%拡大。対応: DG-09/10/12、W05、UX:S22〜S30。

1. pointerを使わず対象の発話から相互作用入力へ移る
2. 「対象発話」と「関係」を目的名で見分け、値を選ぶ。根拠memoを入力する
3. 追加し、結果と通知を確認する。取消・削除・再追加を行う
4. 実ATで名前・role・value・発話文脈・保存通知を読む
5. focus中の実色・背景・遮蔽・clipを採取し、同じ箇所を狭幅でも試す

**受入:** select2つに一意で目的が分かるprogrammatic name。memoは入力後もvisible labelが残る。選択値をcontrolの目的名の代わりにしない。focusが見え、固定バーで完全に隠れない。errorは欄へ結び付き、追加後に入力文脈と通知を失わない。

**contrast:** drop補助文、registry未保存文、淡い共通ring、濃緑border、青outline、濃色sidebarを個別に測る。指定色の計算をcomputed style検証の代わりにせず、良い反例も残す。

**証拠:** 可視操作V3、accessibility tree、AT名・版と発話記録V4。ATがない場合はV4 not-run。placeholder fallbackがあるmemoを絶対無名だったと断定しない。

## S07 日本語の長い発話を狭い画面で確認し保存する

**研究者の仕事:** 長い発話の話者名と誤変換を直し、保存後に統計のページへ進む。別ケースで話者を追加する。

**入力:** 長い氏名・ファイル名、複数段落の日本語、英数字混在、同名話者、多数の分析tab、0件／1件／多数件の一覧、検索0件と全件欠測。対応: DG-07/08/12/14、W08。

1. 390pxと320px相当で、選択発話を開き、原音と本文を照合する。再生中の発話、編集中の選択、保存した引用を区別し、追従を止めても選択を失わないことを確認する
2. IMEで変換し、確定して保存する。変換中に単キーshortcutが走らないことを確認する
3. 保存barとkeyboard表示の間で必要なcontrolを操作し、成功／競合を確認する
4. 右端の分析ページを選び、現在のページ名とfocusがnav内で見えることを確かめる
5. 根拠へ移って戻り、画面幅変更・Back/Forward・reduced-motionでも位置を確認する
6. 話者追加後に次の入力が見えるか確認し、空状態から次の作業へ進む

**受入:** document幅のoverflowがないだけで合格にしない。navの選択labelとmain nav現在地、入力focus、保存feedbackが読める。採用disabledとその理由も色以外の表示・役割・状態で分かる。固定heightによる文字切れなし。text-spacing上書きや200%拡大で機能が失われない。必要な表は領域内scrollと代替表等を保ち、周辺操作はreflowする。v2のMC-07はこの実UI確認へ引き継ぐ。

**比較:** 現行と候補の同じ内容・状態・幅を比べる。主作業到達までのscroll／操作、読み違い、保存誤認を記録する。フォント拡大で全情報を縦に長くする案と、列優先・詳細開閉を使う案のtradeoffを確認する。安全説明を隠して短くする案は採用しない。

## 回帰で必ず残す既存の保護

上記シナリオの変更箇所に応じて原UI-01〜10とA01〜14/V01を再実行する。全シナリオに全試験を機械的に付けず、境界を跨ぐ保護は漏らさない。

- 未保存移動、連打、古いresponse、別対象への移動、中止と完了の競合
- 削除Undo、保存409、未保存draftの書出し、CSV previewの取消
- 計算済みゼロ／欠測／未計算、対象集合・分母、本文版・model版の来歴
- 生成ノートの研究者編集保存、競合、Vaultのみretry、実Vaultを試験に使わない
- 閲覧と実行を分け、未承認の外部送信・モデル取得を試験の裏で始めない

## 利用者比較を行う場合の判定

初回利用者と反復編集者、質的研究経験者、必要なAT利用者の課題を区別する。人数を万能な固定数から決めず、重大な誤認を検出する形成的試験として計画する。比較順と等価fixtureを入れ替え、学習効果を抑える。

主指標は正しい対象・版での完遂、編集保持、誤測定と根拠不一致の発見、回復成功。時間・遷移数・負担は補助。採用前の停止条件は、重大な誤測定、保存損失、外部送信誤認、引用取り違えが候補UIで生じること。発見したら該当案を修正し再確認する。少人数の比率や平均時間を一般的な生産性向上率へ拡大しない。

第4稿時点の結果: 全シナリオは仕様として作成。V3/V4/V5は未実施。clean v2の静止レビューはアプリのV1〜V5成功数へ加えない。DG-01/02/03等の現行不整合は別のソース／隔離probeによる証拠を持ち、[独立反証](ui-design-evidence/2026-10-02/adversarial-checks.md)へ戻れる。追加の送信／保存／handler合成probeも、本シナリオ全体や改修の成功を意味しない。短い表示文は[文言仕様](../40-Design/ui-microcopy-state-catalog.md)の成立条件と一緒に使う。
