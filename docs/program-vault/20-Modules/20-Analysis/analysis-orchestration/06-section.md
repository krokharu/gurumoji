# 結果IDによる再分析・分析処理の完了・必須手法

対象は `krokharu/transcription-finish-20261102`、開始HEADは `d8707f2e02e4e1a74a5d3cb4d6c728e3f5691486`。既存変更を保持し、実装を3担当で並列化する。実装担当は GPT-6.1 Terra、統合と検証は親担当が行う。実行時の分析モデルはGUIの共通設定・担当別設定を利用し、資格情報やクラウド送信の設定は変更しない。

## 要件1：結果IDを指定した再分析

- 実行と個別結果の既存IDをGUIで確認・コピーできる。
- 同じ会話の保存済み実行IDまたは個別結果IDを指定し、人の追加プロンプトを入力できる。
- 参照内容を確認してから新しい実行を開始する。参照GETはAIを呼ばない。
- 元の結果・元の問い・入力版・hash・追加指示を区別して新規実行に固定する。元の履歴と会話本文は更新しない。
- AIへ参照結果と追加指示を渡し、元のAI解釈を観察済みの事実や人の確定解釈として扱わない。
- 不明ID・別会話ID・隔離結果・不正な指示・大きすぎる参照は開始前に拒否する。受信順が逆転したGUI応答や会話変更で別対象を採用しない。

受け入れ条件：一時DBで有効なIDと追加指示が新runの設定・AI文脈・保存履歴へ戻れること。元履歴が不変で、別会話・不明IDを拒否すること。GUIでID入力、参照確認、追加指示、開始、履歴からの選択が操作できること。

## 要件2：分析処理を最後まで実行する

- 予定済みタスク、未評価結果、必須手法を残したまま分析処理完了としない。
- 停止提案に実行可能な追加分析が併記された場合は、その処理を先に行う。
- 終了レビュー後の結果改訂が、同じ停止提案への再レビューを無限に発生させない。
- 分析処理の完了と人の確認待ちを分離する。人の確認事項が残る結果もAI下書きとして固定保存し、人の確認が済んだとは表示しない。
- 取消、入力更新、不明な実行結果、実行障害、明示した上限では正直に停止する。上限拡大や未実行の成功扱いで完了を作らない。
- 過去の実行の状態解釈を変更しない。新しい終了手順は新規実行に版を付けて適用する。

受け入れ条件：終了レビューが「問題なし」で改訂版が返る事例が有限に終了すること。人の確認待ちの状態・元応答・未解決点を保ったまま固定保存できること。未処理タスク・上限停止・失敗を正常完了や自動公開へ変換しないこと。

## 要件3：全自動処理の必須分析手法

- GUIで、現在の自律分析経路が実行できる手法を複数選べる。実行対象は発話量・参加バランス、会話の時間構造、ラベル頻度、話者×コードのクロス集計の4種。
- 分析テンプレートの確認項目と、実行を保証する手法の指定を区別する。未対応の手法を実施済みとしない。
- 選択したIDを新規実行に固定し、AIが提案しなくてもHandlerが登録する。未知ID・不正な配列を拒否する。
- 全対象の入力版・ラベル版に対する実行、専門担当による採否、Coreによる報告の取り込みを追跡する。採用されない結果も不採用理由とともに保持する。
- 必須手法が未実行・失敗・古い版・未評価のままでは分析処理完了としない。
- 統計専用MetricEncoder／MetricDecoderの経路と検証を維持する。

受け入れ条件：GUIの選択IDが要求と保存設定に一致し、Coreが即時停止を提案しても選択した全手法が実行されること。GUIで実行と評価の状況を確認でき、実行記録を再読込して照合できること。

## 共通の検証境界

試験コード・合成データ・検証用ツール・設計根拠は開発資料ブランチに置く。一時DB・一時Vaultと独立したポートを用い、実利用者のruntime、資格情報、研究者ノートへ書き込まない。API／状態機械の試験、DOM試験、実ブラウザー操作、実モデル試験を分けて記録する。

## 追補要件：クロス集計を指定し実行を確認する

- `cross_tabulation` をGUIの必須手法で選択する。行は固定入力の話者ID、列は `codes`。AIによる追加依頼は既存の許可ラベル列にも対応する。
- 発話単位で重複ラベルを除き、話者×ラベルの度数、行内割合、列内割合、全体割合と対応する根拠IDを算出する。複数ラベルの合計は発話数や100%を超え得ることを明記する。
- 行内割合の分母はラベル欠測を含む当該話者の対象発話数、列内割合は話者既知の当該ラベル付き発話数、全体割合は除外後の対象全発話数とする。話者欠測とラベル欠測の和集合を欠測数として示し、内訳の重複を区別する。
- 話者またはラベルが全件欠測なら `availability=unavailable` とし、必須分析の完了条件を満たさない。0件の観測や実施済みの内容別集計として表示しない。既存の初回3手法と過去のrunの契約は維持する。
- 固定した入力・ラベル版・コードブック版を保存し、ラベル更新で再計算する。既存のSQLカラム、利用者のラベル、保存先の契約を変更しない。
- 統計専用MetricEncoder/MetricDecoderでセル件数と話者別の分母・欠測を配送・再検証する。モデルに割合計算を委任しない。GUIの結果表示は原結果から件数と行内割合の表を構築する。
- GUIの必須指定では `codes` 列を生成schemaとHandlerの両方で固定する。別列や部分範囲の結果を必須の全件表へ代用しない。同じ列・対象・入力版・ラベル版・コードブック版の全件表は再発注せず保存結果を再利用する。

受け入れ条件：手計算した合成表と全セル、分母、欠測、複数回答の結果が一致すること。GUIの選択が新規runに固定され、実行・専門側の評価・Core統合を確認できること。合成データの実モデル呼出しで専用codecを通り、別接続から保存結果を読み直して一致すること。実利用者データを試験対象にしない。

## 実装上の判断

- ID参照は同一会話の保存済み有効結果を読み取り専用で確認し、開始時に同一入力hashも照合する。旧入力への参照を黙って現在の根拠IDへ変換しない。履歴の省略やhash不一致は受理しない。
- 元の結果は新runの `config.reanalysis` に固定し、元の問い・追加プロンプト・原結果hashと各IDを保存する。AI配送時の除外フィルタによって内容が変わった場合は、その事実と配送内容hashを残す。元の履歴は変更しない。
- 追加指示は `task_instruction.human_prompt`、元の解釈は `resource_data` として扱う。独立検証と対象を固定した先行所見レビューには、過去の結論を渡さず追加指示と出所IDだけを渡す。追加指示自体を裏付け済みの事実と扱わない。
- 履歴projectionの空の発話IDはnullのまま往復し、存在する参照IDだけを短縮変換する。未知の実IDの拒否と結果検証を維持する。
- 新終了手順は採否を記録できる `core_progress_version=1` の新規runに適用する。GUIと必須手法はこの経路を利用する。既存runと旧採否プロトコルの状態は解釈し直さない。
- 終了前レビュー後も統合結果が改訂される場合、改訂版を確認済みと偽らず、処理完了・人の確認待ちとして固定保存する。モデルが返した元の停止理由・原応答を保持し、要確認の下書きは自動公開しない。
- 予算対応で分割された未送信の親タスクは、理由・親子の所属・版・全対象の多重集合・全葉の有効結果と採否を検証した場合だけ処理済みとみなす。一般のblocked、欠落、重複、失敗、隔離は成功扱いしない。
- 必須手法の実行と専門担当の採否、Coreによる専門報告の取り込みは別々に表示する。Coreが個々の統計を直接採否したとは表示しない。
- 保存結果の確認要求は会話・ダイアログの世代と要求連番で対応付け、同じIDへの再要求を含む応答逆転で古い結果を採用しない。
- GUIで確認した結果IDとraw hashも開始要求へ渡し、確認から開始までに参照するrunの統合結果が変化した場合は再確認を要求する。
- 実モデルが終了案と追加依頼を毎回併記して処理が続く問題に対し、adapter49・`core_control_version=1` では通常Coreの生成schemaを `next_step` の排他分岐とした。追加分析は `kind=analyze / intents>=1 / stop=null`、終了は `kind=finish / intents=[] / stop=終了理由`。原のnext_stepを保存したまま既存Handlerのstop/intentsへ可逆に投影し、不正な応答は隔離する。初回ルーティングと旧版の形式は維持する。
