# 分析オーケストレーター共通契約

個別オーケストレーターは「分析を実行する」だけでなく、再現可能な対象集合を作り、結果と根拠を保存し、解釈不能な状態を成功扱いしない責務を持つ。

## 最小入力契約

| 項目 | 必須内容 |
| --- | --- |
| 対象 | `item_id`、`source_revision`、`analysis_revision`、発話ID集合 |
| 設定 | 手法固有パラメーター、除外規則、分析単位、比較軸 |
| 実行環境 | `method_id`、アルゴリズム版、解析器／ライブラリ版、モデル名・revision・seed |
| 根拠 | 結果行から辿れる発話ID、または元表の行キー |
| 保存先 | 固定 `result.json`と必要な型付き全件表、交換用CSV、Obsidian要約ノート。CSVの空欄・数式対策から元値を推測せず、画面プレビューだけを根拠にしない |

## 結果の状態

`not_run`、`completed`、`empty`、`unavailable`、`fallback`、`partial`、`stale` を区別する。`fallback` はGiNZA不在時の簡易形態素解析、`stale` は入力・設定・モデルが変わり結果が現行でない状態であり、どちらも通常の完了結果と混ぜない。

これは分析結果の表現であり、ジョブ・段階の実行、保存の完了、Vault公開、妥当性の確認を統合するenumではない。追加分析の試行状態・中断・再開は[[40-Design/core-handler-routing-reorganization-plan]]の「段階実行の状態と再開」に従う。

## 必須のゲート

1. **入力妥当性**: 空本文、無効時刻、`UNKNOWN` 話者、除外発話、欠測を数え、手法の前提を満たすか判断する。
2. **設計妥当性**: 分析単位（現行の計量分析は原則「発話」）と、研究質問・比較軸が整合しているか確認する。
3. **計算妥当性**: 乱数seed、候補パラメーター、エンジン・モデル版を結果に残す。統計では実行可能性、期待度数、群数、N、仮定注記を確認する。
4. **根拠妥当性**: 元発話を扱う要約・AI出力・テーマ名は、固定した本文版と発話IDで根拠を解決する。結果文を入力にする場合は親run・artifact・hash・行／主張IDで解決し、元発話の根拠と区別する。固定入力内の参照不成立は失敗、現在版との差は`stale`として別に示す。現在の本文へ黙って差し替えない。
5. **解釈ゲート**: 自動値から合意、因果、重要性、本人の感情、遮り等を断定しない。人の検証・反例・文脈確認を要求する。

## オーケストレーターの出力

`plan`（選択理由・前提）、`run`（入力fingerprint・環境・状態）、`artifacts`（JSON／CSV／ノート）、`evidence`（発話ID・行キー）、`warnings`（前提違反・限界）、`next_actions`（人が判断する問い）を分けて返す。生成AI系はモデル応答を研究者のコードや手動メモへ自動反映しない。

## 手法の専門家（2026-09-16）

設計妥当性と解釈のゲートは、選んだ手法の専門家定義（[[10-Experts/00-Index]]）の適用条件・手順・禁止事項で具体化する。現行実装は `src/gurumoji/method_experts.py`。現状は専門家どうしの合議や独立したレビューを行わず、前提が食い違う場合は統合せずに並べて示す。

現行の`ai_context`は、評価時の定義版・knowledge hashと指示を組み立てる時点の値を照合し、変更があればAI呼び出し前に再確認を求める。実際のbrief・許可段階・禁止事項・根拠IDを版付きpacketとして固定保存する拡張はAI-2で導入する。hashだけでは当時の指示本文を復元できないため、旧runの未記録情報を現行定義から補わない。

## LLM分析専用オーケストレーターと相談の拡張（2026-09-20、未実装）

利用者の追加要求に基づき、[[40-Design/core-handler-routing-reorganization-plan]]の図6とADR-117で、LLM分析専用オーケストレーターが手法・型・後続分析の担当と相談する設計を追加した。上記の現行機能と区別し、次の契約を満たす段階で導入する。

- 先に固定するのは分析手順と結果の項目・意味・型・接続条件であり、結論や値ではない。
- 疑似人格は役割別のLLM呼び出し。同じローカルLLMを使える。Jevは定義済み選択肢の判定を担当し、相談や自由形式の型生成には使わない。
- 相談の相互指摘・修正案・異論・採用理由を記録する。回数・時間・使用量に上限を設け、合意を独立した専門家レビューや科学的妥当性の証明にしない。
- 手法別契約には入出力schema、単位・尺度・欠測・キー・根拠、runner／adapterの能力と版を持たせる。表、主張集合、関係表、系列、ベクトルを必要に応じて扱い、クロス集計を必須にしない。
- 型の構造検証、試行、採用と、統計の妥当性ゲートは分ける。未実装の手法やadapterは、schemaを生成しても実行できない。
- 契約・相談・分析結果は別々に識別して固定し、既存AnalysisStoreとVault公開経路へ段階的に接続する。旧結果は維持し、PersonaVaultの自動読み書きは追加しない。
- 計画の`input_refs`／`scope_ref`を検証済みの`input_bindings`／`scope_id`・hashへ解決する。計画内の参照から導いた依存と`depends_on`が食い違う場合は拒否する。具体例と保存対応は再編計画を正本とする。
- 同じ要求の再送・保存再試行、既存結果の明示利用、新要求での再分析を区別する。同じ入力条件でも明示再分析は別runにし、旧runへのfingerprint再利用を暗黙に適用しない。
