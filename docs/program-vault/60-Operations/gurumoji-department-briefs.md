# Gurumoji 開発部門への依頼テンプレート

これは開発作業用の再利用可能な依頼形式であり、ファイルを置くだけで担当が常駐・自動実行するものではない。実際の担当起動、権限、期限、成果物の確認は調整担当が行う。

## 共通の依頼ヘッダー

対象commitと作業場所、利用者が行う仕事、今回変える範囲、守る契約、合成fixture、合否条件、依存する担当、期限を渡す。現在コードを正本とし、過去のテスト結果を新しい版の合格根拠にしない。共有作業treeでは担当ファイルを分け、commitの順番を明示する。

## UI/UX部門

利用者が何を確認して何を変更するかを先に定める。既存のID・値・送信経路・保存状態を一覧化し、狭幅、キーボード、disabled、loading、失敗、取消、画面移動、遅延応答を含む受入条件を作る。実装は変更せず、再現手順と観測結果を返す。詳細は既存のUI criticと設計契約を参照する。静的検査、合成DOM、実browser、支援技術、利用者評価を区別する。

## 分析部門

定義版、入力版、対象集合、分母、個票、欠測、集計、出力、来歴を同じfixtureで突き合わせる。真のゼロと不明を分け、宣言した測定単位や規則と計算の意味が一致するかを確認する。通常値だけでなく空入力、境界値、不正型、競合、旧形式を含む。実データを使わず、検証済み失敗をプログラミング担当へ渡し、修正版で期待値を反転して独立確認する。

## プログラミング部門

対象の既存責務を確認し、再現テストを先に固定する。互換性を狭く保つ小さな修正に分け、対象ファイルを明示してcommitする。保存形式は追加的な変更を優先し、旧成果を削除・書換えしない。対象テストと隣接回帰の結果、変更commit、未実行範囲を返す。レビューで見つかった不具合を閉じてから次の見た目の改善へ進む。

## 全体調整部門

影響、再現性、利用者の優先で作業を並べ、同じ不具合の重複計数を避ける。実装担当と独立レビュー担当を分け、未解決条件と次の課題を作業ボードへ戻す。テスト結果には対象commitを付け、成功・失敗・blocked・未実施を分離する。意味のある節目で復旧可能なsource bundleを作り、別cloneで復元確認する。公開・配置・実データ移行は別の承認範囲として扱う。

## 完了の判定

変更の意図、ソース差分、回帰結果、独立レビュー、残る制約を突き合わせる。環境制約で操作できなかったものを合格に数えない。新しい永続形式がある場合は旧workerの停止・drainとrollbackの制約を引継ぎに残す。安全な改善余地が残る限り次の優先へ進み、根拠のない時間消化はしない。
