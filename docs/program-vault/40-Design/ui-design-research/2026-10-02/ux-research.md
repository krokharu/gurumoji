# Gurumoji UI UX 設計の根拠と評価手順

調査日: 2026-10-02 UTC  
対象: 日本語の複数話者文字起こし、グループインタビューの質的分析、長時間のローカル／クラウド処理を支えるデスクトップ中心の Web UI  
用途: DESIGN.md の判断根拠、実装前レビュー、回帰検証、後続エージェントが再利用する設計知識  
状態: 文献・標準の初回調査。利用者実験、現行 UI の適合監査、実装変更は未実施

## 結論

Gurumoji の設計で最初に守るべきものは、研究者が「対象を選ぶ → 原音と発話を確認する → 解釈する → 根拠付きで保存する」の往復を失わないこと、その途中で自分の編集・対象集合・処理状態を見失わないことである。装飾や見かけ上の簡潔さだけを成功指標にしない。

重要な設計判断は次の六点にまとめられる。

1. 原音・原文・AI の提案・研究者の確定内容を区別し、根拠と入力版へ戻れるようにする
2. 説明文の長さより検証のしやすさを優先する。発話 ID、該当箇所再生、前後文脈、修正差分を近くに置く
3. 未校正のモデル信頼度を正確さの百分率として表示しない。機械の疑い、人の確認状態、処理の成否は別軸にする
4. 頻出語、発話量、クラスタ、感情推定を研究上の重要性・合意・人物評価に直結させない。母集団、分母、欠測、候補であることを見せる
5. 一度の作業に必要な操作を前面に出し、詳細設定は要約を残して開けるようにする。熟練者の反復操作はショートカットや一括操作で支える
6. 処理中、部分完了、中止要求、停止済み、失敗、未保存を区別する。キーボード操作、可視フォーカス、十分なコントラスト、拡大表示を後付けにしない

上記は、文献で直接実験された効果、標準の規範、Gurumoji への設計推論を組み合わせた提案である。Gurumoji の日本語研究者ワークフローで改善効果が実証済みという意味ではない。

## 調査方法と根拠の読み方

学術論文の著者公開版・大学リポジトリ・学会／出版社、W3C の現行仕様と解説、原著者による HCI ヒューリスティック、公式デザインシステムを優先した。2026-10-02 に Web で確認した。検索エンジンの「公開○か月前」は発行日と一致しないため、論文の書誌と文書本文の日付を採用した。体系的レビューとしての網羅性や選定再現性を主張するものではない。

根拠の種類を以下で区別する。強さの単純な順位ではなく、何を支持できるかの違いである。

- **E 実験**: 比較条件を伴う人の行動実験。課題、参加者、言語、装置、介入の範囲で効果を解釈する
- **B 性能評価**: モデルやシステムのベンチマーク。人の UI 利用実験や因果効果と同一視しない
- **O 観察**: インタビュー、調査、利用観察。利用者の困難や仕組みの仮説を支えるが、因果効果とは区別する
- **R 研究統合**: 複数研究のレビュー／メタ分析。対象期間と選定条件、異質性に制約がある
- **N 規範**: 標準仕様の要求事項。ユーザー実験による効果量とは別物
- **G 指針**: 専門家評価、方法論、公式実装パターン、経験則。状況判断と利用者検証が必要
- **D 設計推論**: 上記を Gurumoji に適用した提案。実装済み・有効性確認済みではない

本文の S 番号は同じフォルダーの `ux-source-ledger.json` と末尾の出典一覧に対応する。出典台帳には閲覧範囲、発行日、対象、限界を記録した。原文の大量転載はしていない。

現行アプリの用途理解に限って README と AGENTS.md を参照した。参照時 HEAD は `ddc23abe0d747a1e6cfd6d3bc262ce226f4756b0`。README に記載された機能は設計の適用先を把握するための情報であり、今回その実動作を確認したわけではない。

## 再利用可能な設計知識

### K01 研究の往復を単位に画面を設計する

**適用場面**: データ一覧、分析結果、発話編集、引用保存の画面遷移

**根拠**: Focus group の方法論は参加者間の相互作用を分析対象として扱う [S16, G]。質的研究の報告指針では、分析過程や根拠と解釈の関係を明らかにすることが重要になる [S17, G]。情報可視化の overview、filter、detail、history、extract は探索作業を整理する概念モデルであり、全利用者に同じ順番を強いる実験的法則ではない [S08, G]。

**Gurumoji への適用 [D]**:
- 集計・見解・検索結果から、対象の発話とその前後、元の音声へ遷移できるようにする
- 戻ったときに対象データ、フィルター、並び順、選択発話、スクロール位置を復元する
- 「発話だけ」の検索でも、誰への返答か、直前の質問、隣接ターンを展開できるようにする
- 分析結果から原音へ進む動線で新しい分析を勝手に開始しない

**避けること**: 派手な分析トップに毎回戻す、選択状態を消す、各発話を文脈から切り離した独立した事実として扱う

**確認**: 見解の根拠を開いて原音を聞き、編集し、元の見解に戻る一連のタスクを実行する。対象集合と位置の復元、引用先の整合性を確認する

### K02 初心者と熟練者の違いを操作層で吸収する

**適用場面**: 新規処理、認識モデル・VAD・出力・AI 仕上げの設定、分析手法選択

**根拠**: Progressive disclosure は重要／頻繁な操作を前面に置き、二次的な機能を必要時に開示する指針 [S13, G]。認知負荷理論の初期研究は学習・問題解決に関するものであり、画面上の項目数の上限や特定のメニュー階層を直接証明しない [S11, E/理論]。

**Gurumoji への適用 [D]**:
- 初回に必要な「ファイル、言語／録音の種類、実行先、出力、外部送信の有無」を短い要約として提示する
- 詳細を閉じても現在値、推奨から変更した値、実行結果に重大な影響を与える値を確認できるようにする
- 研究質問を起点に分析を選べる入口と、手法名から直接進める入口を共存させる
- プリセットは説明付きの出発点とする。変更すると何が変わるかを示し、隠れた連動変更を作らない
- 熟練者の操作を毎回のチュートリアルで遮らない。ショートカットは可視の操作と同じ機能を呼ぶ

**避けること**: 「初心者には重要な警告や送信先も隠す」、全員に単一の線形ウィザードを強制する、「7±2」からタブ数を機械的に決める

**確認**: 初回利用者の設定誤認と、熟練者の繰り返し編集の時間・操作数を別々に観察する。折り畳み数の少なさだけを最適化しない

### K03 AI の提案と研究者の判断の境界を保つ

**適用場面**: 校正、話者特定、アウトライン、コード候補、テーマ候補、見解

**根拠**: Human–AI Interaction Guidelines はできること・性能限界の提示、修正・却下・ユーザー制御を含む。49 名の実務家が 20 製品に適用して評価した指針であり、各 UI の因果的改善効果を証明したものではない [S01, G]。CollabCoder は研究支援の可能性と、初心者だけでなく熟練者も AI の提案に引かれるリスクを報告する [S18, E/O]。

**Gurumoji への適用 [D]**:
- 「AI 下書き」「研究者が編集」「確認済み」は別の状態として持つ
- 元の文字起こしは比較可能に保ち、AI 校正を無表示で上書きしない
- 採用、個別修正、却下、保留、元に戻すを可能にする
- 人が書いたメモと再生成されたメモを混ぜず、再実行時の対象と上書き範囲を示す
- 引用・判断を保存した後で入力が変わったら、再確認が必要なことを見せる

**避けること**: 生成完了を研究上の確定と呼ぶ、緑の完了マークだけで内容の正しさも保証したように見せる

**確認**: 研究者の編集後に再実行し、手動の本文・コード・メモが保護され、旧版と新しい生成物の関係が追えることを検証する

### K04 信頼度の表示は校正と検証を前提にする

**適用場面**: 誤変換候補、話者分離、感情推定、意味クラスタ、LLM の確信度表示

**根拠**: Kuhn らの ASR 研究では 9 モデルを評価し、ドイツ語話者 36 名による修正比較を実施した。低信頼度語の強調による WER 改善の有意差は検出されず、誤検出と見逃しが多かった。ASR が脱落させた語には信頼度スコアが無いため、信頼度による誤り分類の性能評価からは除外された。一方、別に行われた利用者修正実験の WER 評価は脱落誤りも含む。利用実験は 3 分の音声を再生し直せない条件だった [S03, E/B]。従って「表示しても絶対に無益」とも「日本語の任意再生環境で同じ結果」とも断言しない。

**Gurumoji への適用 [D]**:
- 未校正の score を「正確さ 94%」などの成功確率へ読み替えない
- 「機械が確認候補にした」「人が確認した」「音声が欠けている」を分ける
- 強調されない箇所にも誤りがあり得ることを、候補フィルターの近くで説明する
- 必要なら強調をオン／オフできるようにし、候補を修正した件数だけで成果を評価しない
- 話者・録音環境・重なり区間などの条件別に誤りの傾向を調べる。古い英語 ASR の格差研究を現行日本語モデルの格差率として転用しない [S32, B]

**確認**: 強調された誤り、未強調の誤り、正しい強調語、脱落した語を含むテストを行う。編集後の残存誤りと作業時間、不要な修正を測る

### K05 説明を増やすより確認コストを下げる

**適用場面**: AI 見解のカード、校正理由、テーマ候補、研究質問への回答

**根拠**: Bansal らの比較実験では、説明が AI の正誤にかかわらず受容を増やし、confidence-only 条件以上のチーム精度改善を示さなかった [S04, E]。一方 Vasconcelos らの 5 研究・731 名では、検証が相対的に容易になる説明は過信を減らせる条件があった。迷路・模擬 AI・理想的な説明での結果であり、解釈に唯一の正解がない質的研究へはそのまま移せない [S06, E]。

**Gurumoji への適用 [D]**:
- 見解の近くに、短い原文抜粋、発話 ID、話者、時刻、前後文脈を置く
- 「なぜそう思うか」という生成説明と、独立に確かめられる入力証拠を分離する
- 代表例だけでなく反例・異なる意見・未確認箇所を確認できるようにする
- 確認操作を何段ものモーダルや別タブへ追いやらない

**避けること**: 説得的な説明の長さ、ユーザーの信頼自己評価、採用率の高さだけを品質とする

**確認**: 意図的な誤った見解や根拠不一致を含むサンプルで、利用者が誤りに気づき、引用元を確かめられるかを見る

### K06 摩擦は影響の大きい判断へ集中させる

**適用場面**: 一括置換、話者結合、削除、AI 候補の一括採用、外部送信、書き出し

**根拠**: Cognitive forcing の実験（199 名）では過信を減らせる一方、使いにくさの主観評価や利用者間の効果差が生じた [S05, E]。確認ダイアログを増やせば安全になるという普遍則ではない。

**Gurumoji への適用 [D]**:
- 影響する発話数、変更対象、結果の保存先を実行前に提示する
- 可逆な日常編集は Undo／差分プレビューで軽く扱い、広範囲の変更はまとめて確認する
- 研究者の確定見解を一括変更する操作には、元の判断が残るかを明示する
- 意味のない待ち時間や毎回の確認を「安全対策」として追加しない

**確認**: 誤った一括操作を試みた利用者が影響範囲に気づくか、通常操作を妨げる確認が増えすぎていないかを両方調べる

### K07 話者編集では名前と発話の関係を壊さない

**適用場面**: 話者割当、名前変更、話者の統合／分割、連続発話の修正

**根拠**: 文字起こし編集の初期研究では、キーボードを組み合わせた修正やテキストからの音声再生が有用と報告された。ただし 2008 年のシステムで、今回は抄録を確認した範囲である [S02, E]。グループ研究では隣接発話と相互作用を扱う必要がある [S16, G]。

**Gurumoji への適用 [D]**:
- 内部の話者 ID と表示名を区別し、色は補助情報にする
- 名前変更と、発話を別話者へ割り当てる操作を混同させない
- 一括修正では「この発話」「選択した発話」「この会話の同じ話者」を明示する
- 話者色・名前・順序をビュー間で安定させる。フィルターを変えるたびに色を付け直さない
- 重なり・無音の候補を誰かの態度や発言意図に自動翻訳しない
- 再生、短い巻戻し、次／前の発話、話者変更を本文編集の近くに置く

**確認**: 同名の話者、未同定話者、名前変更、一括割当、Undo、引用済み発話を含むシナリオを実行し、原音・ID・引用リンクの整合性を確かめる

### K08 分析方式の違いを UI が勝手に決めない

**適用場面**: コードブック、複数コーダー、コード一致度、テーマ生成、分析結果の評価

**根拠**: Braun と Clarke は reflexive thematic analysis と coding reliability／codebook 型の前提・手続を混同しないよう求める [S15, G]。CollabCoder の比較実験は 16 名・8 組、短い書評データ、二人の協働を対象とし、複雑な複数コード・長いインタビューに制約がある [S18, E/O]。10 名の研究者による ChatGPT 利用研究も効率や初期探索への期待と文脈理解・一貫性への懸念を報告するが、小規模な探索研究である [S19, O]。

**Gurumoji への適用 [D]**:
- 分析目的、単位、コード定義、誰がどの判断をしたかを保存できるようにする
- 一致率や κ を「研究の品質スコア」として全手法共通の必須指標にしない
- AI の意味クラスタは「テーマ候補」、頻出語は「語の出現」と呼び、研究者が意味づける余地を残す
- 1 発話に複数コードを付ける、範囲を変更する、少数意見を保持することを邪魔しない
- 研究者のメモを、分類の正解ラベルだけに矮小化しない

**確認**: reflexive TA と codebook ベースの作業例を別々に歩き、無関係な品質指標や必須手順を押し付けていないか確認する

### K09 数値は質問と分母と一緒に見せる

**適用場面**: 発話量、話者バランス、時間推移、頻出語、クロス集計、共起、感情推定

**根拠**: Heer と Bostock の知覚実験は、同じ尺度上の位置比較などの符号化が比例判断の精度に影響することを示す。一方、グラフ全体の理解・研究上の妥当性まで保証しない [S09, E]。不確実性を表示しない実務上の理由を調べた Hullman の調査は、その省略を透明性の不要さとして正当化しない [S10, O]。

**Gurumoji への適用 [D]**:
- 話者間の量比較は、共通軸の棒・ドットと値を候補にする。円面積やワードクラウドだけに比較を任せない
- 対象データ、期間、除外、分析単位、分母、欠測を図の近くで読めるようにする
- 「発話時間が少ない」は観測量。「消極的」「不満」は別の解釈である
- 集計セル・棒から含まれる発話へ戻れるようにする
- フィルターで分母が変わったら、変化を見せる。図と書き出しで異なる母集団を無表示で使わない
- 空の対象、未計算、計算失敗、計算済みゼロ、欠測を別表示にする
- 感情推定を本人の内面の確定値として扱わない。ラベルの生成元・確認状態を追えるようにする

**確認**: 同じ発話で語が繰り返される例、発話数と人数の混同、フィルター後の分母変更、全件欠測を含む fixture で図・表・CSV を照合する

### K10 認知負荷を減らすとは情報をただ消すことではない

**適用場面**: 高密度の編集表、分析画面、複数ペイン、長い説明

**根拠**: 認知負荷の理論は専門知識による差や作業記憶の制約を扱うが、白い余白を増やすだけで業務が改善するという根拠にはならない [S11, E/理論]。操作・状態の可視化、認識による選択、整合したラベルはヒューリスティックである [S12, G]。

**Gurumoji への適用 [D]**:
- 一緒に判断する原文・音声位置・修正候補を近接させる
- 常に全分析カードを並べず、研究上の質問／作業段階に合わせてまとめる
- 既に選んだ対象やフィルターを隠して暗記させない
- 重要な操作は文字ラベルを付ける。アイコンは識別の補助にする
- 比較中の列幅、話者順、カード位置を不用意に動かさない
- 日本語本文の行間・行長・密度の数値は初期仮説として調整し、科学的な万能値と呼ばない

**確認**: 元の値を覚えて別画面へ行かなければ判断できない箇所、同一語が異なる意味で使われる箇所、視線移動の多い反復作業を探す

### K11 長時間処理を独立した作業状態として扱う

**適用場面**: 認識、話者分離、モデル取得、AI 校正、分析、書き出し

**根拠**: システム状態の可視化は HCI の指針 [S12, G]。Carbon の公式パターンは短いロードと進捗表示を区別する [S31, G]。これは特定の秒数で体験が必ず改善する実験法則ではない。

**Gurumoji への適用 [D]**:
- 状態モデルは少なくとも「準備／待機、実行中、部分完了、中止要求中、中止済み、失敗、完了」を区別する
- 今の工程、開始時刻／経過、対象ファイル、最後に進捗を受信した時刻を表示候補にする
- 計測できる工程だけ determinate progress にする。全工程が不明なら作り物の百分率を使わない
- 残り時間は実測に基づく推定と明記し、不明なときは不明とする
- 画面を離れてよいか、ブラウザーを閉じても継続するかは実際のライフサイクルに沿って説明する
- 中止ボタンを押した直後に「中止済み」と断定しない。保存できた中間成果を明示する
- 別の研究作業を妨げないなら全面のブロッキング表示を避け、戻れる進捗表示を維持する

**確認**: 別画面への移動、再読み込み、中止と完了の競合、部分失敗、通信切断、処理サーバー停止を試し、UI と実際のジョブ状態が一致するか確認する

### K12 エラーは原因と次の手順と保存状態を伝える

**適用場面**: 入力不備、保存失敗、モデル不足、メモリ不足、ネットワーク障害、同期競合

**根拠**: エラー回復・利用者制御は HCI 指針 [S01, S12, G]。WCAG のステータスメッセージには支援技術から知覚できる提示が必要になる [S26, N/解説]。

**Gurumoji への適用 [D]**:
- 「何ができなかったか」「何が残っているか」「次にできること」を分けて書く
- 入力値を保持し、原因に合った再試行・設定変更・詳細確認へ導く
- 「再試行」で最初から高価な全処理を重複起動しない。再開か再実行かを表示する
- 保存に失敗したのにモーダルを閉じたり、完了トーストを出したりしない
- 技術ログは詳細へ分け、run ID 等の非秘密の照合情報を出せるようにする
- エラー文の「入力は残っています」「安全にやり直せます」は、保持・冪等性を実装とテストで確認してから使う

**確認**: エラーを意図的に起こし、修正後に既入力内容で再実行できるか、ユーザーが結果を誤認しないか調べる

### K13 来歴は必要な場面で読めるようにする

**適用場面**: 見解、研究者メモ、AI 実行結果、分析表、エクスポート

**根拠**: W3C PROV-DM は entity、activity、agent と関係を表すデータモデルであり、来歴の相互運用を支える [S20, N]。その採用だけで UI が分かりやすくなるわけではない。

**Gurumoji への適用 [D]**:
- 普段は「元データ／対象数、作成時刻、作成元、確認状態」を短く示す
- 詳細では入力版、発話 ID、対象集合・フィルター、手法とパラメーター、モデル、run ID、出力版に戻れるようにする
- 出力ファイルだけでも何を対象に作ったか分かるようにする
- 再実行の結果と旧結果を取り違えない。原文変更による古い分析を明示する
- ユーザー向け表示に秘密鍵・認証値・不要な生の個人情報を混ぜない

**確認**: 任意の結論と集計値を一つ選び、その根拠と入力版を復元できるか。古い版の引用が新しい本文へ無表示で繋がらないかを調べる

## アクセシビリティの設計基準

WCAG 2.2 の AA を設計・検証の基準にする。ただし、以下は高関連項目の抜粋であり、これだけを通過して AA 適合を宣言してはならない。WCAG 本文が規範、Understanding と ARIA APG は説明／実装指針である。ネイティブ OS 全体の適合まで Web UI の検査だけで保証しない [S22]。

| 項目 | Gurumoji での基準と確認 | 根拠 |
|---|---|---|
| キーボード | 再生、話者修正、保存、フィルター、コード、モーダル、書き出しをマウスなしで操作。フォーカストラップを作らない | S30a、S22 2.1.2 |
| 文字キーのショートカット | 文字だけのショートカットは停止／再割当／その要素にフォーカス時のみ有効のいずれかを満たす。日本語 IME 変換中と入力欄では誤発火させない | S30b。IME は D |
| フォーカス | 可視で論理的に移動し、固定ヘッダーやプレイヤーで完全に隠れない。全体を見せる設計を目指すが、2.4.11 の AA 要件と AAA 要件を混同しない | S25、S22 2.4.7 |
| 操作対象 | 2.5.8 AA は原則 24×24 CSS px。間隔・同等操作・文中等の例外を適切に評価する。重要な頻回操作は更に余裕を取る | S24 |
| ドラッグ | 並べ替え、コードの移動、区間操作には単一ポインターでドラッグ不要の方法も用意する。キーボード代替だけで 2.5.7 を満たすとは限らない | S30c |
| 文字コントラスト | 通常文字は 4.5:1、大きな文字は 3:1 を満たす。薄い補助文、プレースホルダー、各状態を含めて測る。例外の適用は明示する | S28 |
| 非テキストと色 | 必要な UI 識別・状態表示・グラフ情報は対象となる隣接色に対して 3:1 を確認。話者・エラー・選択は色だけで伝えない | S29、S22 1.4.1 |
| 拡大とリフロー | 200% の文字拡大、縦スクロール主体では幅 320 CSS px 相当でも欠落せず操作可能か確認。二次元表などの例外があっても周辺の説明・操作まで免除しない | S27、S22 1.4.4 |
| 状態通知 | 保存、件数変更、処理完了や失敗をフォーカス移動なしでも認識できるようにする。読み上げを毎秒／毎トークン割り込ませない | S26。通知頻度は D |
| タブ | tablist/tab/tabpanel の役割と選択状態、矢印移動を合わせる。切替が遅い場合は手動 activation を検討 | S23a |
| モーダル | 開く時の適切なフォーカス、内部の Tab 移動、閉じる操作、通常は起動元へ戻るフォーカスを確認 | S23b |
| ラベルと意味 | ネイティブ要素を優先し、名前・役割・状態を支援技術で読めるようにする。placeholder のみをラベルにしない | S22 1.3.1、3.3.2、4.1.2、S23c |

「すべて 44 px 以上が WCAG AA」「フォーカス枠 2 px が 2.4.11」「ARIA 属性を付ければキーボード操作もできる」は誤り。プロジェクトの推奨値を標準の要求値と区別する。

自動チェッカーは反復検査に使えるが、原音を確認して編集する一連の操作、読み上げ順、保存失敗からの復帰、見解と根拠の理解は手動確認が必要である。

## 優先順位と重大度

Nielsen の severity は発生頻度、影響、持続性を考慮する指針 [S14, G]。Gurumoji では研究データの完全性と誤解の危険も加えて次の運用定義にする [D]。算術スコアの掛け算で精密に見せず、理由を残す。

| 重大度 | 定義 | 例 | 対応 |
|---|---|---|---|
| S4 致命的 | データ損失、誤った研究結果の確定、意図しない外部送信、中心タスクが特定利用者に実行不能 | 保存失敗なのに成功表示、引用元取り違え、キーボードだけで編集完了不能 | 当該機能の出荷／利用を止める候補。修正と再現テスト優先 |
| S3 大きい | 主作業が止まる、回復が難しい、繰り返し大きな負担／誤判断を生む | 30 分の編集を失う、処理中か不明で二重起動、対象集合が無表示で変わる | 主導線の改善として優先 |
| S2 中程度 | 迂回可能だが非効率や迷いが継続する | 前後音声に戻る度に検索し直す、専門語が不明、主要操作が深い | 関連する主作業とまとめて改善 |
| S1 小さい | タスク結果への影響が小さい表現・見た目の不整合 | 補助アイコンの間隔の揺れ、同義ラベルの軽微な不統一 | 高重大度の回帰を起こさない範囲で整理 |
| S0 未成立 | 問題と判断する根拠が不足、または仕様上必要な差 | 好みだけの配色変更、未確認の推測 | 仮説として残し検証 |

同じ症状でも文脈で重大度が変わる。発生頻度不明を「低頻度」としない。アクセシビリティ障壁や研究の完全性は少数利用者だから低くしない。複数評価者がいればまず独立採点し、不一致と根拠を残して合意する。

記録テンプレート:

- ID／発見日／対象 commit／画面／対象タスク
- 観測したこと／期待した結果／再現手順／証拠画像またはログ
- 利用者への影響／頻度が既知か不明か／回復手順／持続性
- 重大度と理由／根拠種別／確認済みか仮説か
- 最小修正案／副作用／受入条件／検証結果

## 実装前と回帰検証のチェックリスト

以下は利用者タスクを通して確認する。単に要素が DOM にあるかだけで合格にしない。

### 処理を始める

- [ ] 空状態で次にすることが分かる
- [ ] 選択ファイル、録音時間等の取得済み情報、設定要約が見える
- [ ] ローカル／外部処理と送信するデータ範囲が誤解なく分かる
- [ ] 詳細設定を閉じても重要な現在値が分かる
- [ ] 入力不備の場所と直し方が分かり、入力が残る
- [ ] 開始直後の二重クリックで二重ジョブを作らない

### 処理を待つ

- [ ] 実行中、通信切断、進捗未取得を混同しない
- [ ] 数値進捗／残り時間に計測根拠がある
- [ ] 別画面へ移動しても進捗に戻れる
- [ ] 中止要求と停止完了が別に見える
- [ ] 部分失敗、部分成果、再試行範囲が分かる
- [ ] 完了・失敗を視覚と支援技術の両方で確認できる

### 発話を確認して直す

- [ ] 再生中の位置と選択中の発話の関係が分かる
- [ ] 前後文脈を聞け、本文編集の位置を失わない
- [ ] 日本語 IME、複数行、長文、空文字、同名話者で入力が壊れない
- [ ] 名前変更と話者再割当の対象が明確
- [ ] 一括操作の範囲、変更前後、Undo の範囲が分かる
- [ ] 未保存／保存中／保存済み／保存失敗を取り違えない
- [ ] 再読み込み・画面移動時に未保存データが守られるか、失われる前に分かる
- [ ] 機械の候補、研究者の確認、音声の欠落を区別できる

### 分析し根拠へ戻る

- [ ] どの研究質問と対象集合の結果か分かる
- [ ] 単位・分母・欠測・除外・フィルターを確認できる
- [ ] 未実行、失敗、空、欠測、ゼロを区別できる
- [ ] テーマ候補・感情推定・観測量と確定解釈を区別できる
- [ ] 引用された発話と入力版を追い、前後文脈と原音へ戻れる
- [ ] 反例、少数意見、未確認発話が多数派の要約に埋もれない
- [ ] 根拠確認から戻ると対象・絞込み・位置が復元される

### 保存して外へ渡す

- [ ] プレビューと書き出しの対象集合・分母・単位が一致する
- [ ] データ版、手法、run、引用元を追える
- [ ] ファイル作成失敗をダウンロード成功と表示しない
- [ ] 研究者所有のメモを再生成や保存で上書きしない
- [ ] 秘密情報や不要な個人情報を出力へ混ぜない

### 横断的な利用可能性

- [ ] マウスを使わず中心タスクを完了できる
- [ ] 目に見えるフォーカス、自然な読み上げ順、タブ／モーダルの挙動を確認した
- [ ] 色覚差、文字拡大、狭い表示幅、長い日本語ラベルでも情報と操作を失わない
- [ ] コントラストと target size を通常／hover／focus／選択／エラーで確認した
- [ ] コード・図表・ドラッグの代替操作がある
- [ ] 通常表示を整えるために「対象」「保存」「失敗」「未確認」を隠していない

## 利用者検証の計画

これは実施済みの結果ではない。実利用者を募集できない間は、コード・画面操作・合成 fixture による検査として記録する。エージェントのペルソナ歩行を人のユーザーテストと呼ばない。

### 対象者と比較

初回利用者、文字起こしの反復編集に慣れた人、質的研究経験者、キーボード／支援技術利用者を可能な範囲で含める。初心者／熟練者で結果を分ける。形成的テストの人数を万能な「5 人で十分」規則から決めず、課題の異質性と検出すべきリスクを基に計画する。

改修前後比較では同じ機能・同程度の難しさを持つ別データを用い、課題・順序による学習効果を抑える。少人数の結果は問題発見として扱い、母集団での速度改善率や統計的優越性を主張しない。

### 代表タスク

1. 2～3 分の合成音声から、外部送信しない設定で文字起こしを開始する
2. 処理途中に別のデータを開き、元の進捗へ戻る。失敗箇所から復旧する
3. 話者が途中で入れ替わった発話を修正し、一括割当の範囲を確認して取り消す
4. AI が否定を落とした修正候補を原音から発見し、原文と比較して判断する
5. 話者 A のキーワードを探し、相手の直前の発話を含めてコードとメモを保存する
6. 「参加量が少ない」という図から、分母と欠測を確認し、理由を断定しない説明を作る
7. AI の見解に一致しない発話を探し、根拠へ往復して保存する
8. 絞り込んだ分析を出力し、対象集合と引用元が一致するか確かめる
9. キーボードだけで上記の中心作業を行い、拡大表示・読み上げで状態を確認する

### 成功指標

主指標は、正しい対象でのタスク完了、研究者の編集の保持、残存する誤り、根拠に基づく修正、回復の成功とする。補助的に時間、不要な画面遷移、操作ミス、ヘルプ依存、自己評価の負担を測る。NASA-TLX を使う場合は正式手順か簡略版かを明示し、6 次元の主観負担と実際の成績を混同しない [S21]。

Human–AI の評価では、人のみ、AI のみ、協働の比較が可能な課題と、唯一の正解を置けない解釈課題を区別する。106 実験のメタ分析では人と AI の組合せが最良の単独主体を必ず上回るわけではなかったが、対象期間は 2020 年～2023 年前半であり、現在の全 LLM や質的解釈の優劣を決める結果ではない [S07, R]。

採用率の上昇やユーザーの「信頼する」という回答だけでは成功としない。誤りに気づく力、根拠へのアクセス、作業負担、少数意見の保持を合わせて見る。

## DESIGN.md に移す内容

以下を恒久的な設計契約の候補とする。採用時に、現状で満たすもの／今回実装するもの／将来提案を分ける。

1. 原音・原文・提案・確定解釈の区別と来歴
2. 対象集合と分母が見える分析
3. 証拠へ低い操作コストで往復できるナビゲーション
4. 保存とジョブの状態モデル、失敗／中止の表現
5. キーボード・フォーカス・コントラスト・リフローの受入基準
6. 詳細設定と初心者／熟練者の共存方針
7. 一括操作の対象表示、Undo、研究者データの保護
8. 候補・未確認・欠測を成功やゼロとして扱わない表示規則
9. 各判断の出典、適用理由、例外、検証方法

装飾トークン、色、余白、角丸はこの契約を実現する一段下の設計とする。特定の配色やガラス効果を「科学的に最適」と記載しない。

## 限界と次の確認

- 日本語の長時間グループインタビューに特化した UI の直接比較研究は今回の範囲では十分見つかっていない。言語・録音長・話者数・専門知識による移植可能性を確認する必要がある
- 本調査は文献知識であり、Gurumoji の WCAG 適合、現行 UI の不具合、処理性能を証明しない
- confidence の是非、AI の効果、最適な密度は課題依存。単一論文や好みを恒久ルールへ飛躍させない
- アプリ改修後は、上の代表タスクで合成データを用いた操作確認と、可能なら実際の研究者による形成的テストを行う
