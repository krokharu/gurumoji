# Gurumoji：2案の低忠実度フロー比較

2026-10-02 UTC / レビュー用、未採用・未実装  
対象HEAD：`ddc23abe0d747a1e6cfd6d3bc262ce226f4756b0`  
この資料は合成例の静止設計案であり、現行アプリのスクリーンショット、操作可能な試作品、利用者テスト結果ではない。アプリ・runtime・Vault・資格情報には変更を加えていない。

## 判断の要約

**Aを段階導入の初期候補にし、Bの対照面と根拠paneを独立して比較する。** Aは既存の入口とdetailsを残しやすい。Bは定義と個票、主張と引用を同時に見比べられるが、nav移動と狭幅の復帰実装の費用が増える。この優劣はソースと構造に基づく設計判断であり、使いやすさを実証したものではない。

測定の意味、既採用版の保護、試行と採用の分離、実行時の定義固定は両案の必須条件。レイアウトの選択を待たずW02へ進められる。W01の実行入口修正も4タスク化を条件にしない。

## 1 同じ作業を異なる構造で見せる

| 観点 | A：既存モード＋段階レビュー | B：タスク入口＋対照面 |
|---|---|---|
| 分析内の入口 | 自動分析／設定・手動分析／手法別を保持 | 結果を見る／比較する／分析を組む／データ・出力へ再編案 |
| 測定定義 | 既存dialogの流れに沿う編集→試行→確認。図の左側は試行時の読み取り要約 | desktopでは定義編集を左、試行を右。編集と試行が同じ作業面にある |
| 採用 | 試行個票を確認した次の操作。採用と全件実行を分ける | 対照面の下で同じ採用操作。入力を変えたら右の試行は失効 |
| 根拠 | 結果card直下のdetailsを開く | 必要時だけ右pane。閉じると結果の幅を戻す |
| 390px | 定義・試行・採用を1段階ずつ、根拠は同じ結果内 | 定義／試行を同一draftの切替で表示。根拠は全幅の別状態 |
| 必要な復帰 | detailsの起点focusと展開位置、原音確認からの復帰 | 左の選択・filterを保持したpane開閉。mobileではrun等の復帰状態も必要 |
| 主なリスク | 長い引用の展開で結果が遠くなる。段階間で測定内容を記憶し直す | 同時に見せる情報が増える。モード再編による入口の学び直し、狭幅切替の状態管理 |

上部4入口、既存hash/query、対象ID、保存revisionは両案で維持する。Bの4タスクは上部navの置換ではなく「分析内」の再編。manual codeとmanual measurementを同じ意味の「手動」として統合しない。

図は設計注釈を同じ面に載せたストーリーボード。mobileの測定図は複数の状態を縦に並べており、実製品で全段階を1本の長いページにする提案ではない。desktopのAも定義編集と確認を同時に有効にするものではなく、左は保存した試行対象の要約である。

## 2 共通データと算術

全例はこのレビュー用に作成した架空の内容である。実録音・実本文を使わない。

- 対象：相談会サンプル、全5発話、除外1。試行は**除外後の先頭4発話**。任意の代表サンプル選択機能を暗黙に追加しない
- 定義：duration列／duration規則／number／ratio／descriptive、出力speech_seconds、単位は秒、分析単位segment
- S001：00:00–01:00 → 60秒。S002：01:00–01:02 → 2秒
- S003：01:02–01:02 → 0秒。現在のvalid_timeはstart <= endを許す。これは有効な計算済みゼロであり、未発言者を補ったゼロではない
- S004：時刻不明 → null、missing_reason=invalid_source_value。画面では欠測。詳細原因は現行の一般reasonより細かく推定しない
- 有効3、欠測1。平均は(60+2+0)/3=20.666…秒を20.7秒と表示。欠測を0として15.5秒にはしない
- 除外S005は試行対象外。除外数は全体5発話と明確に対応し、試行の欠測数に含めない
- 根拠例：固定run R-demo-07、生成時入力rev12、現在rev13、引用E-002→発話S002。本文が変わった合成状態なので現在音声への再生は無効

### 個票表示に必要な追加の境界

trialへrowsを追加するだけでは、この図の「入力時刻」と値を確実に照合できない。現在のmeasure_segmentsのrowsはID・話者・値・欠測理由を持つが、時刻・本文は持たない。試行に使ったsnapshotの入力値を応答に含めるか、その固定snapshotへIDで解決できる必要がある。最新の本文・時刻をjoinして試行時入力と表示しない。

これは「新しい入力保管システムを作る」という決定ではない。既存snapshot/input_hashを再利用できる範囲、固定入力に到達できない場合の表示、後方互換のresponse契約を先に確認する。入力照合ができない状態は採用前の未確認事項として表示し、個票を補完したふりをしない。

## 4 状態遷移と守る条件

### 測定：両案で共通

1. 定義編集：ID、規則、型、尺度、手法、単位、欠測規則を明示。descriptionは測定命令ではない。使用可能な組合せはvalidatorから確認する
2. 別draftを保存：既採用IDのpayloadを上書きしない。保存競合なら両方を保持し、旧payloadへの逆PUTをしない
3. 試行：上限は現行1〜100、例は4件。連打で重複送信を作らない。対象・draftが変わった後の遅い応答を今の試行として表示しない
4. レビュー：値・欠測・入力対応・限界を読む。失敗や個票不足は「確認できない」状態。0件や全欠測は平均0にしない
5. 採用：明示操作が必要。定義revisionまたはinput_hashが変われば古いレビューは無効。r1を採用PUTするとr2になる現行仕様を表示し、同じ内容のstatus更新と規則変更を区別する
6. 全件実行確認：採用とは別操作。対象、採用版、含む基礎処理、外部送信なし、保存先の実態を表示。O01、Transformer、AI見解をこの操作で一括実行できるとは示さない
7. 実行：受付時payloadを実行・再開・保存で固定するか、不一致で安全停止。最新版を自動採用して続行しない

「画面でチェックされた」をサーバーの永続レビュー記録にするには、定義revision・入力fingerprint・trial IDを結ぶ別契約が必要。採用応答が不明なときは操作成功を推測せず、正式状態を確かめてから表示する。

### 結果と根拠：両案で共通

- 保存済み結果の表示だけで推論や外部送信を始めない。pipeline status GETが自動回復を起こす場合と固定artifact読取を分離する
- 開く前にitem、run、result card、page、filter、selectedEvidence、scroll、focusOriginを保持。新しい永続session storeを前提にしない
- 原資料は生成時本文・話者・時刻・segment ID・入力版。現在の引用と不一致なら自動音声接続を止める
- 元segment削除、音声なし、入力版不明でも、保存引用があればその本文と取得できる来歴を残す。未知を現在版で補わない
- 再生中の発話、編集中の選択、保存引用を同じ選択状態に統合しない。この静止図は再生状態を実装していない
- 戻る／閉じる時は同じ結果へ。Bのmobileの戻る操作は結果を再計算する機能ではない
- 版照合が成功して音声がある別fixtureでは、通常の音声確認→戻るを検証する。今回の画面は意図的に不一致例を示す

### 実行・保存状態を画面案が上書きしない

| 状態 | 期待する表示 | 禁止する解釈 |
|---|---|---|
| accepted / running | 受付済み／処理中を分ける | 受付したから計算完了 |
| waiting | 理由とbackendが許す操作 | 任意の再開buttonを有効化 |
| failed | 失敗箇所、保存済み結果への入口 | 大見出しを「実行中」のままにする |
| cancelling / cancelled | 中止要求中／中止済み | 要求しただけで止まったことにする |
| 通信取得失敗 | 最終取得時刻と状態不明 | backendも失敗したと推測する |
| 計算完了・Vault書出し失敗 | 本体と保存先別の結果 | 全保存成功、計算から全再実行 |

## 5 方向性の採点

5=この観点で有利、1=不利。設計者による順序尺度の見積りで、利用者テスト・統計・使いやすさスコアではない。合計点は付けない。安全条件を満たさない案は点数に関係なく採用しない。

| 観点 | A | B | 根拠と限界 |
|---|---:|---:|---|
| 既存の入口・学習の継続 | 5 | 2 | Aは現在3モード。Bは分析内の入口を再編するため説明・移行が必要 |
| 定義と個票の同時対照 | 3 | 5 | Bは編集と試行を横に保持。Aは確定した要約で比較。実際の誤り発見効果は未測定 |
| 結果と引用の同時対照 | 3 | 5 | Bは2面を保つ。Aはdetails展開で長くなる。日本語長文と200%拡大では逆転し得る |
| 狭幅の状態の少なさ | 4 | 3 | Aの根拠は同じ文書内。Bは全幅根拠と結果の復帰を管理する必要 |
| 局所導入・戻しやすさ | 5 | 2 | Aは既存rendererに追加。Bはtask adapterと復帰管理を増やす |
| 完成前でも必須修正を先行できる | 5 | 5 | いずれもW01/W02の実行境界修正から切り離して導入する方針 |

**提案する決定**：W02の最初の実装にはAの段階を使う。根拠は既存detailsの版・復帰契約を先に整え、Bのpaneはオプション候補として後から比較する。Bの4タスクを採用するかは、修正後のAを基準に同じ課題で判断する。採用済みとは記録しない。

## 6 比較の実施方法

2案を丸ごと比べるとnav、レビュー方式、根拠配置が同時に変わるため、原因を1つに帰属できない。次段階では以下を分ける。

- 比較M：navとデータを固定し、段階レビューと対照面だけを変更
- 比較E：navと結果を固定し、detailsとpaneだけを変更
- 比較N：M/Eの方式を固定し、3モードと4タスクだけを変更

共通課題：

1. 「長さ」を文字数ではなく秒で測る。4個票から0と欠測を説明し、採用前に定義を変更する。古い試行で採用しないかを確認
2. AI下書きの根拠S002を開く。rev12とrev13の差を説明し、誤った音声再生を避け、同じ結果・filterへ戻る
3. 既採用定義を変更途中で取消。旧adopted版が保持され、取消が暗黙採用・実行にならないかを確認

静止図で確認できるのは、説明された構造、情報の所在、読解上の誤解候補のみ。click数・作業時間・focus復帰・完遂率は操作可能な試作品と参加者がなければ測定しない。V3 production CSSの通常操作、V4実AT、V5利用者理解は未実施。最終判断は安全な誤り発見と編集保持を優先し、速さや好みだけで決めない。

## 7 アクセシブルな表示を実装する場合の注意

- 各図にはtitle/descがあり、index.htmlには8図それぞれのテキスト代替がある。これを実アプリのスクリーンリーダー合格の証拠にしない
- 入力labelを可視で関連付ける。図の英語enumは設計確認用で、製品では日本語説明と対応する詳細値を用意する
- 0・欠測・除外・未実行を文字で区別。色だけに依存しない
- draft編集と試行結果に適切な見出しを付ける。status通知は必要な変化だけ読み上げる。毎秒全体再読をしない
- modalまたは切替を採用した実装でTab順、Escape、Close/Cancel、起点focus、未保存確認を検証する
- 390pxは静止図の幅でありreflow検証ではない。320 CSS px、200%/400%相当、長い日本語、Windowsフォント、日本語IMEは別に必要
- 出力形式ごとの含む・省く情報はW04等の下流仕様。今回の静止図は未実装のexport機能を追加しない
