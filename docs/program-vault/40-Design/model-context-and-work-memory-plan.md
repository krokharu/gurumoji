# モデル別コンテキスト管理と作業記録の保存計画

Gurumojiのローカル分析を、モデルの能力と入力予算に合わせて動かす計画。必要なルール・手法・根拠だけを取得し、会話を短くしても作業を再開できるようにする。設計判断と人が読む引継ぎはObsidian、機械が再開する状態はDB、全件の結果と入力は版付きJSONに保存する。

2026-10-05の「プランを実行して」に基づき、既存Handlerへ試験経路を追加した。`model_context_version=1`を明示した新規runだけに適用し、既定は0。実装済みの範囲と役割別品質の未評価を区別する。既存の[[core-handler-routing-reorganization-plan]]、[[expert-knowledge-production-plan]]、[[storage-policy]]を補足する。

## モデルの大きさと実効能力による使い分け

モデルの選択は、パラメーター数だけで決めない。既存の役割別モデル設定に、モデル版・量子化・実行エンジン・chat template・ロード枠・reasoning設定・実測時間・課題別評価を結び付ける。MoEは総パラメーターと有効パラメーターを取得できる範囲で区別し、不明値は不明として扱う。

| モデル規模の試験候補 | 任せる仕事の候補 | 採用条件 |
| --- | --- | --- |
| 7〜8B程度 | 少数発話の根拠抽出、定義済みラベルの下書き、範囲を限定した照合 | 根拠ID・出力型・欠測の扱いが課題別試験に合格。未合格の尺度設計や統合は任せない |
| 20B程度 | 専門分析、尺度設計、初期ルーティング、限定した結果の統合 | 役割ごとに評価。直近の尺度出力の成功をCore統合の合格へ流用しない |
| 32B以上や大規模MoE | 複数結果の比較、代替解釈、最終統合の候補 | 利用可能な機器・実ロード枠・時間予算で試験。大きさによる自動合格はしない |

この表は初期候補であり性能保証ではない。同じモデルでも役割別に合否を持ち、小型でも合格した役割は使用できる。計数、分母、task重複判定、hash照合は既存コードが行う。適合するモデルがない場合は理由付きで保留し、設定済み・許可済みの候補以外へ自動送信しない。

能力情報は既存AI設定の取得境界で確認し、評価記録はDB、選び方の理由はSoftware Vaultへ保存する。取得に伴うモデルのダウンロード・ロード・アンロードを行わず、ロード変更時は枠とtokenizerの対応を再確認する。

## 入力をトークンで予算化する

実ロード枠を`C_loaded`、利用者の上限を`C_user`、課題別に品質確認した枠を`C_validated`とする。確認済みの値から有効枠`C`を決める。品質確認枠が未取得の場合は未検証と記録し、検証済みと表示しない。

```text
C = min(C_loaded, 指定がある場合のC_user, 確認済みの場合のC_validated)
資料に使える予算 = C − 固定指示等 − 出力予約 − 安全余裕
固定指示等 = chat template + 共通必須ルール + 段階別schema
           + 必須の作業状態 + 必須の手法条件と限界
```

予算の例として、8,192枠から出力2,048、安全余裕1,024、固定指示等1,536を引くと、資料予算は3,584 tokensとなる。これは設計説明用の仮値であり、実測済み設定ではない。出力予約は役割・schema・公開されているreasoning設定に応じて決め、JSONが閉じる分も確保する。

実際のchat templateを適用した入力を対応tokenizerで計測する。schemaのサーバー側処理など数えられない部分は安全余裕と実応答のusageで較正し、計測値・推定値・不明を区別する。日本語を一律「4文字で1token」と換算しない。対応API/SDKが使えない場合は、検証済みの保守的な設定か、予算未確認による保留を選ぶ。

予算が足りない場合は、結果の束を小さくする、発話を分割する、任意の例を外す順に組み直し、再計測する。必須契約を含む最小入力が入らなければ実行前に停止する。文字列やJSONの途中切断、独立検証の制約・来歴の削除は行わない。

## ルールとスキルと資料を段階的に読む

開発用エージェントと、Gurumojiアプリ内の分析エージェントを分けて設計する。`AGENTS.md`や`SKILL.md`を配置しても、アプリ内のLLMが自動で読んだことにはならない。

| 層 | 内容 | 取得方法の提案 |
| --- | --- | --- |
| 常時必須 | 作業範囲、所有権、データ送信条件、根拠の契約、停止条件 | 開発用は短い共通ルール。分析用はHandlerが信頼済みの役割別指示を明示的に生成 |
| 入口 | `00-AI-Entry`、note_id・summary、スキルの適用条件 | タスク分類とメタデータで対象を限定 |
| 手順 | 該当スキル、手法の前提・限界、必要な保存契約 | 適用するものだけ取得。共通規則を各ノートへ複製しない |
| 根拠 | 確認したノート節、発話、結果表、必要な例 | 予算内の抜粋とID・版・hash。未取得部分を明示 |

現行の[Gurumoji保存スキル](../../../.agents/skills/gurumoji-obsidian-memory/SKILL.md)は、入口・要約・抜粋を段階取得する文字数制限を持つ。これを削除せず、モデル別トークン予算との小さい方で取得する。スキル本文には入口、適用条件、手順、終了条件を残し、長い契約や例は既存referencesへ整理する。入口だけでは必要な規則が漏れるケースも試験する。

専門知識の部分取得は、承認済みclaim・参照元hash・送信条件を検証してから選択し、生成したパケットも再検証する。手法の前提や限界を関連度が低いという理由で落とさない。文献の根拠と発話の根拠は別の種類として渡す。ノート本文は参照資料として扱い、実行権限を変更する指示へ昇格させない。

パケットには、タスクと対象版、取得したID・版・hash、実際に渡した本文範囲、未取得範囲、取得理由、予算、renderer版を残す。IDの紹介だけを本文の既読と数えない。再利用キャッシュは取得条件・役割・送信条件・元のhash・renderer版で識別し、元資料の変更時に無効化する。

## 初期分析と反復の進め方

初回に全分析エージェントへ依頼し、必要なラベル・尺度を専門エージェントが作る方針を維持する。初回ルーティングはCoreの統合反復回数へ含めない。

1. Handlerが対象入力版と対象集合を固定し、選択された全分析エージェントへ依頼する。全量分析では各役割の発話範囲を予算内に分割し、境界に必要な前後発話を付ける。重複した前後発話を集計の分母へ二重計上しない。
2. ラベル・尺度が必要と判明した専門家は、初回途中でもHandlerへ必要性・用途・型・根拠を報告する。Handlerが重複をまとめてDBへ保存し、Coreへ版付きで報告する。現在の全初期結果を集めた報告に加えて、途中報告の受付を追加する提案である。
3. CoreはHandlerに適切なオーケストレーターへの依頼を指示する。専門エージェントが定義・値の意味・判定基準・欠測条件・根拠を作成する。途中報告の更新で同じ作成依頼を乱発せず、初期集約時に充足・不足を確認する。初回の尺度出力必須条件を省略しない。
4. 尺度定義を保存した後、実際に各発話へ値を付ける工程が必要なら別タスクにする。AI下書きと研究者が確定したコードを分け、定義があるだけでコード付与や尺度妥当性が完了したとは扱わない。
5. 未評価結果は専門オーケストレータが分野別・予算内の束で査定する。必要な根拠本文はHandlerが取得し、原結果を追える状態で採否・理由・見解への影響を保存する。Coreには短い分野別報告と未解決点を渡し、固定の「20件」が入らないモデルでも未評価結果を落とさない。分割数をCore反復回数へ加算しない。
6. 2回目以降は新しい根拠、前回との差分、未解決点、未評価結果を優先する。同じ役割・対象版・範囲・条件の済みタスクは再利用し、明示的な再生成は別attemptにする。同じ主張や作業案の再提出を回数達成だけで進展と判定しない。

独立verificationには、他専門家の出力・Coreの見解・尺度下書きを渡さない現行のblind契約を維持する。全量提示、応答受領、根拠照合済みを別々に記録し、単なる提示を理解の証明にしない。全量を読めていなければ部分分析と表示する。検索による関連発話の取得だけでは、全量を読んだ扱いにしない。

## 作業内容を保存する場所

「人が読む理由」と「機械が再開する状態」で分け、同じ全文を両方へ複製しない。正本の詳細は[[storage-policy]]と[[../30-Data/analysis-storage-v1]]に従う。

| 作業内容 | 正本の保存先 | 保存する内容とタイミング |
| --- | --- | --- |
| 設計判断、作業方針、手法の選び方 | Software Vault | 意味のある区切りで既存の該当ノートを更新。理由、対象版、検証結果、未解決点、次の作業、成果物参照 |
| 分析の再開状態 | 既存SQLite台帳 | run/task/attempt、依存、対象版、処理範囲、未評価結果、進展、停止理由。状態遷移で保存 |
| モデルと入力の来歴 | DBの版付き記録とJSON参照 | モデル・量子化・設定・prompt/schema/renderer版、取得ID/hash、入力と出力の予算・実測usage。不明値を0としない |
| 原入力、原結果、大量の表、固定入力パケット | 既存成果物保存経路のJSON・CSV | 全件を保持し、DBはID/hashと参照を管理。既存の原応答保存は維持し、新しい重複全文保存を増やさない |
| 分析の人向け経過・結果 | 選択されたOrchestrator/Visualization/Research Vault | DB・成果物から概要を生成し、run ID・版・根拠・未実行範囲へ戻れるようにする |
| 研究者の解釈・自由メモ | 研究者所有のMarkdownまたは既存の確定メモ保存先 | 現行の所有権を維持。AI記録で本文・タグ・別名を上書きしない |
| 開発の実行ログ・検証出力 | 既存の検証成果物 | コマンド・結果・commitと作業ツリーhash。Software Vaultには要点と参照を残す。分析runを装ってDBへ登録しない |
| 検索索引、組立て途中のパケット | 再生成可能なキャッシュ | 元ID/hashに基づく索引。正本や長期記録の代わりにしない |

開発作業は当面、Software Vaultの既存セッションノート＋検証成果物で十分と判断する。開発タスクの再開・検索需要が実測で生じた場合に限り、既存ジョブ記録との適合を確認し、必要最小限の作業台帳を追加する。分析台帳へ無関係な開発イベントを押し込まない。

DBとファイルを同一トランザクションと見なさず、既存のstaging・manifest・回復経路を使い、原成果物の確定と台帳の対応を検証してからノートを公開する。Vaultへの保存が失敗した場合は公開待ち/失敗を記録し、保存済み分析を再推論しない。公開を選択していないrunは未公開として保持する。

再開用の短い要約には、目的、済んだ作業、未処理、採用判断と理由、失敗/未実行、次の作業、元記録ID/hashを含める。要約だけを唯一の証拠にしない。生成ノートはVaultRegistry、AnalysisStore、既存の所有権・履歴保存経路を通す。必要なDB変更は追加のみとし、実Vaultを移行試験に使わない。

## 実装の順序と完了条件

順序はP0→P1→P2→P3→P4。日数はP0の計測後に見積もり、未計測の性能目標で工数を断定しない。各段階で既存runの読取、盲検、送信条件、進展判定を維持する。

| 段階 | 作るもの | 主な変更候補 | 完了条件 |
| --- | --- | --- | --- |
| P0 現状計測 | 役割別のprompt・schema・入力・履歴の内訳と評価項目 | 既存の試験スクリプト、保存済み台帳の読取 | 先頭48発話の比較対象と全323発話の別試験を固定し、超過・未実行・統合不足を区別 |
| P1 入力予算 | ロードinstance情報、token計測、出力予約、実行前判定 | `services/ai/settings.py`、`services/ai/client.py`、既存adapter | 最終入力全体が予算内。最小入力が入らない場合はAIを呼ばず理由を保存。ロード変更・不明値も検証 |
| P2 必要情報の取得 | 初期ルーティング等の専用契約、段階取得、発話分割、未評価結果の分割 | `analysis_orchestration.py`、adapter、専門知識の既存生成境界、対象スキル | 全量試験で各役割の対象323発話を漏れなく提示。前後文脈の重複計数なし。必須の手法条件と根拠、blind契約を維持 |
| P3 保存と再開 | 取得範囲とパケット来歴、途中の尺度要求、差分要約、公開待ちの回復 | 既存SQLite台帳・checkpoint・成果物保存・Vault生成 | 再起動で保存済み結果を再利用。未処理が消えず、Vault失敗だけで再推論しない。人の編集を保護 |
| P4 モデル評価と導入 | 役割別の合格表、マーラータン比較、新設定の選択導入 | 関連テスト、実AI試験、Software Vaultの運用資料 | 予算・根拠・内容進展の基準を満たした組合せだけ使用。未合格の役割は明示的に保留 |

P2以降の保存情報は、P1から取得条件とID/hashを記録できるようにする。小さい縦切りで導入し、空の共通基盤や全テーブルの作り直しを先行させない。runtime変更にはprompt/packet/config版を付け、旧runを新設定で自動再実行しない。

## 検証方法と採用基準

最初に一時DBと架空の日本語発話で、8K・16K・32K等の設定枠を試験する。これは容量制御の合成試験であり、その枠で実モデルの品質が保証されたことにはならない。実AIは利用可能なモデルごとに、モデル版・量子化・実行設定・prompt・対象集合を固定して比較する。

| 観点 | 必須の確認 |
| --- | --- |
| 入力と出力 | schemaとtemplateを含む入力、出力予約、安全余裕の合計が実ロード枠以下。途中終了を成功にしない |
| 節約効果 | 同じ発話集合・必須条件で比較し、指示・schema・反復履歴のtoken削減を測る。30〜50%削減は試験目標であり未達でも証拠を削って達成扱いにしない |
| 全量と位置 | 323発話のコピーを予算別に分割し、IDの集合で提示範囲を照合。重要な根拠を先頭・中央・末尾へ動かし、対象数・分母・根拠追跡を検証 |
| 初回の尺度 | 全初期役割への依頼、途中要求の永続化、Handler集約、Core指示、専門家作成、保存の順序。定義だけの状態と値付与済みを区別 |
| 反復の中身 | 回数ごとの新しい根拠・結果採否・主張・保留理由・停止理由を表にする。同じ作業案やIDだけの変化を進展にしない |
| 統合品質 | 主張がある場合は根拠本文と対応。主張を出せない場合は入力不足・対立・未完了工程を追跡できる保留理由が必要。3回実行やJSON合格だけで分析完了にしない |
| 再開と競合 | 完了済みタスクの再利用、未評価結果の保持、元hash変更時の再取得、Vault公開失敗からの回復、人の編集保護。応答未保存の実行は状態不明として扱い、成功を仮定しない |
| 情報の分離 | verificationのblind入力、専門知識の承認と送信条件、秘密値の除外、原本DBと研究者Vaultへの試験書込みなし |

課題別の研究妥当性は構文validatorと分けて評価する。根拠のない主張を増やしてCore主張数0件を解消しない。応答待ち・不正応答・未実行を区別し、VRAM・処理時間・総呼出数も実測する。入力削減で呼出数が増える場合は総時間と品質を合わせて判断する。
