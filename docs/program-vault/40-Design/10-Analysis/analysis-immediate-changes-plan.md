## 1. 範囲と前提

- **実行環境**：利用者のWindows PCで `127.0.0.1` に限定して動く1人用アプリと、利用者が起動するColabジョブ。Dotは開発専用で、実行時の設計条件に含めない。
- **選定基準**：後から取り戻せない、または後回しにすると全データの付け直しが必要になる変更を優先する。新しい分析手法（系列H）は、土台の完成後に最後に行う。
- **DB**：SQLiteを主DBとして維持する。PostgreSQLや別種のDBは導入しない（第15節）。
- **既存の規則**：DBは追加だけで、既存カラムを削除・改名・型変更しない。テストは一時DB・架空データで行い、実Vault・実DBを使わない。利用者データの移動・削除は、対象を示して確認を得てから行う。
- **データの状態（2026-10-12、利用者の判断）**：利用者DBは試験用データだけ。そのため次の2点を許容する。実データを入れる前に、この項目と第16節を見直す。
  - 会話の削除で、新しい表の行が消えて復元で戻らないこと（D8）
  - 移行や切替の前に、追加のバックアップを用意しないこと

## 3. 系列A：分析コアの整合

対象は `src/gurumoji/analysis_core.py`（分析コア）、`src/gurumoji/analysis_pipeline.py`（実行Runtime）、[分析コア制御契約](../analysis-design/core-control-contract.json)と[Schema](../analysis-design/core-control.schema.json)、[統合設計 第17・18節](analysis-milestone-visualization-design/00-Index.md)。

### 基本方針

- **分析コアは決定的な規則で判断する。** Jev・LLM・その他の外部判定を、実行可否・順序・回復・完了の判断経路に入れない。同じ事実からは常に同じ判断を返す。
- **分析コアは純粋関数の集まりとする。** SQLite・ファイル・通信・ロック・待機を持たない。Runtimeが事実を集めて渡し、コアが判断（`CoreDecision`）を返し、Runtimeが比較更新で永続化して実行する（第18.1節）。
- **規則にできない判断は利用者へ返す。** 意味上の十分性や代替手法の選択など、規則で決められない場合は `wait_input`（利用者の確認待ち）とし、外部判定で埋めない。
- **性能の条件。** コアの呼出しで書込トランザクションを増やさない。guardはRuntimeが既に読んだ事実だけで評価し、全発話の再走査やhash再計算をしない。
- **LLM・Jevの位置は変えない。** 計画候補の提案（O01）や分析手法の実行には引き続き使えるが、出力はハンドラーの報告またはAI下書きとして扱い、コアが検証して採否を決める。

### 実施順（2026-10-12 変更）

A-P0 → A-P3 → A-P4 → A-P1 → A-P2 → A-P5 → A-P6 の順に行う。A-P1で全更新を表に通す前に、表の中身（A-P3）と回復方針（A-P4）を決める必要があるため。一時的な互換遷移は作らない（Q14）。

### A-P0 判断不要の不具合修正

- `build_plan_envelope` で `research_protocol` を正規化し、`classification` の既定値を保存値へ入れる（問題8）。
- 検証的分析は `preregistered is True` の場合だけ受け付ける（問題9）。
- `build_execution_binding` のrevision参照を正規化済みIDで引く。`_run_guarded` の到達しない分岐を除く。
- テスト：`test_analysis_research_protocol`・`test_analysis_plan_binding` に、`classification` 欠落・`preregistered: "no"`・前後空白付きIDの3件を追加。

### A-P1 遷移を一つの経路へ集める

A-P3・A-P4の後に行う。

- 最初に、状態を書く全SQLを機械的に一覧にし、A-P3で決めた表と照合する。表にない書込みが一つでも残る間は、A-P1を完了としない。
- `analysis_core` の遷移判定を本番用にし、guard IDを必須にする（既存の `validate_transition` を拡張）。
- `analysis_pipeline` に比較更新のヘルパー（`UPDATE … WHERE status=? AND generation=?`）を置き、pipeline・step・publicationの状態更新をすべて通す。guard IDはイベントへ記録する。
- 連続する遷移（`checking → ready → running` など）は1トランザクションにまとめ、書込回数を現状以下にする。
- テスト：表にない遷移を1件ずつ試して拒否されること、1回のpipeline実行の書込トランザクション数が変更前以下であること（SQLiteのtrace callbackで数える）。

### A-P2 判断をコアへ移す

挙動を変えずに、Runtimeにある判断を純粋関数としてコアへ移す。各関数は事実を受け取り、Schemaの `CoreDecision`（`action`・`reason_code`・`affected_steps`・`rule_refs`・`resume_condition`）と、適用する遷移（guard ID付き）を返す。

| 現在の場所 | コアへ移す判断 | 返す action |
| --- | --- | --- |
| `_run` の実行可能step選択・段階完了 | 親が確定したstepの選択、段階ゲートの解放 | `dispatch` / `release_gate` |
| `_run` の失敗処理 | エラーコード→`reason_code` の対応表（`publication_failed`→`PUBLICATION_FAILED` など）、待機理由の決定 | `retry` / `fail` / `cancel` と待機理由 |
| `_run` の最終判定 | 公開先別状態からpipeline完了か公開待ちか | `commit` / 公開待ち |
| `_execute_step` の適用外条件 | `allow_not_applicable` と計画条件による適用外判定 | `mark_not_applicable` / `dispatch` |
| `retry()` | 再試行対象stepと上限（`attempt >= 3`） | `retry` / `fail`（`RETRY_EXHAUSTED`） |
| `initialize_pipeline_store` | 起動時に残った要求を取消確定か回復待ちに分ける | `cancel` / `reconcile` |
| `_run_guarded` の例外処理 | 想定外の例外時に取消確定か失敗か | `cancel` / `fail` |
| `status()`・`_allowed_actions` | milestone状態の導出、利用者に出す操作 | 表示用の導出値 |

- 対応表にないエラーコードは、推測で再試行にせず、現在と同じ扱いを明示した規則にする。
- 判断の記録は `CoreDecision` をイベントへ保存し、どの規則版で何を決めたかを追跡できるようにする。
- コアから `sqlite3`・`flask`・`os`・ネットワーク関連をimportしないことをテストで固定する。
- テスト：既存の分析コア関連テストを、A-P4で変えた期待値のまま、A-P2の前後で期待値を変えずに合格させる。判断関数ごとに、事実の組合せ→判断の表形式テストを追加。

### A-P3 遷移表の一本化（Q1）

A-P1の前に行う。

- `analysis_core.py` の表を唯一の正本にし、guard IDを付ける。実行時に使わない4状態（`waiting_resource / awaiting_input / retry_wait / blocked`）は `reserved` とし、実装するまで遷移を持たせない。`reused` は[[40-Design/10-Analysis/analysis-reuse-snapshot-package-plan#2. 計画1：確定済みstepの再利用|別計画の計画1]]で実装する。

  - 表に加える（例：起動時の `interrupted`、再公開の `published → publishing`）
  - A-P4で書込み自体をなくす（例：終端からの `accepted`）
- 待機中のstep再試行（`waiting → accepted`）と、A-P4の `resume` 操作で通る遷移も、ここで決める。
- 契約JSONの `state_machines` を実装表に合わせて更新し、両者の一致をテストで固定する。
- 契約にだけあった遷移は個別に判断して記録する。例：`retry_wait→checking` の「再試行時に適用性を再検査する」意味は、新attemptが `planned→checking` を通ることで満たすことを確認する。

### A-P4 回復方針（Q2・Q3）

A-P3の後、A-P1の前に行う。

- `retry()` は `cancelled / failed` のpipelineを `pipeline_terminal` で拒否し、新しい `request_id` での新pipelineを案内する。画面は開始ごとに新しい `request_id` を作るため、既存の開始操作で足りる。確定済みstepの再利用は[[40-Design/10-Analysis/analysis-reuse-snapshot-package-plan#2. 計画1：確定済みstepの再利用|別計画の計画1]]で扱う。それまでは新しいpipelineで全stepを計算し直す。

- UI（`static/analysis-execution.js`）に再開ボタンを追加する。「利用可能な手動再開操作はありません」の文言とJ13の回避文言を更新する。再起動後に状態取得を繰り返し続けないことも含め、画面操作で確認する。

## 4. 系列B：SQLiteの読み書き

### B1 よく通る処理で必要な列だけを読む

- `_assert_current`・`_cancelled`・`_pipeline_row`・`status()` は、`generation / status / cancel_requested / wait_reason` など必要な列だけを読む。
- `snapshot_json / plan_json / binding_json` は、使う箇所（実行開始、固定定義の読込、結果保存）でだけ読む。
- コード変更のみ。挙動は変えない。

### B2 入力スナップショットを絞る（Q4）

入力スナップショットは、分析パイプラインの受付時点の入力を丸ごと固定した写し。実行中や実行後に原文・注釈・設定が編集されても、結果が「どの入力から計算されたか」を変えずに再現・検証するために使う。注釈・設定・話者台帳は上書き保存で履歴がないため、版番号から組み立て直す方式では代わりにならず、写しは必要。

計測した1件（約8.2MB）の内訳は、`analysis`（約7.3MB：計量テキスト分析の詳細 約5.5MB、発話分類 約0.76MB、発話 約0.42MB、手動注釈 約0.33MB、Transformer結果 約0.24MB ほか）と、AnalysisStoreへ保存する `archive_snapshot`（約0.81MB）。パイプラインのステップが読むのは、発話・自動集計（約0.04MB）・手動注釈と、保存時の `archive_snapshot` だけ。ほかは、スナップショット作成時に `include_research_rows=True` で会話の分析全体を取り込んでいるため入っている。

- 版2の中身・読込・版1との同値確認は、[[40-Design/10-Analysis/analysis-reuse-snapshot-package-plan#3. 計画2：入力スナップショット版2|別計画の計画2]]で定める。版2は版1の部分集合で、計量テキスト分析の行を除く。
- `archive_snapshot` はhashの参照にせず、そのまま持つ。AnalysisStoreが入力を保存するのは結果の保存時だけで、受付から保存までの固定入力はスナップショットにしかないため（2026-10-12の点検で判明）。
- 新しい手法が別の部分を必要とする場合は、版2に入れる節の一覧へ加える。他の分析の結果は写さず、保存済みの実行または系列Fの表をIDとhashで参照する。
- 既存6件の旧形式スナップショットは変更せずにそのまま読む。旧形式は、その時点の発話分類・Transformer結果の写しも兼ねている。
- 見込み：1件約8.2MB → 計量テキストの行（約5.5MB）を除いて約2.7MB。発話分類・Transformer結果も除ければ約1.7MB。架空データで計測して確定する。

**別テーブル化の判断（Q4：2026-10-12 決定）**：絞った後に、架空データで状態列だけの読込時間を測る。1回1ms以上かかる場合は、次の別テーブル化も行う。1ms未満なら絞るだけにする。

- 追加テーブル `analysis_pipeline_snapshots(snapshot_hash PRIMARY KEY, snapshot_json, created_at)`。`snapshot_hash` は正規化したスナップショット本体のSHA-256とし、同じ中身は1回だけ保存する。
- 新しいpipelineは受付と同じトランザクションでこのテーブルへ書き、`analysis_pipeline_requests.snapshot_json` には参照（`{"snapshot_ref": "<hash>"}`）だけを入れる。読込時は参照があれば別テーブルから読み、hashを照合する。参照がない旧行は従来どおり列から読む。
- 「中身のhashで一度だけ書き、既存と異なれば拒否する」規則は、AnalysisStoreの入力保存と同じものを使う。
- 旧行の大きな値は移行しない。縮小する場合は別作業とし、バックアップ・dry run・復旧手段を先に用意する。

### B3 WAL方式への切替（Q5）

- DB初期化時に、データフォルダーがローカルの固定ディスクにあると判定した場合だけ `PRAGMA journal_mode=WAL` を設定する。
- **判定**：次のどれかに当てはまる場合は、ローカルとみなさない。判定できない場合も従来方式にする。判定規則はテストで固定する。
  - Colab（`is_colab_runtime()`）、または `/content/drive/` の下
  - Windowsでドライブ種別が固定ディスク以外、またはファイルシステムがNTFS・ReFS以外
  - パスに同期フォルダーの名前（OneDrive・Google Drive・マイドライブ・Dropbox）を含む
- **明示的に戻す**：WALの設定はDBファイル自体に残る。ローカルでWALにしたデータフォルダーを後でDriveへ移した場合に備え、ローカル以外と判定したら起動時に `PRAGMA journal_mode=DELETE` を設定する。
- **バックアップ（Q13）**：新しいバックアップの仕組みは足さない。既存のデータのバックアップはSQLiteのバックアップ機能（`source.backup`）を使うため、WALでも一貫している。初回切替の前のバックアップも取らない（試験用データのみ）。
- **手動の復元手順**：[[60-Operations/10-Data/backup-restore|バックアップと復元の手順]]に1文を足す。内容は「`library.sqlite3-wal`・`-shm` はDBと一組で扱い、復元先に古いものを残さない」。古いWALが残ると、戻したDBに適用されて壊れるため。

### B4 自律分析の実行状態の計測

- `orchestration_runs.state_json` は書込のたびに実行全体を書き直す。利用者DBには実行記録がなく、未計測。
- 架空データで多数のタスクを持つ実行を作り、1回の書込の大きさと時間を測る。問題がある場合だけ、追加テーブルへの分割を別計画にする。

## 5. 系列C：会話横断分析の土台

索引（`sqlite-vec` 等）は後で作る。ここでは、後から付け直せない識別子と版を先に決める。

### C1 発話単位のベクトル保存

- 追加テーブル `segment_embeddings(item_id, segment_id, text_sha256, input_hash, model_name, model_revision, dimensions, encoding, vector BLOB, created_at)`。主キーは `item_id, segment_id, model_name, model_revision, text_sha256`。
- `analysis_jobs.py` が `transformer_analysis_json` を更新するのと同じトランザクションで書く。符号化は既存の `_pack_vectors` と同じint8・scale 127。
- 既存の `transformer_analysis_json` 内のベクトルと意味検索は維持する。旧データからの取り込みは任意とし、行う場合はdry runで件数とhashを確認する。
- `text_sha256` により、発話の編集後に古いベクトルを判別できるようにする。
- 会話を削除した時の扱いはD8に従う。

### C2 比較用の標準モデル（Q6）

意味ベクトルはモデルと版ごとに別の座標系になるため、異なるモデル・版で作ったベクトルどうしの類似度には意味がない。会話をまたいで比べるには、全会話を同じモデル・版で計算する必要がある。

| 項目 | 現在の `intfloat/multilingual-e5-small` |
| --- | --- |
| 版 | コミット `614241f622f53c4eeff9890bdc4f31cfecc418b3`（読込時に解決して結果へ記録済み） |
| 次元 | 384。int8で保存すると1発話384バイト（10万発話で約38MB） |
| 入力上限 | 512トークン（コードは6,000文字で切り詰め） |
| 使い方 | 検索語に `query: `、発話に `passage: ` を付ける（実装済み） |
| 実行場所 | ローカル（キャッシュ約470MB）。外部送信なし |

- 上記のモデル・版の組を「埋め込み標準 v1」として設定に記録する。比較・検索は同じ標準のベクトルだけで行い、異なる標準のベクトルは混ぜずに拒否して再計算を案内する。
- 標準を変える場合は「埋め込み標準 v2」を作り、全会話を再計算する。`segment_embeddings` はモデル・版を主キーに含むため、移行中は新旧が共存できる。
- 変更候補は、より大きい多言語モデルや日本語特化モデル。研究者が類似と判断した発話の組で検索精度を比べてから決める。
- クラウドの埋め込みAPIは、守秘性のあるデータを外部へ送るため候補にしない。

### C3 会話をまたぐ定義の同一性（Q7）

- 現在の定義は会話ごと（主キー `item_id, definition_id`）で、同じIDでも中身が違い得る。
- 会話横断の集計では、定義の同一性を定義IDではなく定義hash（`fingerprint(定義本体)`、実行束縛に記録済み）で判定する規則を、分析コアの純粋関数として追加する。
- 共有コードブックの表は、研究者が会話横断のコード管理を必要とした時点で別計画にする。

### C4 グラフの節点と辺の識別子

- 節点：発話 `utt:<item_id>:<segment_id>`、話者 `spk:<participant_code>`（`speaker_registry` にない場合は会話内 `spk:<item_id>:<speaker>`）、語 `term:<lemma>:<pos>`、定義 `def:<definition_hash>`、知識ベースの主張 `clm:<claim_id>`。
- 辺の必須項目：始点、終点、関係の種類、重み、出所（`rule / ai_draft / researcher`）、生成した手法と版、入力hash、根拠の発話ID。
- 識別子の生成・検証は分析コアの純粋関数にし、契約を[[30-Data/00-Index|データ契約]]へ記録する。

### C5 複数インタビューの架空データ

- `tests/fixtures` に架空の3会話（話者の重なり、同じ定義・異なる定義、発話の編集、手動コード付き発話を含む）を作り、系列B〜D・F・Hのテストで使う。

## 6. 系列D：話者・属性・グループのDB管理

### 現状

| データ | 置き場所 | 問題 |
| --- | --- | --- |
| 参加者台帳 | 表 `speaker_registry`（API `/api/speakers`、CSV取込・書出あり） | 自由属性は `attributes_json` の中で、キーの定義がない |
| 会話ごとの話者情報 | `library_items.speaker_profiles_json`（話者ラベル→プロフィール、`global_speaker_id` で台帳と対応） | JSONの中にあり、会話をまたいでSQLで集計・検索できない |
| 発話ごとの話者・時刻 | `library_items.segments_json`（`id / speaker / start / end / text`） | 同上 |
| 会話の属性 | `session_profile_json` の固定項目 | 自由なキーがない |
| 会話のグループ | `library_groups`（1会話1グループ） | 複数グループに入れない。条件で決まるグループがない |
| 基本情報 | 取込日時（`created_at`）、保存場所（`media_path`）、メタデータからの実施日 | 動画の長さ・形式・サイズがない |

これらのJSONは12ファイルから読み書きされている。既存の `analysis_store_*_changed` トリガーが同じ列の更新を検知して結果を古い扱いにしている。

### 方針（Q8）

- **当面はJSONを正本のまま残し、DBの表はSQLiteトリガーで自動展開する。** `library_items` の該当列が挿入・更新されるたびに、同じトランザクション内で表を作り直す。12ファイルの書込経路を変えずに、表とJSONが常に一致する。
- トリガーは `json_valid()` を満たす場合だけ展開し、不正なJSONで元の保存を失敗させない（2026-10-12、一時DBで動作確認済み）。不正JSONの会話は整合検査で報告する。
- 表を正本にしてJSONを互換出力に回す移行は、表の利用実績を見てから別計画にする。

### D1 会話ごとの話者の表

- 追加テーブル `conversation_speakers(item_id, speaker_label, global_speaker_id, display_name, session_role, organization, department, job_title, consent_status, recording_consent, attendance_status, registration_status, PRIMARY KEY(item_id, speaker_label))`。`global_speaker_id` に索引。
- `speaker_profiles_json` の挿入・更新トリガーで `json_each` から展開する。

### D2 発話の表

- 追加テーブル `conversation_segments(item_id, segment_id, ordinal, speaker_label, start, end, char_count, PRIMARY KEY(item_id, segment_id))`。本文は重複保存しない。
- `segments_json` の挿入・更新トリガーで展開する。会話1件（323発話・49KB）では作り直しの負担は小さい。数千発話の架空データで保存時間を変更前後比較する。
- **発話ID**：IDがない発話のIDは、Pythonが読込時に補っている（`ensure_segment_ids`）。SQLではこの補い方を再現できない。
  - トリガーが展開するのは、`id` が有効な形式（英数字・`_`・`-`、80文字以内）の発話だけ。`INSERT OR IGNORE` で書き、重複で元の保存を失敗させない。
  - IDのない発話や重複したIDがある会話は、整合検査で報告する。
  - 2026-10-12時点の利用者DBは全発話にIDがあり、重複もない（読取専用で件数だけ確認）。
- **表に入らないもの**：準備状態の除外は入れない。表で数えた発話数は全発話の数で、分析の分母はスナップショット側で決まる。この違いを表の説明に書く。

### D3 属性キーの台帳と属性値

- 追加テーブル `attribute_definitions(key, scope, data_type, measurement_level, allowed_values_json, description, origin, version, PRIMARY KEY(key, scope))`。
  - `scope` は `conversation / speaker / segment`
  - `origin` は `researcher`（研究者が作成）と `discovered`（既存データから登録）
- 追加テーブル `conversation_attributes(item_id, key, value_json, source, updated_at, PRIMARY KEY(item_id, key))`。会話の自由属性（地域・年度・実施条件など）の正本とする。
- 話者の自由属性は `speaker_registry.attributes_json` を正本のまま、トリガーで `speaker_attributes(speaker_id, key, value_json)` へ展開する。話者を削除したら、トリガーで展開先の行も消す。
- **会話の属性**：保存時に定義の型・許される値を検査する。未定義のキーは受け付けず、先に定義を作る。
- **話者の属性**：既存の自由入力とCSV取込を変えない。CSV取込は、知らない列をすべて自由属性に入れる。
  - 初回展開時に、台帳にある既存キーを `data_type: string`・`measurement_level: nominal`・`origin: discovered` の定義として登録する。
  - CSV取込で新しい列が来た場合も同じ形で自動登録し、取込を拒否しない。
  - 研究者が型を確定したら定義の版を上げる。合わない既存値は整合検査で報告し、保存は拒否しない。
  - `discovered` の定義も条件グループ・グループ化キーに使えるが、画面には「型未確定」と表示する。

### D4 データグループとタグ（Q9）

- 追加テーブル `data_groups(group_id, name, description, kind, rule_json, version, created_at, updated_at)`。`kind` は `manual`（会話を選ぶ）と `rule`（例：タグ「2024年度」かつ 地域＝A）。
- 追加テーブル `data_group_members(group_id, item_id, added_at, PRIMARY KEY(group_id, item_id))`。1会話が複数のグループに入れる。
- 追加テーブル `tags(tag_id, name, color, description, created_at, updated_at)` と `conversation_tags(item_id, tag_id, added_at, PRIMARY KEY(item_id, tag_id))`。1会話に複数のタグを付けられる。タグ名は正規化（NFKC・前後空白除去・大文字小文字の同一視）して重複を防ぐ。
- グループとタグの違い：タグは会話に付ける自由な目印。グループは分析の対象集合で、版を持ち、実行時に所属を固定する（D5）。`rule` のグループは、D1〜D3の表とタグの表への条件として評価する。
- **UI**：ライブラリ画面で、グループとタグの作成・名前変更・削除、会話への付与・解除（複数会話の一括操作を含む）、グループの条件の作成と所属のプレビューを行えるようにする。会話一覧はタグ・グループで絞り込める。削除時は、使用している会話数と、過去の実行で固定済みの所属は変わらないことを表示する。UIはリポジトリ直下の `DESIGN.md` の該当節に従い、画面操作で確認する。
- 既存の `library_groups`（1会話1グループ）は残す。新しいグループと名前が重なって紛らわしいため、UI上の呼び方（例：既存を「フォルダー」と表示）を画面設計時に確認する。`comparison_group` は従来の比較キーとして読み続ける。

### D5 処理ごとの対象集合の固定

- 会話をまたぐ分析の実行時に、対象のグループIDと版、確定した所属一覧とそのhash、グループ化に使うキーとキー定義の版を、計画（PlanEnvelope）または実行のparametersへ固定する。
- `rule` のグループも実行時点の所属を確定して保存する。後で条件や所属が変わっても、過去の結果の対象集合と分母は変わらない。
- グループ化に使ったキーごとに、各会話の属性値とタグも確定して記録し、hashを取る。キー定義の版だけでは、値が後で変わった時に過去の分母を再現できないため。
- 既存の `analysis_run_members` には確定した所属をそのまま記録する。
- **古い扱い**：`conversation_attributes`・`conversation_tags`・`data_group_members` が変わったら、その会話を含む会話横断の保存結果を古い扱いにする。
  - `analysis_run_members` を通すトリガーで行い、既存の `analysis_store_member_changed` と同じ形にする。
  - 会話1件の分析の入力hash（`archive_source_stamp`）には含めない。会話1件の分析は属性を使わないため。属性を使う手法を会話1件の分析へ入れる時点で、入力hashへ加える。

### D6 初回展開と整合検査

- DB初期化時に、既存の全会話についてD1・D2・`speaker_attributes` を展開する。展開は何度実行しても同じ結果になり、元のJSONを変更しない。展開の版を `application_metadata` に記録し、版が同じなら次の起動では再実行しない。
- 表とJSONの一致を確認する整合検査を、既存の診断経路へ追加する。
- テスト：全書込経路（取込・編集保存・話者特定・台帳取込）の後に表とJSONが一致すること、不正JSONでも元の保存が成功すること、グループの所属と固定した対象集合が後の変更で変わらないこと。

### D7 基本情報（作成日・動画の長さ・保存場所など）の記録

- 追加テーブル `media_assets(item_id, role, path, original_filename, bytes, file_modified_at, media_created_at, imported_at, duration_seconds, container, video_codec, width, height, fps, audio_codec, sample_rate, channels, probe_tool_version, probe_json, probed_at, path_checked_at, path_exists, PRIMARY KEY(item_id, role))`。`role` は元ファイル・アプリ保存版などの区別。
- 日時は3種類を分ける：収録日時（メディアのメタデータ）、ファイルの更新日時、アプリへの取込日時。
- 取込・メディア保存の完了時に `ffprobe` で記録する。`ffprobe` の呼出しは、`services/outputs.py` の既存の処理（収録日時・映像情報の取得）を拡張して使う。
- 既存の会話の一括記録は、DB初期化では行わない。起動後に1回だけ動く処理として実行し、進捗と失敗を診断に出す（Colab・Drive上で起動を遅らせないため）。メディアは読むだけで変更しない。
- `ffprobe` がない、ファイルが見つからない、値が取れない場合は、0や空ではなく「不明」とその理由を記録する。
- 保存場所は記録時と表示時に存在を確認し、移動・削除されていれば「見つからない」と表示する。
- メディアの長さと文字起こしの範囲（最後の発話の終了時刻）は別の値として扱う。
- UI：会話の詳細画面に基本情報を表示する。一覧で収録日・長さを並べ替え・絞り込みに使えるようにする。

### D8 会話の削除とゴミ箱（Q12）

- 会話の削除で退避・復元されるのは、`services/library_trash.py` の `ITEM_TABLES` にある5表だけ。新しい表は含まれない。
- 会話を削除したら、同じトランザクションで、新しい表の会話単位の行も消す。対象：D1〜D4・D7・C1・F2（`conversation_speakers`・`conversation_segments`・`conversation_attributes`・`conversation_tags`・`data_group_members`・`media_assets`・`segment_embeddings`・`segment_labels`）。
- ゴミ箱から復元すると、D1・D2は挿入トリガーで作り直される。ほかの行は戻らない。試験用データだけのため、これを許容する（第1節）。
- 例外として、系列Iの起点・差分記録（`transcript_change_bases`・`transcript_changes` と、`change_log` の会話単位の行）はゴミ箱の対象に加え、復元で戻す。`change_log` は会話キーの抽出条件も対応させる（I4）。
- 保存パッケージ版2が消えた行を参照する場合の表示は、[[40-Design/10-Analysis/analysis-reuse-snapshot-package-plan#4. 計画3：保存パッケージ版2の読み手と検証|別計画の計画3]]に従う。
- 実データを入れる前に、属性・タグ・所属を `ITEM_TABLES` に加えて復元で戻すかを見直す。
- テスト：削除で新しい表の行が残らない。復元でD1・D2が作り直される。削除が新しい表の有無に関係なく成功する。

## 7. 系列E：エージェントへ渡すコンテキストの整形

DBにJSONで保存することはコンテキストの量を決めない。量を決めるのは、Handlerが対象範囲と根拠の発話を選んでエージェントへ渡す前の整形である。E1〜E4で整形の無駄を減らし、E5〜E8で対象範囲をアウトライン優先にする。E9〜E12は、案Aの手法別入力契約で他担当の先行所見を反例点検へ渡す実施計画。既存のhash置換・モデル予算の検査は再利用する。原文の区間分割はE6で行い、先行結果と原文を合わせた追加レビューが予算を超える場合は、E10の規則に従い送信前に停止する。関連：[[40-Design/20-Knowledge/model-context-and-work-memory-plan/00-Index|モデルの文脈と作業メモリーの計画]]。

### 計測（2026-10-11）

利用者の会話1件（323発話）を `intfloat/multilingual-e5-small` のトークナイザーで数えた目安。本文は表示していない。

| 渡し方 | トークン数 | 本文だけとの比 |
| --- | --- | --- |
| 本文だけ（下限） | 6,597 | 1.0倍 |
| 10項目のオブジェクト（`initial_label_definitions_version` 未設定時） | 79,514 | 12.1倍 |
| 6項目のオブジェクト（現在の絞込み） | 36,734 | 5.6倍 |
| 6項目の列形式 | 26,055 | 4.0倍 |
| 列形式＋短い参照ID＋話者記号 | 12,926 | 2.0倍 |

原因は、毎行に入るhashのID（`ev_`＋16進24桁、71文字の `dataset_version`・`source_hash`）と、毎行繰り返されるキー名。10項目の形では同じIDが `id` と `evidence_id` に2回入る。

### E1 渡す項目を常に絞る

- 根拠の行は、設定に関係なく `evidence_id / utterance_id / text / speaker / start / end` だけにする。
  - やめるのは、`analysis_orchestration.py` で `initial_label_definitions_version` によって根拠の行の項目を絞る分岐だけ。
  - 同じ設定値によるほかの分岐（ラベル目録・ラベル項目の絞込み・初回ルーティングなど）は変えない。
- 行ごとのhash・版は固定スナップショットに残っており、エージェントには渡さない。

### E2 列形式で渡す

- `raw_evidence` と `_source_evidence` を、先頭に列名と `dataset_version` を1回だけ書いた列形式で渡す。
- 整形はHandler側の純粋関数にし、`model_context.py` の既存の `reference_messages` の出力として組み込む。

### E3 短い参照IDと対応表

- 根拠1行に短い参照を1つ（`e1`, `e2`…）付ける。対応表は、参照→（`evidence_id`, `utterance_id`）。話者は記号（`S1`…）、時刻は小数1桁にする。
- 同じ対応表を、モデルへ渡す文脈の中の根拠ID・発話IDすべてに使い、2種類のIDを混ぜない。対象：
  - `raw_evidence` と `_source_evidence`
  - `coverage.evidence_index`
  - scope内の根拠ID一覧（`owned_evidence_ids` など）
  - 前の結果・指摘・初期報告の `evidence_ids`
  - 発話IDをキーにしたラベル
- Handlerは対応表とそのhashを、実行記録（context manifest）に保存する。
- モデルの出力に含まれる参照は、意味検証の前にHandlerが元のIDへ戻す。対応表にない参照は、既存の根拠検証と同じ `evidence_missing` として拒否する。研究上の主張は従来どおり発話IDへ戻れる。

- 渡す形式とエージェントへの指示を更新し、`ADAPTER_VERSION`（`services/analysis_orchestration_adapters.py`）を上げる。実行中の自律分析は既存の版確認で止まり、新しい形式は新規の実行から適用する。

### E5 アウトライン優先で分析区間を確定する（Q21）

- **対象**：専門エージェントの初回分析と追加分析の原文入力。`analysis_orchestration.py` の `_initial_specialist_intents`・`_context`、`ai_finishing.create_outline`、`services/model_context.py` と既存の入力固定経路を再利用する。独立した分析Runtimeや保存先は増やさない。
- **現状（基点 `47ecd0a`）**：初回は発話数・本文文字数で分割し、アウトラインの議題境界を使っていない。現行画面は24発話・6,000文字を指定し、クラウド担当を含む場合は分割を無効にするため、先頭の上限内しか渡らない経路がある。新しい区間選択は送信先にかかわらず適用する。
- **準備の順序**：固定した入力版に対応する既存アウトラインを再利用 → 粗すぎる議題を小議題へ細分化 → 未作成なら作成を試みる → 作成できなかった範囲を時間分割。アウトライン作成・細分化は同じ原文の範囲だけを読み、生成回数・費用を既存の予算と取消処理で管理する。AIが使えない・予算が足りない・形式検証に失敗した場合は、その範囲を時間分割へ回す。取消はそのまま停止し、別処理を続けない。
- **発話の所属と引用を分ける**：現在の `sections[].segment_ids` は `bullet_evidence` の引用IDの和集合であり、議題内の全発話ではない。`start/end` も引用発話から作った時刻なので、完全な区間境界とみなさない。別に分析区間と、その区間に属する全発話の一覧を確定し、引用されない応答・否定・少数意見も含める。画面用の `session_outline` はIDを最大50件に絞るため、入力の正本に使わない。
- **境界の検証**：議題の境界は固定入力の発話ID・順序に戻して検査し、区間は連続する発話列にする。離れた時刻に同じ話題が再登場した場合は別区間として持ち、関連する議題として参照できるようにする。重複する候補境界は決定的な規則で正規化し、解決できない範囲は時間分割へ回す。
- **未割当の補完**：アウトラインが一部だけ存在する場合も、除外指定を除く全対象発話を走査し、未割当の連続範囲を時間分割する。時間幅の初期値は300秒とし、既存の分析設定インターフェースから渡して実行時に固定する。発話の開始時刻で所属を決め、発話本文の途中では切らない。時刻の欠落・不正を0秒で補わず、その範囲を処理不可として理由を記録し、確認待ちにする。
- **分担**：LLMは議題候補と細分化候補を出す。所属の全件検査・重複検査・時間分割・実行可否はHandlerが事実を集め、分析コアの規則で判断する。LLMを完了判断へ入れないという系列Aの原則を維持する。

### E6 区間ごとの入力と統合

- 解釈・独立検証・批判の初回担当は、同じ区間の全対象原文をそれぞれ独立に読む。入力に区間ID・親議題ID・開始終了時刻・担当発話IDを加え、研究質問と既存の役割別指示を渡す。
- 前後各1発話を参照用文脈として添え、`owned_evidence_ids` と `boundary_evidence_ids` を区別する。区間の分母・処理済み件数・ラベル付与には担当発話だけを数える。文脈発話を主張の根拠に使った場合も、その発話の担当区間は変えず、統合時に根拠IDで照合する。
- 独立検証には原文・対象範囲・中立な区間識別情報を渡し、AIアウトラインの要点・結論や他担当の所見を渡さない。解釈役へ渡す議題名・要点もAI下書きの補助情報とし、主張の根拠は原文の発話IDに限定する。
- 議題が入力上限を超える場合は、親議題を保持して小議題、次いで時間と発話境界で子区間へ分割する。モデル予算が不足する場合も残りを別タスクへ回し、本文の切詰めや `reduce_context` の半減で担当発話を消さない。1発話だけでも上限を超える場合は未処理として止め、全文を読んだ扱いにしない。
- 追加分析も確定した区間へ結び、原文の読取を対象区間へ限定する。複数区間の比較は対象区間IDを明示した比較依頼とし、必要な区間別結果・根拠を予算内で段階的に参照する。依頼に区間指定がない場合も、全件の先頭だけを渡す処理に戻さず、目的に対応する区間を確定してから実行する。他担当の先行所見を追加レビューへ渡す契約はE9〜E12の案Aで定める。
- 専門オーケストレータが子区間 → 議題の所見・限界をまとめ、Coreが議題間を統合する。ラベル・尺度の設計では各区間の要件を集約し、局所の定義を会話全体の確定尺度と混同しない。会話全体の参加量・時間推移などは全件集計を維持し、区間別集計には区間ID・対象集合・分母を付ける。

### E7 区間の版・保存・再開

- Handlerが区間一覧と所属を一度確定し、既存の実行記録へ固定する。区間ID、親議題ID、分割方式（既存・生成・細分化・時間）、分割規則の版、時間幅、入力版、アウトラインの版・hash、担当発話ID・参照文脈ID、生成run ID・hashを追跡可能にする。要点の引用IDとは別に所属一覧のhashを持つ。
- AIによる作成・細分化の結果は実行別のAI下書きとして保存する。研究者が持つアウトラインや本文を直接上書きしない。系列F・Iの実行別参照と既存の履歴保存経路へ接続し、固定した入力スナップショットを後から書き換えない。
- 各タスクのcontext manifestへ区間と実際の提供発話IDを残す。再開時は保存した区間・所属と完了結果を使い、アウトラインを再生成しない。入力・アウトライン・分割規則・時間幅が変われば再利用条件が変わり、新規実行として扱う。別計画のstep再利用とスナップショット版2でも、この来歴と所属一覧を保持する。
- 全対象発話の割当状況と、役割別の処理済み・未処理区間を分ける。予算切れ・作成失敗・確認待ち・取消は成功に数えず、部分結果には対象区間と未処理範囲を残す。E4の指示版更新へ含め、旧方式の実行を新しい区間方式の途中から再開しない。

### E8 受入条件と検証

- 一時DB・架空会話で、アウトラインの再利用、粗い議題の細分化、未作成時の生成、生成失敗時の時間分割、部分アウトラインの未割当補完を確認する。生成失敗と利用者取消の扱いを分ける。
- 除外指定以外の全対象発話が、親議題と子区間の階層を考慮した末端区間のいずれか1つに所属する。引用IDにない応答も落ちず、同名議題の再登場・境界時刻ぴったりの発話・重なり発話・長い発話・空区間・時刻不正で、所属の欠落や二重計上がない。
- 予算検査の前後で担当発話の集合が保存される。上限超過時は子区間または明示した未処理範囲が残る。全担当ローカル・クラウド混在のモック送信で、同じ区間割当が使われ、先頭だけの処理へ戻らない。送信方針・同意条件は維持する。
- 独立検証へAI要約・他担当の結論が混入しない。前後文脈が分母へ混ざらず、全件統計の対象集合と結果が変更前と一致する。区間別結果から統合見解まで入力版・発話ID・区間IDへ戻れる。
- 中断後の明示再開で、区間の再生成・完了タスクの重複実行がなく、未処理区間を成功扱いにしない。入力・アウトライン・分割設定の変更で古い結果を再利用しない。
- 実装時の関連試験は `test_ai_finishing`・`test_analysis_orchestration`・`test_model_context`・`test_specialist_orchestration`・`test_referenced_context` と隣接統合テストを対象にする。共有入力と保存来歴を変えるため段階1Cの終わりに全体テストも行う。実モデルの品質・300秒という粒度の妥当性は未検証であり、利用者が実行を指示した際に、議題のつながり・少数意見・処理漏れ・費用を確認する。

### E9 案A：手法別の入力契約で先行所見を反例点検へ渡す（Q22）

2026-10-12、利用者の指示で案Aを採用した。以下は実装予定の契約であり、現行の動作ではない。初期導入は「同じrunの先行所見1件を、同じ区間の原文と照合して反例・不足を点検する」用途に限定する。

#### 対象・前提・完了条件

- **確認済みの不足**：通常の追加分析では解釈役の `results` を空にし、`dependencies` は実行順のみを制御する。既存の `clarification_target` は説明専用で `execution_allowed=false`。この経路を維持し、追加レビューを別の入力・出力契約として実装する。
- **実装前提**：E5〜E8の区間契約・発話の所属・文脈用発話の区別・入力manifestを先に実装し、関連試験を通す。未実装の区間IDを有効と見なす暫定経路は作らない。アウトラインの再利用・生成・細分化と、作れない部分の時間分割（初期値300秒）を使う。
- **生成元と受取役**：初期対象は解釈役Aが作った、空でない根拠付き `claims` を持つ所見。受取側は解釈役Bの追加レビューとする。各分野の専門オーケストレータが必要ならBへ依頼できる。分類・尺度・数量表・批判のissues・分野別統合報告を汎用入力へ広げるのは次段階。
- **入力可能条件**：同じrun、生成タスク完了、結果 `validation_status=valid`、隔離なし、入力版・区間版・必要な注釈/手法版の整合、保存本文と `raw_hash` の一致、提示済み候補であること。`valid` は形式検証の合格であり研究上の採用ではない。下書きや研究上却下された所見も、状態を明記して点検対象にできる。原文や確定ラベルの正本にはしない。
- **入力数と制限**：追加依頼1件につき先行結果1件。各分野・各回の追加依頼は既存の1件上限を維持する。完了した結果を参照し、未生成task IDの遅延束縛、複数上流、別run、レビュー結果の連鎖入力は初期導入に含めない。
- **完了条件**：AのR1を対象に、受取側の判断からBへR1と原文が届き、各主張への判定R2が保存され、専門報告とCoreから原文・R1・R2の系譜と限界を追跡できる。判断保存だけ、参照パスだけ、`used` の申告だけでは完了にしない。

#### 各専門オーケストレータによる利用判断

| 判断 | 必須の記録 | 実行への扱い |
| --- | --- | --- |
| `use`（使う） | 理由、用途 `counterexample_review`、対象結果、対象区間、期待する出力 | 正式依頼と結び付け、Handlerの検査に合格した1件だけを渡す |
| `skip`（使わない） | この用途で使わない理由 | 本文をBへ渡さず、元の成果物を保存する |
| `defer`（保留） | 理由、不足、解除条件、次に確認する作業 | 本文をBへ渡さず、未解決として専門報告・Coreへ残す |

- 判断単位は「受取分野・用途・区間・候補の版」。同じR1を分野Xが `use`、分野Yが `skip` としてよく、他分野の記録を上書きしない。既存の `adopt / reject / defer` は研究上の採否であり、入力選択の三択とは別に保持する。
- Handlerが、役割・送信方針・入力可能条件を満たす候補索引を各分野へ提示する。生成担当、result ID/hash、入力・区間・定義版、元タスクの対象範囲、実配送範囲、網羅性、採否状態を含める。他分野の元結果でも許可された所見は候補にできるが、既存の担当分野別 `results` の採否対象を増やさず、候補欄を別にする。
- 候補索引の閲覧と本文の精査を区別する。判断は、用途と範囲から「反例点検にかける価値があるか」を選ぶものであり、索引だけで所見の正しさを承認しない。本文を調べる仕事はBに渡す。
- 候補は予算に合わせて安定順でページ化し、提示ID集合と未提示件数をmanifestへ残す。提示候補にはそれぞれ三択と短い理由を必須にし、未提示候補を `skip` と推定しない。全候補を一度に評価する常駐ループは作らない。
- `use` は1判断につき最大1件で、同じ判断の正式依頼に必ず結び付ける。別の通常分析を発注する場合は `use` を宣言しない。既存の予算・重要度・既発注判定などで発行されなかった場合は、意図した `use` と実際の未発行理由を別記録にし、配送済みと扱わない。
- `defer` は既存の次回判断時に未解除一覧として再提示する。解除条件を満たす新情報がなければ再発注しない。自動監視・自動解除は追加せず、上限に達した保留は未解決として終了できる。変更は前のdecision IDを参照した追記とし、進行中タスクの入力を差し替えない。
- `verification` への成果物投入は、登録時と入力作成時の両方で拒否する。盲検用エージェントとは別のBが点検し、その結果を独立した盲検検証とは呼ばない。

#### 追加する契約と記録先

名称は実装用の予定名。Schema、役割指示、保存JSON、検証コードを一緒に更新する。

`claim_id` は現行CLAIMにも存在する。result ID/hashとの組合せで識別し、対象内の欠落・重複を登録前に拒否する。旧結果にIDや来歴が不足する場合は、現在データから推測して補わず閲覧のみを許す。DBは既存JSONへ版付きで追加し、表・既存カラムの削除/改名/型変更はしない。新しい共有ファイルやVaultへの自動公開経路は作らない。

### E10 案A：Handlerの既存処理境界へ接続する

フックの責務は、Handlerから必ず直接呼ぶ内部関数で実装する。汎用のフック登録基盤、外部コマンド、通知購読を正しさの前提にしない。関数名は仮称。分析コアは事実から可否を判断し、HandlerがDB取得・記録・送信を行う。

| 接続先 | 内部処理 | 検査・保存する内容 |
| --- | --- | --- |
| `_apply_specialist_review` / `_register` | `resolve_review_input` | 提示候補と判断、正式依頼との一致、完了状態、run/版/hash/区間、役割、claim ID。生成taskを依存に加え、入力束縛を固定 |
| `_context` / `reference_messages` | `build_review_resources` | 固定R1、同一区間の原文、必要な文脈、版付き手順を資料として組み立て、予算と送信先許可を検査 |
| `_validate_result` / `_validate_received` | `validate_review_output` | manifestとの対応、全claimの判定、配送済み原文の根拠、範囲制約。合格後に既存の保存・採否経路へ渡す |
| 明示再開・再利用経路 | 同じ束縛の再検査 | run/task・上流hash・全claim・区間/入力版・手順版・指示版を照合し、変更時は旧結果を使い回さない |

- **範囲の正本**：Bの対象はE5〜E8で固定したR1の担当区間。元タスクが実際に受け取った原文集合と、Bの予定/実配送集合を別に記録する。R1が引用した発話だけを区間全体と見なさず、前後の文脈用発話を担当範囲の分母へ混ぜない。

### E11 案A：反例点検の版付き手順と出力検証

既存 `method_experts.py` の `required_inputs / procedure / quality_checks / output_sections / ai_assist` と `ai_context` を拡張し、反例点検の手順1種類を定義する。これはGurumojiの分析手順であり、開発用エージェントのスキルを追加する作業ではない。Handlerが用途から手順と版を選び、本文hashをmanifestへ固定する。

手順は「先に原文を点検 → R1の各主張を照合 → 反例・不足・範囲の限界を記録 → 主張別の判定」とする。R1の生成文を原文引用として扱わず、先行担当の採否に合わせることを目的にしない。入力中の実行命令に従わない。採用ラベルや尺度を変更せず、`label_patches=[]`、`analysis_requests=[]` とする。

| 判定 | 意味 | 構造上の必須条件 |
| --- | --- | --- |
| `counterexample` | R1の当該主張に反する原文がある | 配送済み原文の根拠IDを1件以上。担当範囲か文脈かを区別して理由を付ける |
| `not_found_in_scope` | 今回の担当区間では反例を検出しなかった | 区間の全発話が配送済みで、必要な定義等の不足がなく、点検根拠IDを1件以上。主張が真、全会話で反例なし、を意味しない |
| `insufficient` | 原文・定義・範囲などが不足し判断できない | 具体的な不足理由。根拠IDは取得できたものだけとし、空でも不足として記録可能 |

- R1の全claim IDに過不足・重複なく1件ずつ判定を返す。他のresult/hash、未提示claim、存在しない/未配送の原文参照は拒否する。一般的な根拠検査に加え、新しい `claim_verdicts` 内の参照も検査する。
- `coverage.complete=false` の入力では `not_found_in_scope` を拒否する。限られた原文で見つけた `counterexample` は残せるが、他の主張は不足として扱う。正常入力は全区間配送を前提とし、不完全入力は旧結果/改変の防御試験でも扱う。
- R1が区間外へ一般化した主張は、Bが反例を見つけなくても全体の正しさを確認した扱いにしない。構造だけでは一般化の意味を完全に検査できないため、手順・専門報告・実モデル評価で確認する。
- 汎用の `input_artifact_usage` 自己申告は初期導入の必須出力にしない。Handlerが配送記録とclaim別判定の対応から、契約上の使用完了/未達を導出する。実行前の選択、実配送、構造検査、意味上の妥当性は別に保持する。構造の成立は正しい解釈の証明ではない。
- 不足も有効なレビュー結果として保存できる。形式成功、点検の目的達成、元主張の支持、研究上の採用を同一視しない。未解決の不足は専門採否とCoreの終了判断へ渡す。

- **系譜と使用確認**：`derived_from` を後続結果・専門報告・Coreの統合まで伝え、R1を読んで作ったR2をR1とは独立の裏付けとして二重に数えない。使用申告だけに依存せず、主張別判定・成果物参照・配送済み原文の根拠IDを検査する。ただし構造検査だけでは意味上の適切さを証明できず、誤った先行所見を含む架空データで品質評価する。
- **フック・スキル**：処理境界に直接呼ぶ内部関数と、まず1種類の版付き分析手順で始める案が提示された。E10も汎用の外部スクリプト機構を予定していないため、争点はフックの呼称より実装範囲と間接層の大きさ。CLI設定のフックや開発用スキルを追加する提案ではない。
- **利用判断への留保**：Claudeは判断量を減らすため、未選択をHandlerが記録し、全候補の `skip` 理由を任意にする案も提示した。これは利用者の「使う・使わない・保留を各担当が決める」案とは異なる選択肢。未選択を `skip` と同一視せず、現時点ではE9の三択と理由の方針を維持する。

コード照合による補正：`label_frequency` は `services/analysis_orchestration_methods.py` で発話IDによる部分範囲の集計に対応済み。全範囲専用なのは現行の `participation / conversation_dynamics` であり、Claudeの記述をそのまま採用しない。また標準の専門オーケストレータ構成では、個別結果の採否は専門側の責務であり、Coreの `result_assessments` はSchemaと検証で禁止されている。`task_instruction` と `resource_data` はどちらもAPIのuserロールなので、資料分離の不足をsystem権限への昇格と断定しない。レビューのこれらの説明は補正する。

レビュー時点では方針は未確定だった。その後、利用者の「Aでプランを作成、テスト方法も一緒に」という指示で、案Aの最小導入範囲とテスト方法をE9〜E12・Q22へ反映した。三択判断とQ21のアウトライン単位入力を維持し、汎用化は後続へ分ける。アプリ実装・実データ操作・機能試験は今回行っていない。

### 方針（Q10・Q11）

- **分析ごとに、出力の形に合った形式で保存する。** 手法の出力を次の8つの形に分け、形ごとに保存先・形式・鍵を決める。

- **固定性は保つ。** 保存した分析が参照する行は、版ごとに追記だけで残し、上書き・削除しない。参照されていない行だけを整理対象にする。
- 保存形式の版を上げ、旧形式の保存結果はそのまま読む。利用者向けのCSV書出しは維持する。

  - 参照先の照合と、欠落時の表示
  - 派生データの作り直し

### 確認

- 架空の3会話で、保存量を変更前後で比較する。
- 版2で保存した分析から作った表・CSVが、同じ入力の版1の結果と値で一致する。

## 10. 系列H：新しい分析手法

系列C・D・Fの土台の上に、LLMを使わず同じ入力から同じ結果を出す手法を加える。各手法は手法の登録規約（[[40-Design/50-Governance/method-rules/00-Index|method-rules]]）に従って登録し、手法カードに適用条件・注意を書く。結果は記述的な指標であり、発話を独立した標本として検定しない。グラフ計算は導入済みの `networkx`（3.6.1、PyTorchの依存として導入済み）を使い、依存設定に明記する。

### H1 応答関係ネットワーク

- 入力：既存の会話の時間構造（`conversation_dynamics`）の話者交替（`transitions`）と、D1・D2の表。
- 出力：話者を節点、話者交替を重み付きの辺とするグラフ（F5）。指標は、話者ごとの発話の受け渡し回数（入・出）、相互性、交替の偏り、中心性（F6）。
- 適用条件：話者2人以上、話者交替が一定数以上（手法カードで固定）。満たさない場合は適用外として理由を返す。

### H2 共起ネットワークの構造

- 入力：既存の共起（`cooccurrence`）の語のペアと、F1の形態素。
- 出力：語を節点、共起を辺とするグラフ（F5）。語のまとまり（コミュニティ）と中心となる語（F6）。
- まとまりの検出は、同じ入力で同じ結果になる方法（乱数の種を固定するか、決定的な方法）にし、方法と設定を結果に記録する。

### H3 コーディングの一貫性チェック

- 入力：研究者の手動コード（`analysis_annotations_json`）と、埋め込み標準 v1 のベクトル（C1・C2）。
- 出力：コードごとの意味のまとまり具合（F6）と、「自分のコードより他のコードに意味が近い発話」「どのコードからも遠い発話」の要確認の一覧（F2、出所 `rule`）。
- 研究者のコードを自動で変更しない。一覧は確認の手がかりであり、コードの正誤の判定ではないことを画面に示す。
- 適用条件：コードごとに一定数以上の発話（手法カードで固定）。標準以外のベクトルしかない場合は再計算を案内する。

### 確認

- 架空データで、既知の構造（話者交替の偏り、語のまとまり、意図的に紛れ込ませたコード）を指標と一覧が再現する。
- 同じ入力で2回実行して結果が一致する。適用条件を満たさない入力で適用外になる。
- 手法の画面で結果と注意が表示され、元の発話へ戻れることを画面操作で確認する。

## 11. 系列I：Rawと差分による管理（Q17）

2026-10-12の利用者の指示：今後も、Rawデータ（文字起こし本体、AI仕上げ前）と、処理後の差分データで管理する。

### 原則

- **Raw**：音声認識と話者分離の出力を、AI仕上げの前に固定したもの（`original_segments_json`）。取込後は変更しない。
- **処理後のデータ**：Rawまたは直前の状態に対する差分として追記し、上書き・削除しない。差分には次を持たせる。
  - 順番
  - 出所（`ai / researcher / rule`）
  - 処理の種類と版
  - 適用前後のhash
  - 時刻
- **現在の値**（`segments_json` など）：Rawと差分から作り直せる写しとして扱う。今の読込経路は変えない。
- **処理結果**（発話分類・話題・音声感情・ベクトル・形態素など）：差分ではなく、版ごとに追記する（系列C・F）。
  - 規則で決まる結果（形態素など）：本文hashと手法の版を鍵にする。
  - AIの推論結果：再実行で変わり得るため、実行IDも鍵に加える（F2）。

### 現状（基点 `47ecd0a`）

| データ | 今の持ち方 | 原則との差 |
| --- | --- | --- |
| Raw | 取込時に、AI仕上げ前の出力を `original_segments_json` に固定する。upsertでも上書きしない。状態は `initial_import`。古い移行データは `migrated_current_snapshot` で、本当のRawではない | 合っている |
| AI仕上げ | 仕上げ後の全体で `segments_json` を上書きする。変更点は、保存分析を作る時にRawと現在を比べて（`finishing_changes`）求めるだけ | 差分として記録していない |
| 手動編集・話者・会話情報 | `segments_json`・`speaker_profiles_json`・`speaker_names_json`・`session_profile_json` を上書きする。保存ごとの全文の写しを `transcript_versions` に残す。写しを書くのは、`library_store` の保存の中の `transcript_preparation.capture` だけ | 差分ではなく全文の写し |
| 注釈・分析設定 | `analysis_annotations_json`・`analysis_config_json` を上書きする（`services/analysis_annotations.py`） | 履歴なし |
| 話者台帳・定義 | 上書きする。台帳は版番号だけを持つ | 履歴なし |

### I1 文字起こしの差分記録

- 追加テーブル `transcript_changes(item_id, seq, version, origin, process, process_version, base_hash, after_hash, ops_json, created_at, PRIMARY KEY(item_id, seq))`。
  - `seq`：差分の順番。会話内で一意。
  - `version`：既存の `input_version` と共通の版番号。版は保存1回（`transcript_preparation.capture` の1回の呼出し）ごとに1つ振る。1回の保存で複数の差分ができる場合は、同じ版を共有する。
  - 例：取込時の取込メタデータとAI仕上げ（取込中に行う表記ゆれの統一を含む）の差分は、どれも版1（`initial_import`）になる。今の「取込で1版」と同じ見え方を保つ。
  - 以後は、編集の保存・取込後のAI仕上げ・「表記ゆれを統一」ボタンの実行が、それぞれ次の版になる。
  - `ops_json`：発話IDごとの操作（本文・話者・時刻の変更、追加、削除）、並び順の変更、話者プロフィール・話者名・会話情報のキーごとの変更。
  - `base_hash`・`after_hash`：適用前後の状態（`transcript_preparation.source` のhash）。
- **復元の起点**：`original_segments_json` を発話に持ち、話者プロフィール・話者名・会話情報を空の辞書とした状態を起点とする。起点の形式版・hash・Rawの状態・旧版との接続情報を、追加の会話単位の表 `transcript_change_bases` に固定する。新規取込では、AI仕上げ前のメタデータを `origin: rule / process: import_metadata` の差分で先に記録し、その後にI2のAI変更を書く。空のメタデータを実際の入力値だったと扱わない。
- **既存会話の切替**：既存の `transcript_versions` と現在値を読取専用で照合するdry runを先に行う。起点から切替時点の `source` 全体へ達する接続差分を1回だけ記録し、既存の本文・話者情報・会話情報を保持する。接続差分は `origin: rule / process: legacy_bridge` とし、過去の変更の出所は不明と記録する。AIや研究者の変更に分類せず、旧履歴も削除・改変しない。Rawが欠落・代替状態ならその状態を残し、真のRawがあると表示しない。
- 切替は会話単位の同じトランザクションで行い、接続差分を復元したhashが現在値と一致した場合だけ確定する。再実行で起点・接続差分を重複作成しない。失敗時はロールバックし、その会話を旧履歴で読み続ける。追加バックアップを取らない試験データの前提（第1節）は維持する。
- 書くのは `transcript_preparation.capture` の1か所（今、全文の写しを書いている場所）。同じトランザクションで、直前の状態との差分を書く。
- `transcript_versions` には新しい行を書かず、既存の行は読込用に残す。
- **版番号の接続**：切替時点が旧履歴の最終版とhash一致する場合、接続差分をその版へ対応付け、版一覧では重複表示しない。不一致または旧履歴がない場合は次の版を与える。以後の版は旧履歴と差分履歴を通じた最大版の次から採番する。起点は内部の復元用で、確認済みの版として新たに表示しない。
- **読み手を一本化**：`transcript_preparation` に旧全文版と差分版の共通の読取関数を置き、版一覧・指定版の内容・現在版・既知発話IDをここから取得する。`view()` の `versions` と `input_version`、版の書出し `web/export_routes.py`、既知IDの収集、分析・Vault公開が使う版情報を同じ変更で対応させる。現在hashに対応する記録がある場合だけ現在版を返し、不一致は未固定とする。GETで接続差分の作成や移行を行わない。
- Rawに差分を順に適用して作り直す関数を、純粋関数にする。整合検査（D6）で、作り直した値が `segments_json` などと一致することを確かめる。

### I2 AI仕上げを差分として記録

- 取込時、RawとI1の取込メタデータを固定した後に、AI仕上げを適用した結果を差分として書く。`origin: ai`、`process: ai_finishing` とし、仕上げの版・モデル・段階も記録する。手動編集はその後の差分（`origin: researcher`）になる。
- 取込後にAI仕上げをやり直す経路がある場合も、同じ形で書く。
- 保存分析のAI仕上げ変更記録（`ai_changes`）は、この差分から作る（F8と同じ中身）。
- 古い移行データ（`migrated_current_snapshot`）は、Rawが本当の原文ではないことを表示に残し、差分はその時点から始める。

### I3 研究者が入力するデータの変更記録

- 追加テーブル `change_log(entity, entity_id, seq, origin, ops_json, base_hash, after_hash, created_at, PRIMARY KEY(entity, entity_id, seq))`。
- 対象：
  - 注釈・コード（`analysis_annotations_json`）、分析設定（`analysis_config_json`）
  - 話者台帳（`speaker_registry`）、定義（`analysis_definitions`）
  - 系列Dの研究者入力（会話の属性、タグ、グループと所属、属性の定義）
  - 登録語・表記辞書（J5のDBの表）
- **I3a（段階1B）**：`change_log` の共通記録・復元機能と、登録語・表記辞書への接続を先に実装する。J5はこの完了後に実装する。**I3b（段階3）**で残りの対象へ接続する。
- 既存の各対象は初回切替時の値を、空の状態からの初期差分（`origin: rule`、過去の出所は不明）として1回記録し、それ以降の差分の起点にする。新規作成も初期値を記録する。過去に記録がない状態を復元できるとは扱わない。
- DB内の現在値は今の列・表のまま持ち、書込経路の同じトランザクションで差分を追記する。登録語・表記辞書もDBに置くため（J5）、同じトランザクションで確定できる。

### I4 ほかの系列との関係

- **D8**：`transcript_change_bases`・`transcript_changes` と、`change_log` の会話単位の行は、ゴミ箱の対象に加え、削除・復元で一緒に動かす。文字起こしの正本の一部のため。会話キーが `entity/entity_id` の `change_log` は、`item_id` を前提にする既存の `ITEM_TABLES` 処理へ名前を加えるだけでは足りない。会話単位の抽出・削除・復元条件を明示し、他の対象の履歴を巻き込まない。
- **B2**：入力がすべてRaw＋差分になった後は、入力スナップショットを「Rawのhash＋差分の番号」で表せる見込みがある。今は写しを維持し、I1〜I3の後に別に判断する。
- **変えないもの**：入力hash（`archive_source_stamp`）、古い扱いのトリガー、系列Dのトリガー。どれも現在の値の列を見続けるため。

### 確認

- すべての書込経路（取込・編集保存・話者の特定・AI仕上げ・注釈の保存・台帳の保存）の後で、Raw＋差分から作り直した値が現在の値と一致する。
- Rawが取込後に変わらない（upsert・編集・AI仕上げの後もhashが同じ）。
- 既存会話（編集済み・話者情報あり・旧版あり・Raw欠落／代替）を切り替え、切替前後の現在値とhashが一致する。dry runは書き込まず、切替の再実行で重複がなく、途中の失敗は会話単位で戻る。
- 版の書出しが、既存の全文の版と、差分から作った版の両方を出す。
- 旧版のID・hash・内容が変わらず、新しい版が重複せず増える。編集後の `view().input_version`、書出し、分析・Vault公開の版情報が一致する。未記録の現在値は未固定となり、GETでは記録を増やさない。
- 削除→復元で差分記録が戻る。
- 起点と会話単位の `change_log` も削除→復元で戻り、他の会話・辞書・話者台帳の履歴に影響しない。I3の既存対象も初期差分＋後続差分から現在値を復元できる。
- 保存時間を変更前後で比べる。

## 12. 系列J：AI仕上げでの表記ゆれの統一（Q18）

2026-10-12の利用者の指示：AI仕上げで表記ゆれを探し、見つけた場合は適切な単語を検索して置換する機能を加える。

### 現状（基点 `47ecd0a`）

- **会話全体の統一を見ていない**：AI仕上げの再校正（`ai_finishing.clean_transcript`）は、最大160分割片・約1万文字ずつ処理し、前後2件とアウトラインしか見ない。会話全体で表記が揃っているかは、どこでも確認していない。
- **正しい表記の手がかり**
  - アプリ全体の登録語（`custom_vocabulary.json`、最大100語）がある。ただしWhisperの初期プロンプトにしか使っていない。
  - 話者台帳に、氏名・所属・部署がある。
- **仕上げの経路**：文字起こし中の仕上げと、Obsidianの操作ノートからの仕上げの2つ。どちらも `run_full_cleanup` の同じ段階を通る（ARCH-07）。おすすめモードの修復も、その前に済んでから `run_full_cleanup` に入る。
- **読み**：形態素解析（SudachiPy・GiNZA、`research_analysis.py`）が読みを返す。

### J1 段階の追加

- `run_full_cleanup` の最後に「表記ゆれの統一」（`notation`）段階を加える。再校正・おすすめの修復のどちらの後でも、また両方の経路で、同じ処理を通す。
- AI仕上げの段階ごとの設定（`ai_efforts`）に `notation` を加え、`off` にできる。段階の記録（`finishing_stages`）に結果を残し、版は `NOTATION_VERSION`（`notation-1`）とする。
- すでに取り込んだ会話には、会話の詳細画面に「表記ゆれを統一」ボタンを置く。AI仕上げとは別の明示的な操作にする。送る前に、送信先と見込みのトークン数を表示する。

### J2 表記ゆれの検出（LLMを使わない）

- 形態素解析で語を取り出し、同じ語の書き分けと見なせる組（変種群）を作る。
  - **規則で確定する差**：全角・半角、長音の有無、中黒・空白、大文字・小文字（NFKCと既存の正規化で判定）。例：「ＡＩ／AI」「サーバー／サーバ」
  - **候補とする差**：読みと語彙素が同じで、ひらがな・カタカナ・漢字・英字の書き分けや送り仮名が違うもの。例：「打ち合わせ／打合せ」「グルモジ／ぐるもじ」
- 読みが同じでも、語彙素・品詞が違う語は群にしない。同音異義語（「機会／機械」など）を置換しないため。
- 研究者が手で直した箇所（系列Iの差分で出所が `researcher` のもの）は、群の出現箇所から除く。

### J3 適切な表記の検索

群ごとに、次の順に正しい表記を探す。最初に見つかったものを使い、出典を記録する。

1. 表記辞書（J5）で、研究者が確定した表記
2. 登録語（J5のDBの表）に一致する表記
3. 話者台帳の氏名・所属・部署
4. ライブラリのほかの会話で、研究者が確定した表記（系列Iの差分の履歴）
5. どれにもない場合だけ、LLMが会話の文脈から選ぶ
   - 送るのは、群の表記・出現数と、各表記の出現箇所の短い前後文だけ。会話全体は送らない。
   - LLMが選べるのは、群に含まれる表記と、1〜4の出典にある表記だけ。新しい表記を作った応答は採用しない。

外部のWeb検索は使わない（語が守秘情報を含み得るため）。

### J4 置換と記録

- 群ごとに、決めた表記へ一括で置換する。Rawは変えない。
- 置換は、系列Iの差分（`origin: ai`、`process: notation`、版、群ID、出典、理由）として記録する。I1・I2と辞書履歴のI3aを前提とし、差分が残らない暫定経路は作らない。
- 保存分析のAI仕上げ変更記録（`ai_changes`、F8）に、変更の種類 `notation` として出す。
- LLMだけで決めた群（J3の5）は置換したうえで「要確認」と表示する。

### J5 表記辞書と確認画面

- **登録語と表記辞書の正本をDBに置く（Q20）。**
  - 追加テーブル `vocabulary_terms(term, position, created_at, PRIMARY KEY(term))`：登録語（正しい表記）。
  - 追加テーブル `notation_variants(variant, canonical, created_at, PRIMARY KEY(variant))`：ゆれ→正しい表記。
  - 登録語・辞書の変更は、I3aの変更記録と同じトランザクションで確定する。ファイルとDBを同時に確定する必要がなくなるため、保留記録や中断時の復旧手順は作らない。
- **`custom_vocabulary.json` はWhisper用の写しにする。**
  - 形式は今の版1（`version: 1`・`terms`）のまま変えない。DBの確定後に、既存のファイルロックと `atomic_write_text` で書き直す。
  - Whisperの初期プロンプトと旧コードは、今までどおりこのファイルを読める。
- **保存窓口を一本化する。** 既存の `save_custom_vocabulary` をDBへ書く窓口に変える。登録語API・文字起こし開始時の登録語保存・確認画面の辞書登録を、すべてここに通す。
  - 登録語だけの更新では、表記辞書を変えない。
  - 登録語から外した語の辞書項目も暗黙には消さない。辞書の変更・削除は明示操作にする。
- **ファイルとDBの照合**：初回は、既存のファイルの登録語を、I3aの初期差分（`origin: rule`）としてDBへ取り込む。
  - 以後の起動時に写しとDBが違う場合（旧コードや手作業でファイルが書かれた場合）は、ファイルの内容を差分（`origin: rule`、`process: vocabulary_file_import`）として取り込んでから写しを書き直す。ファイル側の変更を黙って上書きしない。
- 登録語・辞書はDBにあるため、既存のデータのバックアップに含まれる。
- 確認画面（会話の詳細、AI仕上げの結果）には、群ごとに次を表示する。
  - 表示する内容：変種・出現数・決めた表記・出典
  - 操作：取り消し、別の表記への変更、辞書への登録
- 取消・変更は新しい差分（`origin: researcher`）として書く。辞書への登録・変更・削除は、系列I3aの変更記録に残す。

### 確認

- 架空データに意図して入れた表記ゆれ（全角半角、長音、送り仮名、カナと英字、人名）が群になり、辞書・登録語・台帳の表記へ置換される。
- 同音異義語は群にならない。研究者が直した箇所は変わらない。
- LLMが群や出典にない表記を返したら採用しない。送信内容が、群と短い前後文だけである。
- `off` のときは段階が動かない。文字起こし中とObsidianの2経路で、同じ入力から同じ結果になる（LLMの応答はモックで固定）。
- 置換の差分から、Raw＋差分で作り直せる。取消しが研究者の差分として残る。
- 確認画面での取消・変更・辞書登録を、画面操作で確かめる。
- 既存のファイルの登録語が、初回にDBへ取り込まれる。登録語の更新や文字起こしの開始では、表記辞書が変わらない。辞書の明示変更だけが、対象の辞書項目を変える。
- 写しのファイルが版1の形式のままで、Whisperの初期プロンプトが今と同じになる。
- ファイルを外から書き換えて起動すると、その内容が差分として取り込まれ、DB・写し・変更記録が一致する。
- 関連テスト：AI仕上げ（`run_full_cleanup`）と登録語のテスト、系列Iのテスト。

**T0 実行時領域の隔離（最初に行う。並列化の前提）**

- `tests/conftest.py` を追加し、autouseの関数スコープfixtureで `MOJIOKOSI_DATA_DIR`・`MOJIOKOSI_OUTPUT_DIR`・`MOJIOKOSI_BACKUP_DIR` を `tmp_path` へ向ける。モジュール定数でパスを持つ箇所は、呼び出し時に読む形か `monkeypatch.setattr` で差し替える（from-importした名前は差し替わらないため、該当箇所を先に洗い出す）。

**T1 実行器と層**

- 開発用依存として `pytest` と `pytest-xdist` を導入する（本番の依存へ入れない）。`pytest.ini` は既存。実行は `-n 8 --dist loadfile`（並列数は実測で決める。8は仮置き。ファイル単位でワーカーへ配る。SQLite・固定ポートを共有する試験は、T0の隔離後に衝突しないことを確認する）。
- 導入できない環境向けに、現行の1ファイル1プロセス方式を並列化したランナーを予備として残す（`xargs -P` 相当）。
- マーカーで層を分ける：`slow`（10秒以上。上の2モジュール）、`browser`（Edge・Node）、`real_model`（実LLM・Colab・実モデル。既定で除外し、実行できなければ「未実行」と記録する）。
- 層：
  - **関連**：変更したモジュールと直接の依存だけ。実装担当（codex）はこれだけを回す。
  - **領域**：分析コア／パイプライン、保存／Vault、画面・ブラウザーの3組。段階の影響領域だけを回す。
  - **全体**：全モジュール。依頼元だけが、下の表の段階の終わりと最終に回す。
- 日常の再実行には `--lf`（前回失敗のみ）と `--ff`（失敗を先頭）を使う。`pytest-testmon` は、導入してから一覧の再現性を確認できた場合だけ関連層の補助にする（段階の合否判定には使わない）。

**T2 基点比較の機械化**

- 既知失敗56件を `tests/known_failures.txt`（1行1ID、テストID形式を `module.test` に正規化）としてリポジトリへ置く。pytestの `module::Class::test` との対応を正規化関数で1か所に集める。

## 15. 今はやらないこと

- PostgreSQLへの移行：1人用・ローカル限定では、サーバー導入・ローカルとColab間の受け渡し・SQLite固有の書き方の書換えの負担が上回る。複数利用者が1つのサーバーを同時に使う場合、書込プロセスが分かれる場合、B1〜B3の後も書込待ちが実測で問題になる場合に再検討する。
- 補助DB（ドキュメント・キー・バリュー・グラフ・時系列・カラム指向・オブジェクト）：既存のJSON列・`application_metadata`・Obsidian・ファイル保存で役割を満たす。
- ベクトル索引（`sqlite-vec`）・全文検索（FTS5）・集計エンジン（DuckDB）：会話横断の検索や集計が必要になり、データ量が増えてから。C1〜C4の保存があれば後から作れる。
- 会話をまたぐ類似発話検索：インタビューが増え、ベクトル索引を導入する時点で行う。
- Jev・LLM・外部判定を分析コアの判断経路に入れること。
- `waiting_resource / awaiting_input / retry_wait / blocked` の実装（各機能の導入時に別計画とする）。`reused` は別計画の計画1で実装する。
- 推論統計・LLM役割・JEV評価など、能力一覧で利用不可の機能。
- 旧pipeline行の大きな値の移行と縮小。話者・発話の正本をJSONから表へ移すこと（表の利用実績を見てから別計画）。
