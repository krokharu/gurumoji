# Gurumoji 日本語UI文言と状態の仕様案

2026-10-02 UTC / 設計案・未実装  
対象HEAD: `88f5e3eea245166ee68ed4dc6c3f99c31e149228`、branch: `dot/cloud-cpu-setup`。確認開始時のアプリGitはclean。対象は現行template/JavaScript/backendと、統合済みDESIGN・Software VaultのW01〜W08。アプリソース、runtime、研究データ、既存試作は変更していない。

## 1 結論

**動詞が示す処理と、確認できた状態を一致させる。** 「手動」はコード付与と測定設定へ分け、「公開」は実際のVault保存へ改める。見出し、ボタン、完了通知は同じ実行状態から決める一方、計算・本体保存・Vault保存・研究者確認・通信の状態は別々に示す。

先に直すのは、failedを実行中と呼ぶ表示、再試行しないボタンの「再試行」、採用と実行を一度に進める「開始」、閲覧端末を示す「このPC」。見た目だけの書換えでは解決しない箇所を以下で明示した。25件は文言の対象箇所数であり、新規不具合数や改善効果の測定数ではない。

### 今回確認した重要な条件

- 現行のfailedに対する`allowed_actions`は空。画面の「失敗した処理を再試行」は実際には設定画面を開く場合がある。waitingでも理由と許可操作を読まなければ「再開できます」と約束できない
- 現行の手動測定は「開始」でdraft保存→試行→adopted保存→全件実行へ進む。明示採用やレビュー待ちは未実装。文言だけを「試す」に変えてはいけない
- 中止要求を送信中、要求を受け付けた状態、処理の中止完了は別。通信失敗は処理停止や未保存の証拠にならない
- 本体の固定ファイルを上書きしない契約・読取時hash照合はある。しかし定義の履歴不変性、実行時の採用版固定、試行の人による確認記録を保証する契約は未整備
- 個別AI見解などの実行入口はCSSで隠れている。案内文を変えるだけで「実行できます」とすることはできない
- 送信説明と保存先説明にも範囲の不足がある。AI見解のpayloadには役割・コード・重要フラグ等も入り、pipelineのVault保存は3先の管理表に加えてResearchVaultも扱う。文言を短くする際にこの内容を落とさない

参照: [設計入口](../../../DESIGN.md)、[設計契約](ui-design-contract.md) §3〜7、[実装計画](ui-design-implementation-plan.md) W01〜W08。

## 2 共通語彙

| 用語 | 利用者へ示す意味 | 避ける使い方 |
|---|---|---|
| 設定・コード付け | 分析設定、研究者が付けるコード、関連する記録を編集する場所 | 測定規則を選ぶ操作まで「手動」で一括する |
| 測定を設定 | 入力と計算規則を指定する。説明文を書くだけでは規則にならない | 「独自分析」「自由に測定」など、自然文から任意の計算を作るように見せる |
| 少数の発話で試す | 対象から定めた順序・件数を測定する | 代表性を検証していない試行を「サンプルで検証済み」とする |
| この定義を採用 | 使う測定内容を明示的に選び、採用状態を保存する | 計算開始、研究の妥当性確認、試行レビューの永続保証と同義にする |
| 全件で実行 | 表示した除外条件を適用した対象全体に実行する | 除外を含む元の全発話へ実行するように見せる |
| 算出済み | 値を計算できた | 値や解釈の正しさ、人の確認まで保証する「有効」「検証済み」 |
| 欠測 | 対象だったが値がない。理由を取得できれば添える | 0、未実行、対象外を一つの「なし」にする |
| 対象外 | 指定した条件によって集計から外した | 欠測と同数にまとめる |
| 保存済み結果 | 特定の実行で保存された入力・条件・結果 | 現在データを再集計した画面に「保存済み」と表示する |
| 現在のデータと差分あり | 保存時と現在の入力・分析条件が異なることを照合できた | 結果を消すべきだと読める「無効」、不明時の「最新版」 |
| 確認記録なし | 対象の確認記録がないことを確かめた | 人が一度も読んでいないと断定する「未確認」。読取失敗は「確認記録を確認できません」と分ける |
| Vaultに保存 | 設定された保存先へ書き出す | 「公開」「端末に保存」「全Vaultに同期」 |
| ダウンロード | 閲覧中の端末へファイルを取得する | Gurumoji実行環境への保存と同義にする |
| 接続先 | 選択した処理サービス・LLMの実際の宛先 | 遠隔ブラウザーから見た「このPC」「ローカル」の無条件使用 |

「版」は短い通常表示、「ID・hash・出力列・技術情報」は詳細へ置く。詳細を折りたたんでも、対象、単位、対象数、欠測数、保存先、実行するかどうかは主操作の近くに残す。既存の専門用語は詳細で保持するが、`pipeline`、`永続ゲート`、`binding`、`committed`を通常UIの説明へ移植しない。

## 3 状態ごとの短い文と許可操作

以下は表示adapterの提案。UI上の語彙であり、backendに新しい状態を保存する要求ではない。`ready`は全体実行statusにはなく、開始前の確認と個別工程で扱われる。実行の可否は実際の検証結果・API応答に従う。

| 状態と確認条件 | 見出し・補助文の例 | 許される操作と停止条件 |
|---|---|---|
| 開始前の確認中 | 「開始条件を確認しています」 | 設定の閲覧・閉じる。開始可と表示しない |
| ready相当 | 「開始できます」＋残るモデル読込条件があれば隣接表示 | 対象・未保存・必要設定・確認項目が揃った場合だけ開始。推論成功は保証しない |
| accepted | 「開始待ち」 | `cancel`がある場合だけ「中止を依頼」。受付済みを計算開始済みにしない |
| running | 「分析中」＋「処理：{工程名}」 | `cancel`がある場合だけ中止。画面を離れる操作は処理中止と分ける |
| waiting | 「分析が待機しています」＋取得した理由 | `retry_publication`なら「Vaultへの保存を再試行」、`retry_failed`なら「失敗した処理を再試行」。両方なければ「設定を見直す」等、実際にできることだけ。待機理由不明ならそのまま示す |
| failed | 「分析が停止しました」＋「{確認できた原因}」 | 現行は許可操作が空なので同じ実行の再開を約束しない。設定確認は可。別の分析開始は対象・条件の再確認を伴う。確認できた保存物への読取入口は保持 |
| 中止要求の送信中 | 「中止を依頼しています」 | 重複送信を防ぐ。送信済み・受付済み・中止済みと言わない |
| cancelling | 「中止の完了を待っています」 | 再中止ボタンは無効。サーバーのterminal応答まで完了表示をしない。現行`active`は取消可能性から計算されるため、`active=false`を停止証拠にしない |
| cancelled | 「分析を中止しました」 | 保存済みを確認できた結果だけ開く。「すべて元に戻しました」は不可 |
| completed | 「分析が完了しました」 | 表示対象run・計算・本体保存・選択Vaultの状態を別に明示。「結果を見る」が現在データを開く間は固定runを開くと約束しない |
| 編集の保存中 | 「変更を保存しています」 | 二重送信を防ぐ。保存中に追加した編集は別の未保存状態として保持 |
| save conflict | 「別の更新があるため保存できません」 | 現行の退避機能がある画面では「未保存内容をダウンロード」→「最新の内容を開く」。無断上書き、退避前の自動再読込は禁止 |
| stale | 「保存後にデータが更新されています」 | 保存時の結果を保持。再分析は別操作。差分がないか確認できなければこの状態に決めつけない |
| unknown | 「最新の状態を確認できません」＋「最後の確認 {時刻}：{状態}」 | 前回状態は過去のものと明記。再取得の副作用を確認してから再取得。成功・失敗・中止を推測しない |
| missing | 「値なし」または「欠測：{確認できた理由}」 | 計算対象・理由・根拠が取れるときだけ確認先を示す。測定できなかった値を0にしない |
| zero | 「0秒」など数値と単位、必要なら「集計に含む」 | 有効な入力から算出した0だけ。平均の分母へ含めるかはその計算法に従う |
| inaccessible run/artifact | 「保存済み結果を開けません」＋取得できた理由 | 同じ結果の再取得、確認できる別ファイル、履歴へ戻る。現在値への自動置換・再計算・新規実行は禁止。404だけで削除やアクセス権不足と断定しない |

根拠コード: `analysis_core.py:19–30,42–76`、`analysis_pipeline.py:752–812,823–845`、`analysis-execution.js:302–327,393–476,524–539,602–636`。工程の完了割合は`analysis_pipeline.py:792–812`の成功終端数に基づく。処理時間の割合ではなく、対象外工程も成功終端へ含む。出すなら「工程の完了 {p}%」とし、残り時間へ換算しない。

## 5 保存と確認を過剰に保証しない

### 採用とレビュー

採用状態は現行DBに保存されるが、**誰かが個票を読んだ事実の永続保証ではない**。`analysis_pipeline.py:227–256`はstatusとrevisionを保存し、`trial_definition:258–280`は件数・値・入力hashを返す。試行IDと定義版と確認者を結んだgateはない。画面のチェックを付けたことだけで「研究者確認済み」と表示しない。

当面、確認操作が実装された後でも「この画面で試行値を確認」に限定する。確認を保存する機能がなければ再読込後の確認済み表示を出さない。記録がないと確かめた場合だけ「確認記録なし」、読取失敗なら「確認記録を確認できません」とする。既存の発話準備記録にある本文・音声確認（`static/app.js:7509,7586–7595`）は別の対象の記録であり、測定定義レビューへ流用しない。生成Vaultノートに付く`review_status="unreviewed"`（`analysis_store.py:613,624`）も初期ラベルであり、人がこの試行を確認した記録とは異なる。

### 版と固定結果

`analysis_store.py:400–426`は固定ファイルの上書きを拒否し、`304–312`は読取時のhashを照合する。一方、同IDの定義はdraft保存でも更新され、`analysis_pipeline.py:640–643`は実行時に現行定義を読み直す。従って次を分ける。

- 言える範囲: 「この実行で保存した結果」「保存時の入力{版}」など、取得できた実際のmetadata
- 条件付き: 「この定義で実行」には受付内容の固定、または不一致時の安全停止が必要。提案の採用後も対応fixtureで確認する
- 言えない範囲: 「採用版は永久に変わりません」「確認済み定義で必ず実行」「記録は改ざんできません」「いつでも同じ画面に戻れます」

変更防止と変更検知、保存byteの一致と計算意味の一致を混同しない。旧runで版の対応を確かめられない場合は「測定定義の版を確認できません」と表示し、現在の定義で来歴を補完しない。

### 保存先ごとの書式

1つの総合成功色で処理を終わらせず、取得できた対象ごとに「結果ファイル：保存済み」「ResearchVault：保存済み」「InputVault：未完了」のように名詞を付ける。pipelineの`publication_targets`と`publications`はInput／Orchestrator／Visualizationの3先だが、実処理の`publish_result`は`store.publish`へ結ばれ、ResearchVaultも書き出す。archiveの`vault_status`はResearchVaultを表す。3先の配列を全保存先一覧とみなさない。

現行はResearchVaultの例外を`vault_status=conflict`として返し、pipelineは3先のoutcomesを判定する（`app.py:1578`、`analysis_pipeline.py:504–508,620–631,737–750`、`analysis_store.py:588–697`）。独立した[合成契約probe](../50-Tests/ui-design-evidence/2026-10-02/microcopy-contract-probes.json)は元のM0〜M7処理と元の`store.publish`を合成adapterで使い、3先published／ResearchVault conflictでも全体completedになる組合せを再現した。これは実Vault・GUIの成功や障害発生を検証したものではない。W03で全体完了を4先成功へ読み替えない。

同probeではinputだけを指定しても4保存経路のattemptがあり、管理表上は残る2先がnot_selectedになる。現UIのcheckboxは3先一括のため、これは狭い保存先選択を追加する際の契約上の留保。現在のpublisherを変えずに「選んだVaultだけに保存」「失敗したVaultだけ再試行」と約束しない。

checkbox OFFは`publish=False`で本体を保存し、Vault工程を対象外にする（`analysis_pipeline.py:476–482,583–588`）。probeのこのケースはpublication記録が3先not_selected、ResearchVaultの`vault_status`はpending、保存経路attemptは0だった。したがってこの実行に対するResearchVaultは「対象外」と表示し、pendingだけで未完了の警告を出さない。既存のVaultファイルを削除する操作ではない。このcheckboxは基礎pipelineの設定で、AI見解成功時の自動archive等を含むアプリ全体のVault保存停止ではない。

結果ファイルが保存済みで再試行可能と分かる場合だけ「結果ファイルは保存済みです。Vaultへの保存を再試行できます」。どのVaultが失敗したかは別行に出し、操作の対象がそこだけとは示さない。不明なら「{Vault名}への保存結果を確認できません」。保存先フォルダー、実行環境、閲覧端末のダウンロードを必要時に示す。利用者の手元のObsidianへ到達できることまで保証しない。

生成ノートの`published`は「すべてのノートが存在する」という保証でもない。研究者が削除したノートを再作成しない所有権保護があり、missingを尊重した結果でも保存先全体がpublishedになり得る（[独立契約確認](../50-Tests/ui-design-evidence/2026-10-02/microcopy-contract-review.md) §2）。現行`vaultNotesMessage`の「削除されていたノート{n}件は作り直していません」（`static/analysis-storage.js:122–129`）を完了要約から落とさない。例は「保存処理が完了しました。削除済みのノート2件は再作成していません」。この注意を新たな失敗や無断復旧の要求へ変えない。

## 6 色と読み上げの仕様案

### 状態の見た目

色値は既存CSSを正本とし、ここで新しいtoken表を作らない。以下は役割の提案であり、色そのものによる理解を前提にしない。

| 表現 | 使用する場面 | 一緒に表示する文字 |
|---|---|---|
| 控えめな緑の強調 | 実行中の現在工程、主要な次操作 | 「分析中」「中止の完了待ち」など実状態。成功のチェック記号と共用しない |
| 完了の緑と完了記号 | 指定対象の完了・保存成功を取得できた | 「結果ファイル：保存済み」等、何が完了したか |
| 通常の中立色 | 未実行、開始待ち、対象外、モデル読込未確認 | 「未実行」「開始待ち」「未確認」を省略しない |
| 注意色 | 再確認、版差分、保存競合、利用者の対応を要する待機 | 理由と次操作。すべてのAI下書きを警告色にし続けない |
| エラー色 | サーバーの確定したfailed、保存拒否 | 「停止」「保存できません」と対象。通信未確認に処理失敗色を流用しない |
| 無効な操作の表現 | 採用条件不足、再生不可 | disabled状態と「再試行してから採用できます」等の理由。色の薄さだけに頼らない |

「未確認」は処理未確認か人の確認記録不足かを明記する。既存の薄い緑を「すべて安全」「研究として確認済み」と読ませない。computed styleと実backgroundのcontrast、focus、disabledの識別はW05の受入で確認する。

### Screen readerへの通知頻度

**基本は状態が変わったときに1回。pollingごと、秒ごと、同内容の再描画ごとには通知しない。** この頻度はGurumoji向け設計案で、WCAGが指定する秒数ではない。

- 1つの操作について、短い専用`role=status`／polite領域を1か所使う。見出し・chip・ボタン・ログを全部liveにせず、可視状態から同じ意味の短文を作る
- 通知の重複キーは対象・実行ID・状態の軸・状態・工程・エラー種別。新しい対象Aの完了を編集中Bの完了として通知しない。長いIDは発話せず対象名を添える
- 開始受付、待機への移行、中止受付、中止完了、計算完了、保存先の最終結果はそれぞれ1回。中止クリック直後は「中止を依頼しています」、応答後は「中止の完了を待っています」と別事実を伝える
- 進捗は工程変更を基本単位にする。短時間で複数工程が変わったら最新の工程へまとめる。任意の割合通知を付けるなら初期案は10ポイント以上の変化かつ前回から15秒以上とし、実ATで邪魔になれば減らす。割合を計測できない処理へ適用しない
- 完了・操作を要するエラーは上の間引きを待たず1回伝える。入力の保存競合のように現在操作が止まった場合は、エラー要約をフォーカスで示すかalertで示すかを選び、同文を両方で二重通知しない
- 通信失敗は最初の1回を通知し、同じ接続失敗の繰り返しは無音。最後の確認時刻と状態は可視のまま更新する。再接続して取得できたときに「実行状態を確認できました：{状態}」を1回
- 毎秒の経過時間、全ログ、進捗barの小刻み更新はliveにしない。ログは利用者が開いて読める。barには工程単位の割合である名前と値を付ける
- 保存中に追加編集が残ったときは「保存しました。追加の変更は未保存です」を1回。単に「保存しました」の成功音だけで終えない
- 設定の入力文字ごとにvalidation全文を読まない。送信時、項目確定時、実際に可否が変わったときに必要な内容を出す。エラー後も入力とfocusを保つ

現行は`templates/views/analysis.html:59`の工程sectionがpoliteで、`analysis-execution.js:538`は350ms間隔のpollを設定する。属性があることは発話品質の合格ではない。同一stateのDOM更新、ページを離れた実行、複数保存先の同時完了を実ATで確かめる。

- [ ] エラーは具体的で可逆な次操作を示すか。根拠なく「すべて保持」「安全」「いつでも復元」を付けていないか
- [ ] 狭幅で短くした結果、AI下書き、限界、欠測、版、保存先、主張が消えていないか
- [ ] 読み上げは1遷移1回か。350ms polling、秒時計、log、重複live領域で同じ内容を連読しないか

### 最小の受入例

1. running→failedで見出し・chip・操作が一致する。failedのreviewは「設定を見直す」で、そのクリックを再試行と記録しない
2. 中止POSTの応答を保留し、送信中を確認。cancelling応答後も中止完了にしない。通信断とcancelled応答を別fixtureで確認
3. 本体成功＋ResearchVault成功＋InputVault失敗を表示し、InputVaultの失敗を総合成功文で消さない。3生成Vault成功＋ResearchVault conflict＋全体completedも別fixtureで確認する。OFF＋ResearchVault pendingはこの実行の対象外。限定先だけの再試行と案内しない
4. 保存開始後に編集を追加し、成功後も追加分の未保存表示が残る。409では入力と退避手段が残る。timeoutでは成功・失敗を断定しない
5. durationの60／2／0／欠測で平均20.7、分母3。全欠測は「算出できる値がありません」、対象0は「対象の発話がありません」、未実行は「未実行」。3状態を0秒へ集約しない
6. 同じ定義名でdurationから文字数へ変え、古い試行を採用できない。試行応答が遅れて返っても変更後の版と取り違えない。永続レビューgate未導入ならその保証を表示しない
7. stale、来歴不明、artifact404、hash409、元発話なし、時刻欠測を別fixtureで確認。保存済み結果の閲覧から現在値の再計算や外部AIを呼ばない
8. モデルmissing／unknown／cachedを同じ「準備完了」にしない。閲覧端末と実行環境が別でも送信先説明が正しい。モデル・実データは動かさずstubで検証
9. 1実行の同状態pollを繰り返し、実ATで開始・工程変更・待機・中止・完了の短い通知を確認。実AT未実施ならV4未実施と記録
10. 「内容・文脈検索から実行」の案内先へ、production CSSと通常pointer／keyboardで到達する。hidden要素のJS clickを代替合格にしない

上記は実装後の受入設計であり、このUI受入は実行していない。現行の保存先経路と失敗時の契約については独立した合成probeの確認を引用した。V1/V2/V3/V4/V5の区別を既存受入方法に従って維持する。
