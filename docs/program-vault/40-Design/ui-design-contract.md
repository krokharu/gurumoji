日本語の録音を確認し、発話を直し、分析から根拠へ戻り、研究結果を保存する作業を支える。まず**実行入口と実際の処理、測定の説明と計算規則、表示結果と入力版を一致させる**。濃緑と紙色の静かな既存UIを土台にする。

## 3 守る実装契約

1. 既存API、ID、フォーム名、URL、revision確認、保存経路を再利用する。React/Tailwind移行、全画面生成、別状態ストアはこの計画の前提にしない
2. 実行中対象と編集中対象を分離する。処理完了で別の編集中データを置き換えない。未保存確認、競合draft退避、削除Undo、CSVのpreview→適用→通常保存を保つ
3. 発話ID・生成時本文・話者・時刻・入力revision/hash・run IDを保持する。古い結果に現在の来歴を補わず、不明は不明とする。古い引用を現在音声へ黙って接続しない
4. 欠測、未実行、失敗、計算済みゼロを分ける。図・表・出力の対象集合、分母、除外理由を一致させる。観測話者数と実参加人数を混同しない
5. AI下書き、研究者編集、研究者確認を分ける。実行成功・schema合格を科学的妥当性や研究者の採用に置き換えない。頻度・感情・発話量から重要性・合意・内面を自動断定しない
6. 閲覧・検索・比較結果を開く操作は、新しい推論や外部送信を暗黙に始めない。基礎pipeline、計画相談、個別分析の能力と送信先を別々に説明する。AI見解は発話・話者名／役割・研究質問だけでなくコードと重要フラグ、設定時には専門家の短い説明・手順情報も送る。計画相談には入力した目的文を送るため、そこへ貼った本文まで「送らない」と保証しない
7. 研究者所有ノートの本文・タグ・別名を再生成しない。生成ノートは既存の履歴保護経路を通す。SQLは追加のみ。保存形式・移行変更はバックアップ／dry run／復旧を設計してから行う

根拠: [AGENTS.md](../../../AGENTS.md)、[詳細開発規則](ai-development-rules.md)、DG-01/02/06、UX:S01/UX:S15/UX:S17/UX:S20。文献の一般知見と既存契約は別の根拠として使う。

## 4 情報構造と主要フロー

上部4入口と `#/new`、`#/data`、`#/data/<id>`、`#/analysis/<id>`、`#/speakers`、既存の根拠queryリンクを保つ。新規作成はファイル→設定→開始、1データは発話編集／会話・話者／議事録・アウトライン／ファイル・管理を維持する。

分析内は当面、現在の各結果部品をそのまま使い、正しい実行入口・現在地・版を補う。次にADR-118の「結果を見る／比較する／分析を組む／データ・出力」を小さい単位で評価する。手法は結果の分類、手動コードは解釈作業として扱い、手動測定と同じ意味の「手動」へまとめない。旧入口は移行中の戻り口として残し、同じ結果を二重描画しない。

| 研究者の仕事 | 常に見える文脈 | 完了の意味 |
|---|---|---|
| 原音を確認して直す | 対象・未保存・選択発話・再生位置 | 指定版の保存成功。人の確認状態は別 |
| 結果から根拠へ往復 | run／入力版・選択引用・前後文脈 | 同じ結果・filter・位置・focusへ戻れる |
| 測定を定義する | 入力列・規則・型・尺度・出力単位・対象 | 試行値を見て明示採用した定義版が固定される |
| 分析を待ち回復する | 対象・工程・状態・最後の取得時点 | 計算／保存／Vault書出しそれぞれの結果が分かる |
| 比較して出力する | 比較集合・条件・分母・親run | 表示と同じ固定結果・来歴を持つ出力 |

根拠: DG-05/06、[ADR-118](decisions.md)、UX:K01/UX:K02/UX:K05/UX:K09/UX:K13。優れた情報構造であるとの実証は今後行う。

## 5 部品ごとの実装契約案

### 対象と表示版の帯

対象名、現在データ／保存済みrun、算出日時、対象数と欠測・除外、更新必要を短く示す。hash・設定全文は詳細へ置く。対象数の意味を曖昧にしない。値がないlegacy runは「版不明」。既存レスポンスと固定packageのartifact読取から始め、表示のためだけに新しい保存体系を作らない。artifactのhash一致は、定義版や研究内容の妥当性の証明ではない。固定成果物の閲覧を、再起動後に自動回復し得るpipeline状態取得と分ける。

### 測定定義と試行レビュー

名称・説明・列名は規則の説明であり計算命令ではない。対応する入力列・規則・型・尺度・手法を見える形で選択／確認し、単位は規則から説明する。任意の自然文による新尺度生成を装わない。

提案フローは「編集→少数で試す→個別値・欠測理由・限界を見る→この定義を採用→全件実行」。初期修正は既存draft/adopted APIとrevisionを利用し、画面内の『試行確認待ち』を新しい永続statusに勝手に追加しない。現行は同一IDのdraft保存が旧adopted行を上書きするため、既採用の変更試行は別draft ID等で保護し、取消時の逆PUTを復旧策にしない。定義または入力版が変わればレビューは再確認対象。現行trialは件数・有効値・input_hashのみで個票IDと欠測理由を返さないため、個票レビューには後方互換のresponse拡張が必要。加えて、受付時bindingの版と実行時に再取得する定義が異なる隔離再現がある。固定定義snapshotを使うか、版不一致で安全停止する実行境界対策を必須とする。人がレビューした事実を保証する採用gateのサーバー強化とは分けて計画する。

通常表示にも試行した定義版・入力版、全体→除外→試行の関係、計算の限界を短く残す。定義変更後は試行を失効させ、編集内容とfocusを保って再試行へ導く。欠測の確認入口は発話を特定できる名前を持ち、固定した試行入力と現在の編集を分ける。

### 結果と根拠

結果cardは質問／手法、対象、値または主張、制約、根拠、次操作を持つ。すべてのcardを大型の装飾面にしない。引用は生成時と現在の違いを表示し、元音声、前後発話、反例へ進める。再生中の発話、編集中の選択、保存した引用は別状態にし、再生追従で編集選択を奪わない。文字修正で原音を編集せず、精密な時刻が無い場合は推定を精密な引用として見せない。desktopの開閉paneとmobileの全幅表示は試作候補。採用前は既存details＋音声往復を保つ。

狭幅の根拠画面でも、照合する主張、AI下書き、取得できた確認状態、主張の限界、選択発話IDを残す。「確認記録なし」と記録の読取不能を分け、人が未読とは断定しない。研究者メモを別状態へ移す案は、戻る／展開の負担を含めて比較する。

### 状態と回復

見出し・chip・主操作・通知を同じ状態表から決める。UIから推測した状態でbackendを上書きしない。

| 軸 | 表示する区別 | 混同しないもの |
|---|---|---|
| 編集／確認 | 未保存・保存中・保存済み・競合、別に人の確認 | 保存済み＝確認済み |
| 実行 | accepted/running/waiting/failed/cancelling/cancelled/completed | 中止要求＝中止完了、通信断＝処理失敗 |
| 結果の版 | 現在入力・固定run・更新必要・来歴不明 | 新しい日時＝同じ入力 |
| 成果物の保存先 | 本体保存、Vaultごとの未選択／処理中／成功／失敗／競合／不明 | 計算完了＝全保存先成功 |

waitingは理由と実際のallowed actionを見せる。現行failedでは同じrunの許可操作が空なので、設定を開く操作を「再試行」と呼ばない。保存済み成果を開く入口は残す。中止は送信中・受付済み・完了を分ける。Vault再試行の可否と範囲も実契約に従い、保存先1つだけをやり直せると先取りしない。全体%は工程基準と明記し、処理時間へ換算しない。

「結果を公開」は「設定済みのVaultにも保存」等の実態に合う文言へ改める。**現行APIのtargetはInput／Orchestrator／Visualizationの3種だが、非空ならその3先とResearchVaultへの処理を試みる。** inputだけの指定でも他2先は台帳上not_selectedになりながら処理経路へ入り、ResearchVault conflictでもpipeline completedになることを[合成probe](../50-Tests/ui-design-evidence/2026-10-02/microcopy-contract-probes.json)で確認した。実Vaultへの書込み検証ではない。対象配列・not_selected・completedから実際の保存範囲や全4先成功を推定しない。選択を実writerへ渡し、Researchを含む結果を照合するW03の契約対策が必要。旧completedは新しい成功条件へ書き換えず、研究者が削除したノートのmissing保護も残す。publishedは全ノート存在の保証ではない。空配列はこのpipelineのVault工程を省略するだけで、他の自動保存の全体OFFではない。詳細は[独立契約確認](../50-Tests/ui-design-evidence/2026-10-02/microcopy-contract-review.md)。

Gurumoji実行環境への保存、閲覧端末へのダウンロード、外部AI送信は別。出力前に固定run／現在filter、含む情報と省かれる重要情報を示し、形式を選ぶだけで全来歴が付くと誤認させない。成功・保持・再試行可能の文言は実装で保証できる範囲に限定する。

## 6 視覚的意図

**日本語の長文と数値を落ち着いて照合できる、控えめな研究作業面。** 既存の緑・紙色・日本語sans-serifを保ち、強い色と面積は主操作・現在地・重要な状態へ配分する。AI感を避けるためだけの紫禁止、紙色禁止、セリフ導入は行わない。

通常の説明・操作名は短い日本語にする。ID等の来歴詳細と開発用のAPI／移行注記は分け、後者を利用者画面の常設警告にしない。[利用者表示v2](ui-design-assets/2026-10-02/prototypes/v2/index.html)は比較8図＋定義変更後の補助2図。初期の仕様注釈付き8図は契約確認用で、密度比較はv2を使う。[独立批評](../50-Tests/ui-design-evidence/2026-10-02/mockup-critique.md)の修正確認は静止表示に限る。Aの段階導入を暫定候補にし、Bの対照面・根拠pane・4タスク入口は個別に利用者検証する。画面の短さを効率や好みの証拠にしない。

| 役割 | 現行値／資産 | 提案と検証境界 |
|---|---|---|
| 本文／作業面 | ink `#18211d`、paper `#f4f5f0`、card `#fffef9` | 継承。実背景・各stateのcontrastは別測定 |
| 主操作／選択 | green `#1c6b50`、dark `#13513c`、soft `#e9f2e6` | 継承。保存成功／人の確認／話者属性を同じ緑だけで表さない |
| 警告／補助／focus | orange `#e87941`、muted `#68736e`、35%緑ring | warning-text・muted-text・focus-ringの役割へ整理。色値はcomputed style後に確定 |
| 書体 | Yu Gothic UI / Hiragino / Meiryo / sans-serif | 継承。新規webfontを前提にしない |
| 文字階層 | 画面によって`.7rem`〜`.9375rem`等が混在 | 本文16px相当、label14〜15px相当、補助13px相当を比較候補にする。WCAG規定値ではない |
| 余白／角丸 | radius16/10px、部品に22px等、可変padding | 値を全統一する前に部品責務を揃える。要約と詳細を分け、警告を隠して密度を下げない |
| 幅／動き | content1280px、960/540pxの境界、既存reduced-motion | 当面維持。固定バー、選択nav、根拠往復のfocus/scrollを優先確認 |

DG-09で計算したdrop補助文字は白背景で3.128:1、話者概要の未保存文字は約2.63〜2.76:1。一方、分析sidebarの未保存は約5.99:1。すべての未保存表示やfocusを一律不合格とせず、CSS cascadeと実描画の用途ごとに直す。密度・幅・行間の候補は現行画像と同一条件で比べて採用する。

## 7 アクセシビリティと評価

WCAG 2.2 AAを設計基準にする。通常文字4.5:1、大きな文字3:1、必要な非テキスト状態3:1を該当条件と例外込みで確認。24×24 CSS pxは2.5.8の原則であり例外がある。44pxやfocus面積のAAA要件をAA必須と誤記しない。

- 可視label、名前・役割・状態、実Tab/Enter/矢印、モーダルの開閉・focus復帰、固定バーに隠れないfocusを確認
- 日本語IME中と入力欄では文字ショートカットを誤発火させない。色だけで話者・選択・欠測を区別しない
- 200%拡大、320 CSS px相当、長い日本語、表の代替、reduced-motionを確認。表の二次元性を周囲の操作までの免除理由にしない
- 更新・保存・失敗は必要なlive通知を持つ。毎秒の進捗でページ全体を読み上げ直さない

受入は **V1 contract/unit、V2 component、V3 browser operability、V4 assistive technology、V5利用者理解** を別記し、各層にpassed/failed/not-runを記録する。V3はproduction CSSと通常pointer/keyboardが必要。非表示要素へのJS click、closed dialogへの値代入、production CSSなしのfixtureはV1/V2の補助証拠であり、操作受入へ繰り上げない。

成功は正しい対象・版での完遂、編集保持、誤測定／根拠不一致の発見、回復、出力整合を主に測る。時間や美観は補助指標。エージェントのシナリオ歩行は利用者実験ではない。詳細: [受入方法](../50-Tests/ui-design-acceptance.md)、UX:S22〜S30、PR:P1/PR:P2。

## 8 採用と保守

推奨順は可視入口・測定意味→状態／版／保存先→accessibility→履歴→タスク別構成・密度。P1の最小修正をIA全面移行まで待たせない。

着手前に[実装計画](ui-design-implementation-plan.md)§6のチェックリストで、確認済み事実、未実装の技術判断、利用者検証待ちの配置選択を区別する。

基本作業はdotで進め、意味のある節目だけSoftware Vaultへ対象commit、決定理由、検証と未実行、次の作業を残す。0.3文書は`88f5e3e`で統合済み。本0.4更新はSoftware Vaultの文書に反映し、アプリのコード・runtime・移入Vaultは変更していない。今後の実装・受入の節目に[運用引継ぎ](../60-Operations/dot-cloud-development-handoff.md)と既存ノートへ記録し、研究者所有ノートへ開発ログを複製しない。
