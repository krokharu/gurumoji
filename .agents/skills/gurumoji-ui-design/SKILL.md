# Gurumoji UI design

[AGENTS.md](../../../AGENTS.md)と対象実装でGurumojiの仕事だと確認し、[DESIGN.md](../../../DESIGN.md)から対象節だけを読む。このスキルは設計知識の取得と更新を支える。アプリが生成する研究用AIプロンプトの変更や、外部AIの実行を指示するものではない。

## 作業に応じた参照

- **既存UIの局所修正:** 対象コード・隣接testと[設計契約](../../../docs/program-vault/40-Design/ui-design-contract.md)の該当条件。研究pack全体は読まない
- **新しい配置や導線の案:** [知識索引](../../../docs/program-vault/40-Design/ui-design-knowledge.md)から対応する研究知見またはpromptを選ぶ。[実装計画](../../../docs/program-vault/40-Design/ui-design-implementation-plan.md)と実装済み範囲を照合し、既存方式との比較・採用条件を示す
- **独立した評価:** [既存UI critic](../../agents/gurumoji-ui-critic.md)の証拠・報告形式を使う。対象commit、URL、許可範囲、対象シナリオを渡す。ソース確認だけなら実画面合格にしない
- **受入:** [シナリオ](../../../docs/program-vault/50-Tests/ui-design-scenarios.md)と[受入方法](../../../docs/program-vault/50-Tests/ui-design-acceptance.md)から必要な層だけを選び、成功・失敗・未実施を返す

通常の作業はdotで進める。Software Vaultの事前更新や全資料読込を開始条件にしない。Vault保存・検索・同期・移行自体が対象へ広がる場合だけ、既存の[専用スキル](../gurumoji-obsidian-memory/SKILL.md)を使う。

## 判断と再利用

出典の主張とGurumojiへの設計仮説を分ける。資料ID（UX:S、PR:）、参照版・取得日・適用条件を保持する。日付不明を推測しない。現在のコードと古い画面説明が食い違えばコードを確認し、重要な不一致を報告する。

別担当へは、対象版／対象作業／ユーザーの仕事／変更範囲／守る契約／必要な根拠・scenario／合否条件を渡す。prompt集を丸ごと付けない。評価と修正は依頼された範囲で切り分ける。

## 意味のある節目で更新

採用した判断は既存ADR、実際の版・検証・未実施・次の作業は既存の運用引継ぎへ。新しい知見は設計契約と知識索引の該当箇所へ狭く反映し、条件・未確定事項・採用理由を残す。重複する規則や作業ログを入口へ足さない。

日付付き研究・証拠packは過去版として凍結し、訂正や意味のある追加調査は新しい日付の版に記録する。既存のsource IDを保ち、別文献には新IDを付ける。URL、参照版、公開・更新日、取得日、確認した節、支持する主張と限界を添える。公開日不明はnullとし、取得日で代用しない。現行の知識索引から採用版と置換理由へ案内し、古いsnapshotを現在の推奨として読み込ませない。

改善の効果は対象課題、比較条件、測定法、母数、結果、限界と結び付ける。静的probe・agent評価・実ブラウザー操作・利用者評価を混同せず、未測定値は未測定のままにする。変更が裏付けられなければ仮説として残し、廃止した推奨は後継と理由を示す。

実測の記録が必要なら[任意の記録例](../../../docs/program-vault/90-Templates/ui-design-outcome.example.json)から必要な項目だけを使う。例のnull・空配列は未測定で、成功やゼロ件ではない。
